# Авторинг заданий hashpass

## Обзор

Задание — это тренажёр мышления, а не диктант команд. Система ведёт себя как хороший наставник:
**спрашивает, а не отвечает**; показывает, *куда* смотреть (вывод команды, `man`, `--help`, поиск),
а не *что* набрать. Ответ студент добывает сам. В конце — шутка, чтобы было за что любить курс.

**Нарушить букву этих правил = нарушить их смысл.** Подсказка с готовой командой «для удобства»,
«потому что так в соседних заданиях», «на второй попытке уже можно» — это нарушение.

Справочник синтаксиса и рантайма — `dsl-reference.md` рядом (читать перед написанием Taskfile).

## Когда использовать

- Пишешь/переписываешь любой `content/tasks/<id>/` (Taskfile, brief.md, hp/finale).
- Добавляешь `hint`, `on enter`, `say`, формулировку `stage`, финал.
- Ревьюишь чужое задание: сверяй с контрактом ниже.
- Не для: правок движка DSL (`src/hashpass/recipe`, `taskrun`) — там обычный TDD.

## Контракт задания — что есть каждая часть

Тон: обращение на **ты**, коротко, с юмором; ключевые слова DSL — английские, всё для студента — по-русски.

| Часть | Что это | Чего в ней НЕТ |
|---|---|---|
| `stage "…"` | **Цель** в терминах результата: что должно появиться / что узнать. Пути — да. | Команды, ключей, «Этап 1/3», «наберите». |
| `brief.md` | Теория: как устроена команда, **обобщённые** примеры на *других* именах/путях/числах; раздел `## Задание` с реальными путями. Заканчивается «Нажми **Enter**». | Команды, решающей это задание; путей задания внутри примеров. |
| intro `say` | Одна фраза-**завязка**: настроение, повод, интрига. Не инструкция. Потом `read brief.md`. | Пересказа задания, «сейчас вы будете…». |
| `on enter` | **Редко.** Только рамка, которой нет в цели этапа. Никогда не пересказывает цель другими словами (`stage "Дай apt узнать о новом репозитории"` + `on enter "apt пока не в курсе — какой командой…"` = лишнее: оставь только цель). | Команд, ключей, повтора цели. |
| `on pass` | **Добавка после решения** — одна фраза: факт, прикол, мини-вызов («а теперь попробуй `sl -F`»), следующий уровень. Есть у каждого этапа. | Похвалы без содержания. |
| `hint output "…"` / `hint cmd …` | Реакция на **естественную ошибку**: одна фраза — прочитать вывод или вопрос. Ставится **выше** `tries`. | Названия ключа, команды. |
| `hint tries N` | Лестница **вопрос → куда смотреть → понятие**; **одно предложение**, оставляет подумать. Каждая ступень срабатывает один раз. | Готовой команды с путями. Абзацев. |
| `hint idle N` | «Долго сидишь»: перечитай цель и вывод последней команды. | Ответа. |
| `hp/finale` | `#!/bin/sh` + `cat <<'ART'`: **большой мем-фоточка** (braille-арт из картинки мема, 25–45 строк, 80 колонок) + одна строка-подпись с шуткой про задание. | Маленькой картинки, «Отлично, молодец». |
| Среда | Данные — настоящие файлы в `data/` рядом с Taskfile (`mkdata.py`), в образ — `copy data/… /home/student/…` + `chown`; `run` ставит пакеты, права, владельцев **при сборке**; нужный инструмент установлен (`run apt-get install -y …`), иначе `command not found` — не задание, а баг. | `printf`/`touch`-среды в `run`; «искусственных» действий ради приёмки (лишний redirect в файл, когда результат и так виден). |

Приёмка — по **результату** (`observe`/`check`), и любым способом (`variant`), а не по
совпадению с эталоном. `accept cmd` — только когда результата на диске нет (запуск программы,
`man`, `--help`), и тогда с `ok`: команда обязана завершиться успешно. Установка, у которой есть
статус (`dpkg -s`, `command -v`), проверяется по статусу — упавший `dpkg -i` с «dependency
problems» принимать нельзя (это и случилось с `apt-deb`, пока приёмка была по команде).

## Масштаб данных — чтобы была видна магия

Файлы и деревья в задании должны быть **достаточно большими**, чтобы студент почувствовал, зачем
нужна команда: автоматизацию и скорость. Три строки в логе не объясняют `grep`, три файла не
объясняют `find`, пять строк — `sort | uniq`. Ориентиры: журнал — сотни строк, где нужные
десятки разбросаны среди шума; дерево для `find` — десятки каталогов и сотни файлов, из них
нужных — единицы; список для `sort`/`uniq`/`wc` — сотни строк с повторами. Нужные объекты
прячь среди похожих. Примеры в `brief.md` остаются маленькими и на других именах. Где команда
нужна не ради масштаба (`whoami`, `man`, `--help`), правило не действует.

**Данные — настоящие файлы рядом с заданием, а не `printf` в `run`** (пользователь, 2026-09-29:
«вместо создания их из printf посоздавай их рядом и просто скопируй»). Правило:
- Среда задания лежит в `content/tasks/<id>/data/` (журналы, письма, деревья каталогов) и
  коммитится в git. В образ её кладёт `copy data/<что> /home/student/<куда>` (каталог ложится
  содержимым, как `COPY` в Docker), следом `run chown -R student:student …`; права/владельцы,
  которые git не хранит (`chmod 000`, `chgrp`), — отдельными `run` после `copy`.
- Файлы делает `python3 .claude/skills/task-authoring/scripts/mkdata.py` (детерминированно от
  `--seed`): `text --kind ads|notes|log|prose` с `--plant "СТРОКА@0.6"` и `--sprinkle ERROR
  --sprinkle-count 41`, `list` для `sort|uniq|wc`, `tree` для `find` с `--plant a/b/level4_x/`,
  `plant` — вставить ключ в готовый файл, `stats` — подобрать seed. Команду генерации запиши
  комментарием над `copy` в Taskfile, чтобы данные можно было пересобрать.
- `run printf`/`touch` — только для того, что не является предметом задания: маркер-файл,
  пустой каталог-приёмник (`mkdir -p /home/student/dir2`).
- Данные, которые должны появиться **по ходу** задания (после этапа), держи в `hp/` (`hidden hp`
  → `/hp/work/…`, студент их не видит) и переноси скриптом из `on enter exec <скрипт>`: он
  работает внутри контейнера с `/hp` подмонтированным.
- Содержимое `data/` входит в ключ сборки: поменял файл — образ пересоберётся.

Приёмка: по `observe` файла / `check exec` размер не страдает. Вывод `find`/`ls -R` на сотни
строк **нельзя** принимать через `observe output`: порядок обхода каталогов зависит от диска
(readdir на другой машине другой). Бери `check exec grade` со сравнением **отсортированных
множеств** — образец в `content/tasks/find-1/hp/grade` (нормализует абсолютные/относительные
пути, `sort -u`, сравнивает с `find … | sort`), заодно принимает любую команду с тем же
результатом. `observe output` — только для одной строки или стабильного вывода
(`settings similarity 100`, ≤ 64 КиБ — столько консоль передаёт хосту).

## Этапы — сколько и какие

Одно задание — одна тема, но не обязательно один этап. Этап нужен там, где есть **естественная
последовательность**: поставил → запусти (`apt-deb`: установка, потом `cmatrix`); создал →
проверь; узнал → примени. Соседние однокомандные задания одной темы **объединяй** в одно с 2–3
этапами (`help-man` = `--help` + `man`), чтобы студент видел связь, а не россыпь мини-заданий.
Не дроби ради дробления: этап должен добавлять новое действие, а не переформулировать прежнее.
Если у действия есть приз (запуск установленного, показ результата) — он и есть последний этап,
и финал печатается после него.

## Что студент никогда не читает — внутренности

Студент живёт в мире файлов, команд и их вывода. Мир движка — **стадии/этапы, грейдер,
«засчитается», `/hp`, `Taskfile`, `observe`/`accept`** — ему не показывают. Ни в `stage`, ни в
`say`/`hint`, ни в `brief.md`/`theory.md`, ни в финале. Единственный текст про механику —
стандартная строка консоли «проверка после каждой команды; exit — завершить», и её пишет движок.
Структуру задания описывай **содержимым**, а не механизмом:

| Нельзя | Можно |
|---|---|
| «Стадия засчитается по самой команде — файлов она не создаёт» | «Ничего создавать не нужно — достаточно спросить» |
| «Три этапа, где нужно выставить права…» | «Три файла, каждому — свои права…» |
| «Два этапа: 1) … 2) …» | «Два шага: 1) … 2) …» |
| «Тот же приём, что на прошлом этапе» | «Тот же приём, что и при создании файла» |
| «В `/hp` живёт грейдер, прочитать его нельзя» | «Фразу подсмотреть негде — зато есть подсказка» |
| «Как только результат совпадёт с ожидаемым, этап засчитается» | «Ничего отправлять не нужно: результат на месте — увидишь следующую цель» |

Это проверяет линт `tests/content/test_no_internals_in_student_text.py` (красный = переписать).
Комментарии `#` в Taskfile и `README.md` задания — для авторов, там можно всё.

## Логика задания — предпосылка, наследование, проверка вживую

**Предпосылка обязана быть правдой в консоли.** Всё, что текст обещает студенту, должно быть
видно и *работать* до решения: «поезд ходит на каждую опечатку» — значит `sl` в консоли
**запускается**, а не только числится в dpkg; «файл закрыт чужой группой» — значит `cat` его
действительно не открывает. `command not found` у предпосылки = баг сборки, а не задание.
Поэтому `run`, создающий предпосылку, **никогда** не заканчивается `|| true`: пусть сборка
упадёт, чем выйдет задание с ложной предпосылкой.

**Продолжение наследует предыдущее задание.** Действия студента между заданиями не сохраняются,
поэтому задание-продолжение начинается с образа предыдущего и воспроизводит его *конечное*
состояние: `from apt-update:1` (голое имя → твой же namespace, `hashengine build` подставит) +
`run <решение предыдущего>` (`run apt-get update … && apt-get install -y sl`). В `deploy.sh`
родитель стоит раньше потомка. Цепочка — из **того же** курса: не копируй `run`-ы предка руками.

**Задание идёт от обычного пользователя.** Умолчание — `student` (не пиши `settings user root`):
привилегии студент одалживает через `sudo` (в базе он без пароля, так что и `solve sudo …` при
деривации работает). Файлы-результаты — в `/home/student/…`, а не в `/`. `user root` — только
если предмет задания сам root, и тогда над `settings` стоит строка `# root: <почему>` (линт
`tests/content/test_no_internals_in_student_text.py` иначе красный). Ошибка «Permission denied» у
`apt`/записи в `/etc` — повод для `hint output`, а не для root-консоли.

**Проверяй логику приложения, а не только приёмку.** Приёмка (`check`/`observe`) ловит
результат решения; она *не* заметит, что предпосылка ложная (пример: `apt remove sl` проходил
проверку, хотя `sl` в консоли root'а был `command not found` — бинарь в `/usr/games`, которого
не было в PATH root'а). Живой прогон обязан включать всё это:

1. **До решения** — выполни в консоли то, о чём говорит сюжет (`sl`, `cat` закрытого файла,
   `ls` каталога): предпосылка видна, ошибки «нет такой команды/файла» нет.
2. **Цель ещё не достигнута**: финал не печатается сам, до какого-либо действия.
3. Неверная команда ×3 → вопрос; ещё ×3 → источник; подсказка не повторяется на `ls`.
4. Верная команда → зачёт → **последствие видно** (после `apt remove sl` — `sl` больше нет).
5. Линт текстов зелёный.

## Коротко и с добавкой — тон живого разговора

Студент думает сам, поэтому текста должно быть **мало и в нужный момент**:
- Цель этапа — одна строка. `on enter` — только если добавляет рамку, которой в цели нет; если он
  переформулирует цель, его нет. Пользовательский пример «как не надо»: цель «Дай apt узнать о новом
  репозитории» + `on enter` «apt пока не в курсе. Какой командой он перечитывает свои источники?» —
  вторая строка выдаёт ход мысли; оставить только цель.
- Подсказка — одно предложение, чаще вопрос. Не абзац с объяснением.
- Не выдавай сразу «что делать»: завязка → цель → студент работает → **после решения** накидываешь
  ещё (`on pass say`: факт, прикол, мини-вызов «а теперь попробуй…», крючок к следующему заданию).
  Интерактивность живёт после зачёта, а не в инструкции до него.
- Интерфейс (нет кнопки «отправить», `exit`) объясняется **только в первом задании** (`intro-hello`);
  движок ничего про это не печатает, остальные задания считают, что студент уже знает.

## Без дублирования

Каждая мысль звучит в задании **один раз**. Команда и приёмы — в теории брифа; цель этапа
называет результат, а не команду; `say`-завязка не пересказывает первый абзац брифа; `on enter`
не повторяет цель; подсказка отсылает туда, где написано («выход описан в брифе»), а не
повторяет; финал не повторяет `on pass`. Антипример (было в `star-wars`): «добил модуль» в `say`
и в брифе, `telnet telehack.com` в теории, в задании и в подсказке, `Ctrl+]` дважды. Перед коммитом
прочитай тексты задания подряд — `say` → бриф → цель → `on enter` → подсказки → `on pass` →
финал — и всё, что встретилось второй раз, удали. Линт
`tests/content/test_no_internals_in_student_text.py` ловит буквальные повторы длинных фраз.

## Мемы — финал как фоточка

Финал — большая картинка-мем (как фото), а не эмодзи-рисунок. Так делал автор курса: брал мем
(John Cena, Surprised Pikachu, Drake…) и превращал в braille-арт (см. `docs/Задания/Мемы.md`).
Инструмент: `python3 .claude/skills/task-authoring/scripts/meme.py`:

```
meme.py list drake                              # имена шаблонов imgflip (нужна сеть и Pillow)
meme.py render "Surprised Pikachu"              # braille, 80 колонок, ≤45 строк (высокий мем сузится сам)
meme.py render photo.jpg --mode ascii --width 70 # плотностной ASCII, если braille-шрифта нет
```

Правила: **чтобы было хорошо видно** — ширина 80 колонок (влезает в любой терминал; шире —
перенос строк превращает картинку в кашу), 25–45 строк; крупность берётся не шириной, а выбором
мема: крупное лицо/фигура и контраст, а не мелкий текст на картинке; картинка по смыслу задания; под ней одна строка-подпись с шуткой (это и есть
«мораль»); `hp/finale` печатает `cat <<'ART' … ART`. Текст мема в картинку не вставляй — подпись
отдельной строкой. Проверь в консоли (`hashpass run`), что арт влезает и узнаваем.

## Блоки, нумерация, оболочка

- Каталог разбит на **тематические блоки**; их порядок и порядок заданий внутри = нумерация на пуле.
  Источник — `BLOCKS` в `content/tasks/deploy.sh`; новое задание добавляется в свой блок, деплой
  отправляет раскладку `hashengine catalog layout` (только администратор). Ручная правка номеров
  в веб-каталоге переживёт до следующего деплоя.
- Хуки консоли (промпт, приёмка, подсказки) работают в **любой** интерактивной оболочке: `su -`,
  `sudo -i`, пользователь, которого студент создал (`useradd` даёт bash). Задания про
  пользователей и смену личности — можно; `accept cmd` видит команды из любой такой оболочки.

## Лестница подсказок — умолчания

| Ступень | Условие | Форма |
|---|---|---|
| реактивная | `hint output "<точный фрагмент ошибки>"`, `hint cmd <base> missing <флаг>` | «Прочитай, что ответила команда: …» / вопрос по выводу |
| 1 | `hint tries 3` | Наводящий вопрос («Что ты ждёшь увидеть в X? Проверь, что там сейчас.») |
| 2 | `hint tries 6` | Источник: `man <cmd>` + слово для поиска внутри, `<cmd> --help`, «загугли: …» |
| 3 | `hint tries 10` | Только для сложных этапов: понятие или *имя* ключа («нужен ключ рекурсии»). Не команда. |
| долго | `hint idle 240` | «Перечитай цель и последний вывод» |

Простое задание (одна очевидная команда, прямо из теории: `whoami`, `ls`, `man man`, `--help`) —
**одна** ступень-вопрос на `tries 4` или **ни одной**. Три ступени — для многошаговых и «с подвохом»
(скрытые файлы, рекурсия, порядок аргументов `find`, права).

Точные фрагменты ошибок (локаль C): `omitting directory`, `Is a directory`, `paths must precede
expression`, `No such file or directory`, `Permission denied`, `Operation not permitted`,
`Unable to locate package`, `command not found`.

## Пример: было → стало (`cp-more`, скопировать каталог целиком)

```
# БЫЛО — ответ до первой попытки, точная команда на второй
  on enter say "cp с последним аргументом-директорией копирует туда все предыдущие."
  hint tries 2 say "Подсказка:  cp -r /home/student/dir1/. /home/student/dir2/"
  hint idle 30 say "Ключ -r (recursive) даёт cp повторить обход дерева."

# СТАЛО — вопрос, вывод, источник; ключ по имени — только на 10-й попытке
  on enter say "В dir2 пока пусто. После твоей команды там должно лежать всё то же, что в dir1."
  hint output "omitting directory" say "Прочитай ответ cp целиком: он сам сказал, чего ему не хватило."
  hint tries 3 say "Загляни в dir2: что там оказалось? Всё, что было в dir1, или только часть?"
  hint tries 6 say "man cp — найди слово recursive. Или загугли: «cp скопировать каталог со всем содержимым»."
  hint tries 10 say "Каталог — не файл; cp обходит его только с ключом рекурсии. Какая это буква — ты уже знаешь."
  hint idle 240 say "Долгая пауза. Перечитай цель и вывод последней команды — ответ обычно там."
```

Финал не «cp -r — рекурсивный копир», а шутка: `«Копия неотличима от оригинала. Как и твой дипломный проект»`.

## Рационализации, которые НЕ принимаются

| Отговорка | Реальность |
|---|---|
| «Так во всех соседних заданиях» | Соседние переписаны по этому skill. Старый стиль — ошибка, а не образец. |
| «Это единственная новая мнемоника, стоит дать сразу» | Мнемоника живёт в `brief.md`, на обобщённом примере. `on enter` — вопрос. |
| «На второй попытке уже можно конкретику» | Вторая попытка — это ещё не думал. Вопрос на 3-й, источник на 6-й, понятие на 10-й. |
| «Без точной команды студент не пройдёт» | Пройдёт: вывод, `man`, поиск. Если этап непроходим без ответа — сложность не та, перепиши этап, а не подсказку. |
| «Подсказка с командой, но “в общем виде” (`tar -czf <архив> <каталог>`)» | Это команда с плейсхолдерами. Не проходит. |
| «Финал — просто похвала» | Финал — мем/шутка. Похвала без прикола не выполняет требование. |
| «`hint idle 30` — чтобы не скучал» | 30 секунд — это он ещё читает вывод. Минимум 180–240. |

## Red flags — остановись и перепиши

- В `say`/`hint` есть слово «Наберите», «Точно:», «Подсказка:  <команда>», путь задания рядом с именем команды.
- `hint tries 1` / `tries 2`.
- `on enter` содержит имя ключа (`-r`, `-a`, `-czf`) или команду.
- `brief.md` содержит команду решения с путями *этого* задания.
- Сообщение `stage` начинается с «Запустите»/«Наберите» или содержит «Этап N/M».
- Финал без шутки.
- Любой текст для студента упоминает стадию/этап, грейдер, «засчитается», `/hp`, `Taskfile`.
- `run … || true` у шага, который создаёт предпосылку задания.
- Задание-продолжение («удали то, что ставил в прошлый раз») без `from <предыдущее>` — или с
  `from`, но без `run` решения предыдущего.
- «Работает» сказано по приёмке, без прогона предпосылки в консоли (п. 1 живого прогона).
- `settings user root` без строки `# root: <почему>`; результат пишется в `/` вместо `/home/student`.
- `accept cmd` там, где у действия есть проверяемый результат (установка, файл), или без `ok` у
  запуска программы.
- Установил и не дал запустить: нет этапа-приза после установки.
- Файл из трёх строк или дерево из трёх файлов там, где команда нужна ради масштаба
  (`grep`/`find`/`sort`/`wc`): магии не видно. Среда набрана `printf`/`touch` в `run` вместо
  `data/` + `copy`. `observe output` на многострочном выводе `find`.
- `on enter` пересказывает цель этапа; подсказка длиннее одного предложения.
- Одна и та же фраза или команда встречается в задании дважды (say/бриф/цель/подсказка/финал).
- Этап без `on pass` (нечего накинуть после решения); финал без большой картинки-мема.

## Процесс

1. Прочитай `dsl-reference.md`; посмотри 1–2 уже переписанных задания как образец тона.
2. Напиши `Taskfile` + `brief.md` + `hp/finale` (`chmod +x`) + `data/` через `mkdata.py`
   (команду генерации — комментарием над `copy`).
3. Парсинг + линт: `python3 -m pytest tests/content/test_bundled_taskfiles_parse.py tests/content/test_no_internals_in_student_text.py -q`.
4. Сборка: `cd content/tasks/<id> && hashengine build Taskfile` (деривация в nspawn; родитель из
   `from` должен быть собран раньше).
5. Живая проверка `expect`-ом по реальной консоли (`hashpass run <id>:1`) — все пять пунктов из
   раздела «Логика задания»: предпосылка до решения, цель не достигнута заранее, лестница
   подсказок, зачёт и видимое последствие, линт. Без этого прогона «работает» не говорить
   (memory `verify-with-expect-before-delivery`).
6. Один коммит на задачу/пачку. На пул (`hashengine push`) — только по явной просьбе; перевыпуск
   **той же версии** пул по умолчанию пропускает (HEAD-дедуп) — `--force` или новая версия.
