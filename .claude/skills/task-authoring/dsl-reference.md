# Справочник DSL Taskfile — по парсеру (`src/hashpass/recipe/parse.py`) и рантайму (`taskrun.py`, `cli.py`)

Строчный язык, блоки отступами. Ключевые слова английские, тексты любые.
Пустые строки и строки, начинающиеся с `#`, игнорируются — **комментарий только на отдельной
строке** (инлайновый `#` внутри `run`/`solve`/`say` сохраняется как текст).

## Файлы задания

```
content/tasks/<id>/
  Taskfile        # рецепт (единственный обязательный файл)
  brief.md        # теория для студента; показывается через `read brief.md` (Markdown, постранично)
  hp/             # скрытый слой: `hidden hp` → внутри контейнера /hp/work/*  (студент его НЕ видит)
    finale        # `#!/bin/sh` + `cat <<'ART'` — финальный мем; вызывается `exec finale` в конце
    grade         # опционально: скрытый грейдер для `check exec grade`
```

Пути `hidden`/`copy`/`readme` резолвятся относительно **папки Taskfile** (`hashengine build` сам
переводит их в абсолютные). `read`/`show file <p>` ищет файл сначала в `/hp/work/<p>`, потом в ФС
студента (`settings workdir`, по умолчанию `/home/student`), потом по абсолютному пути.

## Верхний уровень (колонка 0)

| Директива | Синтаксис | Смысл |
|---|---|---|
| `image` | `image <name>:<ver>` | Имя образа. Без `:ver` → `latest`. Один раз. |
| `from` | `from <ref>[, <ref>…]` | Наследование (транзитивное); правее = приоритет. Голое имя (`from apt-update:1`) `hashengine build` подставляет в namespace владельца (`bunnyton/apt-update:1`); явный `alice/lib:2` остаётся как есть. Задание-продолжение: `from <предыдущее>` + `run` решения предыдущего (действия студента не сохраняются). |
| `run` | `run <shell-команда>` | Выполняется **при сборке**, запекается в образ. Так создаётся среда (`mkdir`, `printf > file`, `apt-get install`, `chown -R student:student …`). |
| `copy` | `copy <src> <dst>` | Хостовый файл/каталог → в образ. |
| `hidden` | `hidden <dir>` | Каталог → скрытый `/hp/work/`. Обычно `hidden hp`. |
| `readme` | `readme <file>` | Markdown-брифинг; показывается после intro. Современные задания вместо него пишут `read brief.md` в intro. |
| `settings` | блок | См. ниже. |
| `voice` | блок `hello <action>` / `bye <action>` | Приветствие при входе / прощание после последнего этапа. |
| `react` | `react on command <action>` | Обработчик на **каждую** команду студента (полный `HP_*`-контекст). Редко нужен. |
| действия | `say "…"` / `read <file>` / `exec <…>` / `show file <p>` | **До первого `stage`** = intro (при входе); **после последнего** = outro (когда всё пройдено). Между stage — ошибка парсера. |

Порядок при входе в консоль: `voice hello` → intro (по порядку) → `readme` → объявление первого
этапа (`──  <сообщение>`) → его `on enter`. Номера этапов студенту **не показываются** — не пиши
«Этап 1/3» в сообщении.

### `settings`

```
settings
  user root          # логин консоли (по умолчанию student). Только с `# root: <почему>` над settings — привилегии дают через sudo
  sudo off           # убрать студента из sudo (по умолчанию on; sudo у student БЕЗ пароля)
  pager on           # длинные read/show file — постранично по Enter (по умолчанию off)
  similarity 100     # порог приёмки observe output, % (по умолчанию 90; 100 = строго)
  type-mode normal   # instant | normal | dramatic — темп печати say/hint
  type-speed 55      # символов/сек
  workdir /home/student
```

## Блок `stage`

`stage "<цель для студента>"` — текст показывается как `──  <цель>`. Тело — с отступом.
Этапы идут по порядку; этап N видит результат этапов 0..N-1 (эталон `solve` предыдущих
этапов прогоняется как подготовка).

### Приёмка — ровно один из способов

| Способ | Синтаксис | Когда |
|---|---|---|
| Derived по файлам | `solve <cmd>` + `observe <path…>` | Результат — детерминированный файл/каталог. Сравнение толерантное (канонизация на 2–3 прогонах). |
| Derived по выводу | `solve <cmd>` + `observe output` | Результат — stdout команды (только чистый stdout по OSC-133; порог `settings similarity`). |
| Существование | `solve <cmd>` + `observe bool <path…>` | Важно лишь есть/нет (файл/каталог), без содержимого. |
| Скрипт/команда | `check exec <файл-в-hp \| shell-команда>` | `exit 0` = принято. Для недетерминированного: права (`stat -c %a`), процессы, архивы, «файла нет». `solve` при этом всё равно обязателен (подготовка следующих этапов), но не деривируется. |
| По самой команде | `accept cmd "<начало команды>" [ok]` (можно несколько) | Команда без следа на ФС (`man man`, `ls --help`, `telnet …`). Образец — **начало** команды (после `sudo`) в любом сегменте конвейера, до границы слова: `cmatrix` ловит `cmatrix`/`sudo cmatrix -s`, но не `dpkg -s cmatrix` и не `ls cmatrix.deb`; `sl` не ловит `sleep`; образец с `/` на конце (`apt install ./`) — префикс. Без FS-грейда. `ok` (на весь этап) — команда обязана ещё и завершиться с кодом 0 (runtime ≥ 20): упавший `cmatrix` — не «запустил cmatrix». Без `ok` — только когда провал тоже засчитывается по смыслу (`telnet` без сети). |

Дополнения к derived:

| Под-директива | Смысл |
|---|---|
| `solve:` + строки глубже | Многокомандный эталон (один шелл; cwd/env живут внутри этапа; `<output>` = stdout последней). |
| `variant <cmd>` / `variant:` | Другое решение той же задачи. Эталон = **общее** для solve и всех variant. Требует `observe`. Расходятся → сборка падает. |
| `exclude <glob…>` | Выкинуть шум из наблюдаемого (`*.log`, `.cache`). |

### Политика команд

| Под-директива | Смысл |
|---|---|
| `neutral <base…>` | «Просто смотрю»: `ls cd cat pwd less head tail`. **Не считаются попыткой** для `tries`. |
| `deny <base…>` | Эти команды **не выполняются** в консоли и не засчитывают этап. Сообщение движка: «Команда «X» здесь запрещена — решите задачу иначе.» |
| `allow <base…>` | Засчитывают этап **только** эти (плюс neutral/cd/exit); остальное блокируется. Сообщение: «Засчитывается только через: …». Взаимоисключимо с `deny`. |

### Хуки и подсказки

| Под-директива | Смысл |
|---|---|
| `on enter <action>` | При входе в этап (после объявления цели). Можно несколько. |
| `on pass <action>` | При прохождении этапа. |
| `hint <условие> <action>` | Условная подсказка. Проверяется **на каждой команде, не прошедшей этап** (включая neutral). **Первое совпавшее и ещё не сработавшее правило побеждает; каждое правило срабатывает ОДИН раз за этап.** |

Условия:

| Условие | Срабатывает когда |
|---|---|
| `tries N` | попыток на этапе ≥ N (neutral не считаются; опечатка/непарсибельная команда — считается) |
| `idle N` | с момента входа в этап (последнего прогресса) прошло ≥ N секунд — оценивается при очередной команде, таймера нет |
| `cmd <base> [has <t…>] [missing <t…>]` | команда с базой `<base>`, у которой есть/нет флаги (`-r`) или слова-аргументы |
| `output "<подстрока>"` | stdout+stderr команды содержит подстроку (вывод берётся из живой консоли) |

Из-за «один раз за этап» лестница пишется **по возрастанию** порогов и сама эскалирует:

```
hint output "omitting directory" say "Прочитай, что ответил cp: он сам сказал, чего ему не хватило."
hint tries 3   say "Что ты ждёшь увидеть в dir2 после копирования? Проверь, что там сейчас."
hint tries 6   say "man cp — найди слово recursive. Или загугли: «cp скопировать каталог целиком»."
hint idle 240  say "Долгая пауза. Перечитай задание: что именно должно оказаться в dir2?"
```

Реактивные (`output`/`cmd`) ставь **выше** `tries`: они точнее, а первое совпавшее выигрывает.

### Действия

| Действие | Смысл |
|---|---|
| `say "текст"` | Напечатать (посимвольно, `type-mode`). Снимаются только внешние кавычки — внутри можно `"` и `«»`; escape-последовательностей (`\n`) нет, одна строка = одно действие. |
| `say dramatic "текст"` | Медленно, с паузами. |
| `read <file>` | Markdown → ANSI, постранично (разделитель страниц — строка `---`, иначе по высоте экрана). Для brief/теории. |
| `show file <path>` | Показать файл как есть (большой → пейджер). |
| `exec <файл \| команда>` | Первый токен — файл в `/hp/work` → запустить его (по shebang); иначе `sh -c`. stdout печатается **мгновенно** (ASCII-арт не «печатается»). Именованные `key=value` после файла → `HP_ARG_key`. |

Контракт `exec`-скриптов: `argv[1]` = команда студента; env `HP_TRIES`, `HP_LAST_OUT`, `HP_STAGE`,
`HP_STATE` (rw json), `HP_HISTORY`, `HP_ROOTFS`, `HP_ARG_*`. Для `check` — exit-код; для
`say`-подобных — stdout. Скрипты — `#!/bin/sh` (в базе нет python), `chmod +x`.

## Рантайм: что важно знать автору

- Консоль передаёт код возврата каждой команды (runtime ≥ 20) — его использует `accept cmd … ok`.
- PATH консоли (и у `student`, и у `root`) включает `/usr/games` и `/usr/local/games` (runtime ≥ 19):
  пакеты вроде `sl`, `cmatrix` запускаются по имени. `check exec` выполняется НЕ в оболочке
  студента — в проверках пиши полные пути или `command -v X || test -x /usr/games/X`.
- `run`, создающий предпосылку задания (`apt-get install -y sl`), — без `|| true`: провал должен
  ронять сборку.
- Кэш сборки: ключ = стамп базы + родители (`ref@build_key`) + шаги. Пересобранный родитель
  инвалидирует потомков; на пул та же версия уходит только с `--force` (HEAD-дедуп).
- Консоль — реальный загруженный Debian (systemd-nspawn, bash). Сборка (`solve`) идёт под
  `settings user` — `whoami`, `$USER`, владельцы файлов совпадают с живой консолью.
- Грейд после **каждой** команды (фоновый сокет) + фоновая проверка ФС каждые 2.5 с. `accept cmd`
  и `output`-подсказки работают только по введённой команде.
- Вывод `ls` в TTY — колонками, в pipe — построчно → `observe output` для `ls` нестабилен;
  бери `accept cmd` или `observe` файла. `ls -la` печатает mtime → не деривируется, используй
  `check exec` по смыслу (`grep -q hidden_key …`).
- Фоновый процесс не переживает команду при деривации: запускай и проверяй в одной `solve:`.
- Изменения в `/` или `apt` в этапе — через `sudo` (у `student` он без пароля, `solve sudo …`
  деривируется). Пакет нужен для среды → `run apt-get …` при сборке (один раз), а не в `solve`.
- В базе (runtime ≥ 21) есть `man` и man-страницы coreutils/grep/find/sudo/apt/dpkg/bash — подсказки
  «man cp» честны. Пакеты, поставленные в `run`, приходят со страницами тоже (dpkg-исключение снято).
- apt в базе (runtime ≥ 22) ставит без Recommends и с молчаливым debconf: студенческий `apt install`
  никогда не откроет диалог (cmatrix через kbd тянул keyboard-configuration и вешал консоль).
- База = `debian:trixie` + `systemd dbus bash sudo procps` (см. `image/base.py`): есть `coreutils grep sed
  find tar gzip apt dpkg`; **нет** `man`, `vim`, `python3`, `tree`, `telnet`, `less` — ставь `run apt-get install -y …`
  при сборке, если задание про них (иначе студент получит `command not found`).
- `hidden hp` → содержимое `hp/` ложится в `/hp/work/` (т.е. `hp/finale` → `/hp/work/finale`,
  вызывается как `exec finale`).
- Формат сообщений движка при отказе политики — фиксированный (см. выше); текст «принято»/«готово»
  движок не печатает — это делают `on pass`/`voice bye`/outro автора.

## Команды

```bash
cd content/tasks/<id> && hashengine build Taskfile      # собрать (деривация в nspawn; apt-задания — минуты)
hashpass run <id>:1                                    # живая консоль студента (exit — выйти)
hashengine images                                      # что собрано
python3 -m pytest tests/content/test_bundled_taskfiles_parse.py -q   # все Taskfile парсятся, ссылки на файлы целы
content/tasks/deploy.sh --dry                          # собрать ВСЕ задания без пуша
hashengine push base                                   # базовый образ этого runtime на пул
```

Пуш на пул (`hashengine push … --task [--force]`) — только по явной просьбе автора курса
(135.106.177.228 — prod).
`hashengine build` берёт namespace из пул-логина (локальный реестр 127.0.0.1:8080 — только без пула). Пул принимает push только под своим логином (`<логин>/<имя>:<версия>`); база — `bunnyton/debian:trixie` (фиксированный тег, владелец bunnyton/админ; `push base` перезаливает только пересобранную базу). Ненайденный ref с одноимённым образом в другом namespace → «быть может, вы искали …?».
`hashengine logout` — забыть кэшированный токен; `login` при живом токене спрашивает про перезаход (`--if-needed` — не спрашивать, для скриптов).
