# Docker: образ и контейнер

Программа никогда не живёт одна: ей нужна своя версия языка, библиотеки, настройки, файлы в
нужных местах. Всё это вместе — **окружение**, и из-за него рождается вечное «а у меня
работает». Docker отдаёт программу **вместе с окружением**, одной коробкой: что лежит в
коробке, то и запустится — на ноутбуке, у коллеги, на сервере.

## Как к этому шли

1. **Сервер на каждую программу** — надёжно, но дорого: 64 ядра крутят один сайт.
2. **chroot** (1979) — процесс видит другой каталог как свой `/`. Файлы свои, а процессы, сеть
   и пользователи — общие с машиной.
3. **Виртуальные машины** (1999) — целый компьютер понарошку со своей ОС. Изоляция отличная,
   но это гигабайты на диске и минута на загрузку.
4. **Пространства имён и cgroups** (ядро Linux, 2002–2013) — ядро показывает процессу свой
   список процессов, свою сеть, своё имя машины и ограничивает ему память и процессор.
   Процесс выглядит как отдельная машина, а на деле это обычный процесс. Это и есть
   **контейнер**.
5. **Docker** (2013) — сделал всё это удобным: окружение упаковано в **образ**, образ описан
   текстовым рецептом, готовые образы лежат в каталоге **Docker Hub**.

Название — из порта: стандартный железный контейнер одинаково грузят краны и корабли, что бы
ни лежало внутри. Docker — «портовый грузчик» для программ.

## Образ и контейнер

- **Образ** (image) — заготовка: файлы системы, программы, библиотеки плюс указание, что
  запускать. Образ не меняется, его только читают.
- **Контейнер** (container) — запущенный образ: живые процессы со своим `/`, своей сетью и
  своими изменёнными файлами. Из одного образа — сколько угодно контейнеров.

Как в программировании: образ — класс, контейнер — объект. Или файл программы и процесс.

                 Виртуальная машина            Контейнер
    ядро         своё                          общее с машиной
    размер       гигабайты                     от нескольких мегабайт
    запуск       десятки секунд                доли секунды

Какие образы уже лежат на машине:

    $ docker images busybox
    IMAGE            ID             DISK USAGE   CONTENT SIZE   EXTRA
    busybox:1.36     b116e1550744       4.42MB             0B
    busybox:latest   b116e1550744       4.42MB             0B

Колонки зависят от версии docker; в старых вместо `IMAGE` — `REPOSITORY` и `TAG`. После
двоеточия — **тег**, версия образа; без тега docker подставляет `latest`.

## docker run: образ → контейнер → команда

    $ docker run busybox echo привет
    привет

Сразу после `docker run` — образ, всё дальше — команда, которая выполнится **внутри**.
Docker создаёт из образа новый контейнер, запускает в нём команду, показывает её вывод, и
когда команда закончилась — контейнер останавливается.

Внутри — совсем другие файлы. Вот корень контейнера alpine:

    $ docker run alpine ls /
    bin
    dev
    etc
    home
    lib
    ...

Ключи `docker run` пишутся **до** имени образа: всё, что после него, docker отдаёт команде.

    $ docker run --name mytest-hello alpine ls /     # --name — своё имя контейнера
    $ docker run --rm busybox hostname               # --rm — удалить контейнер после работы
    5f99c3149877

Имя машины внутри — короткий ID контейнера: у него и правда своё имя хоста.

## Список контейнеров и их статусы

`docker ps` показывает контейнеры, которые **работают сейчас**:

    $ docker ps --filter name=mytest
    CONTAINER ID   IMAGE     COMMAND       CREATED        STATUS                  PORTS     NAMES
    52953ef98f8d   busybox   "sleep 300"   1 second ago   Up Less than a second             mytest-nap

Контейнер, команда которого закончилась, не исчезает: он лежит на диске остановленным, и
обычный `docker ps` его не показывает. Как увидеть всех — расскажет `docker ps --help`. Статусы,
которые там встретятся:

    Up 5 minutes        работает
    Exited (0) ...      команда закончилась без ошибок
    Exited (3) ...      команда закончилась с кодом ошибки 3
    Created             создан, но так и не запущен

Число в `Exited (…)` — код возврата команды, тот же, что `$?` в bash.

## Уборка

Остановленные контейнеры копятся и занимают место. Убирают их по ID или имени из списка —
подкоманда docker называется так же, как удаление файлов. Работающий контейнер так просто
не удалить:

    $ docker rm mytest-nap
    Error response from daemon: cannot remove container "mytest-nap": container is running: stop the container before removing or force remove

Чтобы мусор не появлялся вовсе, разовые запуски делают с `--rm`. А все команды docker
перечислит `docker --help`; всё, что умеют с контейнерами, — `docker container --help`.

## Где это пригодится

- попробовать программу, не ставя её в систему: `docker run --rm python:3.12 python -V`;
- проверить скрипт на другом дистрибутиве: Alpine, Debian, Ubuntu — одной командой;
- дальше по курсу — сервер в контейнере: [docker-web](/web/wiki/bunnyton/docker-web).
