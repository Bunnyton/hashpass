# Один коммит в другую ветку и теги версий

Обычная жизнь проекта: у покупателей работает версия из ветки `release/…`, а разработка ушла
вперёд в `main`. И вот в `main` появилось срочное исправление. Слить `main` в релиз нельзя —
приедет всё недоделанное. Нужен **один** коммит. Это `git cherry-pick`. А когда исправление на
месте, версию отмечают **тегом**.

## Найти нужный коммит

`git log` умеет сужать поиск — и ключи можно сочетать:

    git log main                 коммиты другой ветки, не переключаясь
    git log -- файл              только те, что меняли этот файл
    git log --grep=слово         только те, в чьём сообщении есть слово
    git log -p                   с самими изменениями

Пример: магазин, ищем правку входа.

    $ git log --oneline main -- login.sh
    b3a0256 login: проверка пустого пароля
    6475816 Версия 2.0

    $ git log --oneline --grep=парол main
    b3a0256 login: проверка пустого пароля

`--grep` ищет подстроку: по «пароль» не нашлось бы ничего — в сообщении «пароля». Ищи по
корню слова. `-i` — без учёта регистра.

## cherry-pick: повторить коммит здесь

`git cherry-pick <хеш>` берёт **изменения** одного коммита и повторяет их в текущей ветке
новым коммитом — с тем же автором и сообщением, но своим хешем:

    $ git switch release/2.0
    $ git cherry-pick -x b3a0256
    [release/2.0 a516192] login: проверка пустого пароля
     1 file changed, 1 insertion(+), 1 deletion(-)

Ключ `-x` дописывает в сообщение, откуда взят коммит, — через год это очень выручает:

    $ git log -1
    commit a5161929f884ac36094431fb63ada96e7e4b6759
    Author: Аня <anya@example.com>
    Date:   Wed Nov 4 02:17:59 2026 +0300

        login: проверка пустого пароля

        (cherry picked from commit b3a025663086b1f2db6d2be31c0a3f30a393b4a5)

Важно, **где стоишь**: коммит появится в текущей ветке. Можно назвать и несколько хешей, и
диапазон `A..B`.

Если изменения не легли чисто — будет конфликт, как при слиянии. Решаешь, `git add`, потом
`git cherry-pick --continue`; передумал — `--abort`.

## Что уже перенесено

Хеши у оригинала и копии разные, но git умеет сравнивать сами изменения. `git cherry`
показывает коммиты второй ветки, которых нет в первой; `-` — «такая правка там уже есть»:

    $ git cherry -v HEAD main
    + 8e67ea872f1183e1924fb714dc6d215a37661e08 Корзина: черновик
    - b3a025663086b1f2db6d2be31c0a3f30a393b4a5 login: проверка пустого пароля
    + 6d529a754461b8b87fd0a0257e77c67631f5014c Новые цены

## Почему не merge

`git merge main` в релиз притащит **всю** ветку: корзину-черновик, новые цены — всё, что
сделано после выпуска. Влил по ошибке — `git merge --abort`, пока слияние не закончено, или
`git reflog` + `git reset --hard <хеш до слияния>`, если уже закончено.

## Теги: метка, которая не двигается

Ветка ползёт вперёд с каждым коммитом. Версии нужна метка навсегда: «вот ровно это выпущено
как 2.0.1». Это **тег**. Два вида:

- **простой** (lightweight) — просто имя на коммите;
- **аннотированный** — отдельный объект: автор, дата, сообщение.

Для выпусков ставят аннотированные:

    $ git tag -a v2.0.1 -m "Версия 2.0.1: вход без пустого пароля"
    $ git tag v2.0-test
    $ git tag
    v2.0-test
    v2.0.1

Разницу видно по типу объекта, на который указывает имя:

    $ git cat-file -t v2.0.1
    tag
    $ git cat-file -t v2.0-test
    commit

А `git show` у аннотированного сначала покажет сам тег:

    $ git show --stat v2.0.1
    tag v2.0.1
    Tagger: Аня <anya@example.com>
    Date:   Wed Nov 4 02:18:09 2026 +0300

    Версия 2.0.1: вход без пустого пароля

    commit a5161929f884ac36094431fb63ada96e7e4b6759
    ...

Тег ставится на текущий коммит — или на тот, что назовёшь после имени тега
(`git tag -a v1.2 -m "…" 1a2b3c4`). Ещё полезное:

    $ git describe
    v2.0.1
    $ git tag -d v2.0-test
    Deleted tag 'v2.0-test' (was a516192)

`git describe` называет ближайший тег — так программы узнают свою версию при сборке.

## Теги на сервере

`git push` теги сам не отправляет. Один тег — `git push origin v2.0.1`, все сразу —
`git push --tags`. Имена версий обычно по [семантическому версионированию](https://semver.org/lang/ru/):
`v<мажор>.<минор>.<патч>`, исправление ошибки поднимает последнее число.
