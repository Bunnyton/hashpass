# Как git хранит данные: объекты

Под всеми командами git — простой склад **объектов** в `.git/objects`. Всё, что ты
коммитишь, лежит там: файлы, каталоги, коммиты. Остальные команды — удобные надстройки над
этим складом. Разберёшься в нём — сможешь достать данные даже тогда, когда «обычные» команды
бессильны.

## Имя объекта — хеш содержимого

git берёт содержимое, считает от него **SHA-1** (40 шестнадцатеричных знаков) и кладёт под
этим именем: первые два знака — каталог, остальные — файл.

    $ find .git/objects -type f | head
    .git/objects/26/f9ba9bb1c22d3d4bb549386ca87f04ecead383
    .git/objects/ee/4246c4b461285b5c9efb9da508de0598902244
    .git/objects/aa/7ff13cbc54c81123f72eca37228a52a01e725e
    .git/objects/97/d7b9b314e42569a6a3d00aa8c589f7dda7e35b
    .git/objects/e9/8b5d16e0dbb30f55503aad23ecc22f158f1a70

Пять объектов на один коммит с двумя файлами в двух каталогах. Хеш считается **по
содержимому**: одинаковые файлы — один объект, одна буква разницы — совсем другой хеш.
Проверить можно `git hash-object` — он считает хеш, как это сделал бы git:

    $ echo "Полив по вторникам" | git hash-object --stdin
    97d7b9b314e42569a6a3d00aa8c589f7dda7e35b

Внутри файл объекта — это заголовок «тип размер», нулевой байт и содержимое, сжатые zlib.
Распакуем Python-ом и заменим нулевой байт переводом строки, чтобы было видно:

    $ python3 -c 'import sys,zlib; sys.stdout.buffer.write(zlib.decompress(open(sys.argv[1],"rb").read()))' .git/objects/97/d7b9b314e42569a6a3d00aa8c589f7dda7e35b | tr '\0' '\n'
    blob 35
    Полив по вторникам

## Четыре типа

| Тип | Что хранит |
|---|---|
| `blob` | содержимое одного файла — **без имени** |
| `tree` | каталог: имена, права и хеши blob или вложенных tree |
| `commit` | хеш корневого tree, родитель, автор, дата, сообщение |
| `tag` | аннотированный тег: на что указывает, кто и зачем поставил |

## git cat-file: заглянуть в объект

`-t` — тип, `-p` — содержимое в читаемом виде, `-s` — размер. Хватит первых 7 знаков хеша, а
вместо хеша годятся имена: `HEAD`, ветка, тег.

    $ git cat-file -t HEAD
    commit
    $ git cat-file -p HEAD
    tree ee4246c4b461285b5c9efb9da508de0598902244
    author Аня <anya@example.com> 1793747974 +0300
    committer Аня <anya@example.com> 1793747974 +0300

    Грядки и правила

Время — в секундах с 1970 года. У первого коммита нет строки `parent`, у слияния их две.
Дальше по цепочке — дерево:

    $ git cat-file -p ee4246c
    100644 blob e98b5d16e0dbb30f55503aad23ecc22f158f1a70	beds.txt
    040000 tree aa7ff13cbc54c81123f72eca37228a52a01e725e	docs

Права, тип, хеш, имя. `docs` — вложенное дерево:

    $ git cat-file -p aa7ff13
    100644 blob 97d7b9b314e42569a6a3d00aa8c589f7dda7e35b	rules.txt
    $ git cat-file -p 97d7b9b
    Полив по вторникам
    $ git cat-file -s 97d7b9b
    35

Цепочка **commit → tree → tree → blob**. Имя файла хранится в дереве, а не в blob, — поэтому
переименование не копирует содержимое. 35 — байты: кириллица в UTF-8 по два байта на букву.

Сокращения: `HEAD^{tree}` — дерево коммита, `HEAD:путь` — объект по пути в коммите. Всё
дерево сразу показывает `git ls-tree -r HEAD`:

    $ git ls-tree -r HEAD
    100644 blob e98b5d16e0dbb30f55503aad23ecc22f158f1a70	beds.txt
    100644 blob 97d7b9b314e42569a6a3d00aa8c589f7dda7e35b	docs/rules.txt

Аннотированный тег — тоже объект:

    $ git cat-file -p v1
    object 26f9ba9bb1c22d3d4bb549386ca87f04ecead383
    type commit
    tag v1
    tagger Аня <anya@example.com> 1793747983 +0300

    Первый урожай

## Ничьи объекты

`git add` не ждёт коммита: он **сразу** кладёт содержимое файла в склад, а в индекс пишет
только ссылку. Убери файл из индекса — ссылка пропадёт, а объект останется. На него больше
никто не ссылается: ни коммит, ни индекс, ни ветка. Такой объект — **dangling**, «висячий».

`git status` о нём молчит. Найти умеет проверка целостности склада:

    $ git status --short
    $ git fsck
    dangling blob 4e722eed529325a9ffcfee5a1d7b661ae0d5b9d0
    dangling blob f24e48fcb49fb61607d872df2a076002a16fb375

Имени у blob нет — что внутри, смотришь тем же `cat-file`:

    $ git cat-file -t 4e722ee
    blob
    $ git cat-file -p 4e722ee
    редис

`git fsck --lost-found` ещё и сложит копии ничьих объектов в `.git/lost-found/`. А вывод
`cat-file -p` — обычный поток: его можно отправить в файл перенаправлением `>`
([про потоки](/web/wiki/bunnyton/streams)).

Ничьи объекты git удаляет не сразу, а при уборке (`git gc`), и то если им больше двух недель.
Поэтому «я точно делал git add» — почти всегда спасаемо. Ничьими бывают и коммиты — после
`reset` или удаления ветки; их проще находить через [reflog](/web/wiki/bunnyton/git-reflog).

## Сколько всего на складе

    $ git count-objects -v
    count: 7
    size: 28
    in-pack: 0
    packs: 0
    ...

`count` — отдельные файлы объектов. Когда их много, git упаковывает их в pack-файлы
(`in-pack`) — сжимает похожие объекты разницей друг от друга.
