# Поиск по истории и отмена коммита

Главная польза git видна, когда что-то сломалось. Вместо «вчера работало» ты ищешь в истории
коммит, после которого перестало, — и отменяешь только его.

## Хеш — имя коммита

У каждого коммита есть **хеш** — 40 шестнадцатеричных символов. git вычисляет его из
содержимого коммита: файлы, автор, время, сообщение и хеш предыдущего коммита. Поменяй хоть
букву — хеш другой. Поэтому историю нельзя незаметно подделать, а хеш одинаково называет
коммит на любой машине. В командах хватает первых семи символов.

## Читаем список коммитов

Пример — история настроек кафе, три автора:

    $ git log --oneline
    029ffe4 README: меню
    f4902e8 Работаем дольше
    14cfbf0 Обновил настройки
    d6c63f8 Часы работы

Свежие сверху. Свой формат строки — ключом `--format`:

    $ git log --format="%h %an %ad %s" --date=short
    029ffe4 Вера 2026-10-05 README: меню
    f4902e8 Аня 2026-10-05 Работаем дольше
    14cfbf0 Борис 2026-10-05 Обновил настройки
    d6c63f8 Аня 2026-10-05 Часы работы

`%h` — короткий хеш, `%an` — автор, `%ad` — дата, `%s` — сообщение.

## Сужаем поиск

| Что нужно | Как |
|---|---|
| только коммиты, где трогали файл | `git log -- файл` (или просто `git log файл`) |
| коммиты одного автора | `git log --author=Борис` |
| за период | `git log --since=2026-10-01 --until=yesterday` |
| по словам в сообщении | `git log --grep=скидка` |
| последние N | `git log -3` |

    $ git log --oneline hours.conf
    f4902e8 Работаем дольше
    14cfbf0 Обновил настройки
    d6c63f8 Часы работы

## Сообщения врут — изменения нет

«Обновил настройки» не говорит ничего. Правду говорит сам diff. Ключ `-p` (patch) печатает
под каждым коммитом его изменения:

    $ git log -p -1 hours.conf
    commit f4902e819470773ff4802ec90970faf7855fd049
    Author: Аня <anya@example.com>
    Date:   Mon Oct 5 10:20:00 2026 +0300

        Работаем дольше

    diff --git a/hours.conf b/hours.conf
    index 07f2f23..d7a09e9 100644
    --- a/hours.conf
    +++ b/hours.conf
    @@ -1,3 +1,3 @@
     open=09:00
    -close=21:00
    +close=23:00
     tables=15

В длинном выводе ищи прямо в пейджере: `/` и слово, `n` — следующая находка (как в `less`).

Если знаешь, **какая строка** подозрительна, есть «кирка» (pickaxe): `-S текст` оставляет
только коммиты, где число вхождений этого текста изменилось — то есть он появился или исчез.

    $ git log --oneline -S tables=15
    14cfbf0 Обновил настройки

Родственник — `-G регулярка`: коммиты, в diff которых есть строка под шаблон. А если плохой
коммит ищешь не по тексту, а по «работает / не работает», — `git bisect` делит историю
пополам и находит его за несколько шагов.

## Отменить коммит: git revert

Коммиты в общей истории не удаляют: на них уже опираются другие люди. Ошибку исправляют
**новым** коммитом с обратной правкой — `git revert <хеш>`:

    $ git revert --no-edit HEAD~1
    [main a68aa75] Revert "Работаем дольше"
     Date: Mon Oct 5 10:30:00 2026 +0300
     1 file changed, 1 insertion(+), 1 deletion(-)
    $ git log --oneline
    a68aa75 Revert "Работаем дольше"
    029ffe4 README: меню
    f4902e8 Работаем дольше
    14cfbf0 Обновил настройки
    d6c63f8 Часы работы

Отменилась ровно та правка (`close` снова `21:00`); коммит Веры после неё на месте. Без
`--no-edit` git откроет редактор для сообщения. Если после плохого коммита ту же строку
правили ещё раз, revert остановится с конфликтом — разбирают его как при слиянии.

## Типичные грабли

- **Откатить файл целиком** к старой версии — потеряются все правки, сделанные в нём позже.
- **`git reset` на старый коммит** — ветка отъедет назад, и все коммиты после пропадут из
  неё (вернуть можно через [журнал](/web/wiki/bunnyton/git-reflog), но в общей истории так
  не делают).
- revert отменяет коммит, а не «возвращает проект в момент до него».
