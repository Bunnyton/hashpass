# Журнал git: reflog спасает «потерянное»

`git reset --hard` не туда, удалённая ветка, неудачный rebase — и `git log` больше не
показывает нужные коммиты. Паниковать рано: git почти ничего не удаляет сразу. Коммит, на
который не указывает ни одна ветка, ещё недели лежит в репозитории — его просто не видно в
`git log`. Видно его в **журнале**.

## Как теряются коммиты

Пример — песня в git: в `main` три куплета, в ветке `bridge` — бридж. Потом две ошибки:

    $ git reset --hard HEAD~2
    HEAD is now at 56d96c1 Припев
    $ git log --oneline
    56d96c1 Припев
    b75849e Куплет 1
    $ git branch -D bridge
    Deleted branch bridge (was 81eb275).

`git log` показывает историю **от текущего коммита вниз**. Ветка отъехала назад — коммиты
выше неё выпали из вида. Ветку удалили — пропало только **имя**, метка на коммите; сами
коммиты целы. Кстати, `branch -D` сам напечатал, где была ветка: `was 81eb275`.

## git reflog — журнал перемещений HEAD

Каждый раз, когда `HEAD` куда-то двигается — коммит, переключение ветки, reset, merge,
rebase, — git пишет строку в журнал. Свежие сверху:

    $ git reflog
    56d96c1 HEAD@{0}: reset: moving to HEAD~2
    c521ecb HEAD@{1}: commit: Куплет 3
    6e551e7 HEAD@{2}: checkout: moving from bridge to main
    81eb275 HEAD@{3}: commit: Бридж: рифма
    39b3346 HEAD@{4}: commit: Бридж: набросок
    6e551e7 HEAD@{5}: checkout: moving from main to bridge
    6e551e7 HEAD@{6}: commit: Куплет 2
    56d96c1 HEAD@{7}: commit: Припев
    b75849e HEAD@{8}: commit (initial): Куплет 1

Как читать строку:

- **хеш** — коммит, на котором оказался `HEAD` после действия;
- **`HEAD@{N}`** — N шагов назад: `HEAD@{0}` — сейчас, `HEAD@{1}` — до последнего действия;
- после двоеточия — **что** ты сделал.

Журнал — это твой дневник: читай его снизу вверх как историю дня. Ищи запись, где всё ещё
было на месте, — обычно строка прямо **перед** роковой (`reset`, `rebase`). Для ветки ищи,
где ты в ней был в **последний** раз — какая запись стояла перед тем, как ты из неё ушёл.
Ранние коммиты той же ветки — промежуточные, на них не всё.

С датами вместо номеров удобнее вспоминать «вчера вечером»:

    $ git reflog -3 --date=iso
    56d96c1 HEAD@{2026-10-05 11:10:00 +0300}: reset: moving to HEAD~2
    c521ecb HEAD@{2026-10-05 11:00:00 +0300}: commit: Куплет 3
    6e551e7 HEAD@{2026-10-05 10:50:00 +0300}: checkout: moving from bridge to main

Свой журнал есть и у каждой ветки: `git reflog show main` — только перемещения `main`.

## Проверь, прежде чем возвращаться

`HEAD@{N}` и хеш из журнала — такие же имена коммита, как любые другие:

    $ git log --oneline -3 HEAD@{1}
    c521ecb Куплет 3
    6e551e7 Куплет 2
    56d96c1 Припев

Нашёл — возвращайся **теми же командами, что и на любой коммит**: передвинуть ветку
(`git reset`), создать ветку (`git branch`), просто посмотреть (`git switch --detach`).

## Ветка — это просто имя

Удалённую ветку возвращают, повесив метку заново — `git branch` принимает после имени коммит,
с которого начать:

    $ git branch bridge 81eb275
    $ git log --oneline bridge
    81eb275 Бридж: рифма
    39b3346 Бридж: набросок
    6e551e7 Куплет 2
    56d96c1 Припев
    b75849e Куплет 1

Повесишь на промежуточный коммит — получишь ветку без последних правок. Проверяй `git log`
или `git show имя:файл`.

## Что журнал не спасёт

- **Незакоммиченные правки.** Журнал хранит перемещения между коммитами. Правка, которую
  стёр `reset --hard` или `restore` до коммита, пропала навсегда.
- **Чужой репозиторий.** Журнал локальный: на сервер он не уходит, в свежем клоне пуст.
- **Старьё.** По умолчанию записи живут 90 дней, а недостижимые коммиты — около 30; потом
  `git gc` их выбрасывает.

Если журнал уже не помогает, есть последний шанс — висящие коммиты:

    $ git fsck --lost-found
    dangling commit c521ecb85820d0c93f6375fae23109b43a18195b
