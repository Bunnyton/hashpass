# Отмена в git: restore и reset

В git можно отменить почти всё. Но **какой** командой — зависит от того, где сейчас лежит
изменение. Поэтому сначала — карта мест.

## Три места

    рабочий каталог  --git add-->  индекс  --git commit-->  история (HEAD)

1. **Рабочий каталог** — файлы, как ты их видишь и правишь.
2. **Индекс** (staging area) — черновик следующего коммита, то, что уже отложено `git add`.
3. **История** — коммиты. `HEAD` — коммит, на котором ты стоишь.

`git status` показывает первые два места и в скобках **сам подсказывает**, как отменить:

    $ git status
    On branch main
    Changes to be committed:
      (use "git restore --staged <file>..." to unstage)
    	new file:   draft.txt
    	modified:   guide.md

«Changes to be committed» — индекс, «Changes not staged for commit» — файлы.

## Индекс: вынуть файл, не трогая его

Лишний файл попал в индекс вместе с нужным. Вынимаем только его:

    $ git restore --staged draft.txt
    $ git status -s
    M  guide.md
    ?? draft.txt

`guide.md` остался в индексе (`M` в первой колонке), `draft.txt` снова просто лежит в
каталоге. Сам файл не тронут. Старая запись того же — `git reset draft.txt`. А `git reset`
**без имени файла** вынимает из индекса всё сразу — поэтому имя важно.

## История: снять последние коммиты

`git reset <коммит>` переставляет ветку и `HEAD` на указанный коммит. Всё, что было после,
пропадает из истории ветки, а правки этих коммитов попадают туда, куда скажет ключ:

| Ключ | Правки снятых коммитов | Теряется ли что-то |
|---|---|---|
| `--soft` | лежат в **индексе**, готовые к новому коммиту | нет |
| `--mixed` (по умолчанию) | лежат в **файлах**, индекс пуст | нет |
| `--hard` | **стёрты** — и в индексе, и в файлах | да, и незакоммиченное тоже |

Коммиты называют относительно `HEAD` тильдой: `HEAD~1` — на коммит раньше, `HEAD~3` — на три.

    $ git log --oneline
    a83de8a Глава 3
    a145f8c Глава 2
    7d628a5 Начало
    $ git reset --soft HEAD~1
    $ git status -s
    M  guide.md
    ?? draft.txt

Коммит снят, его правка ждёт в индексе (`M` в первой колонке) — можно сразу сделать новый
коммит, например с другим сообщением или вместе с другими правками. То же с `--mixed`:

    $ git reset HEAD~1
    Unstaged changes after reset:
    M	guide.md
    $ git status -s
     M guide.md
    ?? draft.txt

Теперь `M` во второй колонке: правка в файле, индекс пуст. Так из трёх черновых коммитов
делают один аккуратный: сняли, проверили `git diff`, закоммитили заново.

## Рабочий каталог: выбросить правку файла

Неудачную правку в файле, которая ещё не в индексе и не в коммите, возвращают к последнему
коммиту:

    $ git restore app.ini
    $ cat app.ini
    debug=false

Остальные изменённые файлы не тронуты. Старая запись — `git checkout -- app.ini`.

**Эта отмена необратима**: правка не была ни в коммите, ни в индексе, и её не вернёт ни
журнал, ни полка. Сомневаешься — сначала `git stash` или `git diff > на-всякий.patch`.

## Почему не --hard

`git reset --hard` — самый короткий путь «всё как было», и самый опасный: он стирает
незакоммиченные правки во **всех** файлах разом. Им пользуются, когда точно знают, что ничего
нужного нет. Снятые коммиты (не правки!) после него ещё можно найти
[в журнале](/web/wiki/bunnyton/git-reflog):

    $ git reflog -4
    a145f8c HEAD@{0}: reset: moving to HEAD~1
    a83de8a HEAD@{1}: commit: Глава 3
    a145f8c HEAD@{2}: reset: moving to HEAD~1
    a83de8a HEAD@{3}: commit: Глава 3

## Шпаргалка

| Где изменение | Как отменить |
|---|---|
| в файле, не в индексе | `git restore файл` |
| в индексе | `git restore --staged файл` |
| в последних коммитах, ещё не отправленных | `git reset [--soft] HEAD~N` |
| в коммите, который уже на сервере | [`git revert`](/web/wiki/bunnyton/git-log) — новый обратный коммит |

Снимать коммиты `reset`-ом стоит только пока они не ушли на сервер: у напарников они уже есть.
