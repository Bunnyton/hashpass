# Модерация заданий — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** одобрение заданий админом (с авто-одобрением), снимок одобренной версии для студентов,
блок «Отклонённые» с чисткой через 7 дней, удаление своих заданий автором и просмотрщик файлов
задания в hashpass.

**Architecture:** состояние модерации живёт в записи задания `catalog.json`; одобренная версия —
снимок (блоб слоя + `task/`) в `<root>/approved/`; сервер по роли запроса отдаёт студенту снимок,
автору задания и админу — свежую версию. Клиент шлёт токен и при скачивании образа. TUI получает
пометки, клавиши и экран просмотрщика по файлам исходников на пуле.

**Tech Stack:** Python 3.13, Flask/werkzeug (пул), Textual (TUI), pytest (tier1/tier2), ruff.

**Spec:** `docs/superpowers/specs/2026-10-14-модерация-заданий-design.md`

## Global Constraints

- Авто-одобрение: общий флаг пула **или** флаг автора; по умолчанию `false` у всех, включая админа.
- Обновление одобренного задания → снова `pending`; студенты видят прежний снимок.
- Отклонённое удаляется через **7 дней** (`REJECT_TTL = 7 * 24 * 3600`).
- Удалить задание: автор — только свой namespace (`_owner_of(name) == user`), админ — любое.
- Старые записи каталога = одобренные (`state` по умолчанию `approved`, снимок не нужен, пока
  `approved_digest == digest`).
- Клавиши TUI — с русской раскладкой: `a,A,ф,Ф` одобрить; `n,N,т,Т` отклонить;
  `delete,backspace` удалить; `z,Z,я,Я` показать/скрыть «Отклонённые»; `v,V,м,М` просмотрщик.
- Тексты для пользователя — по-русски; идентификаторы — по-английски.

## Review Focus

- Админ одобряет задание, у которого на пуле нет блоба (legacy-запись): одобрение не должно
  падать — снимок из `pack_image` на лету. Тест в Task 2.
- `hashengine catalog layout` после модерации: `state`/`approved_digest`/`reason` сохраняются.
  Тест в Task 1.
- Автор открывает своё обновлённое задание старым клиентом (без токена на образ): получает снимок
  образа + свежий task — расхождение. Принято: старый клиент обновится; новый шлёт токен. Тест
  клиента в Task 4 (заголовок Authorization на GET /image при наличии кэша).
- Удаление задания, которое прямо сейчас качает студент: блоб удаляется через `unlink` после
  того, как сервер открыл файл — GET дочитает. Тест в Task 3 (удаление не трогает открытый fd —
  проверяем, что маршрут удаления использует store-удаление, которое уже `unlink`-безопасно).
- Чистка отклонённых при задании, перезалитом в день чистки: `state != rejected` — не трогать.
  Тест в Task 1.

### Task 0: Исходники задания на пуле — файлами, архив по запросу

Пользователь, 2026-10-14: «давай не архивом, давай все-таки все файлы, но скачать можно архив».

**Files:**
- Create: `src/hashpass/registry/sources.py` (`SourceStore`)
- Modify: `src/hashpass/registry/server.py`, `remote.py`, `cli.py` (`_attach_source`, `cmd_source`)
- Test: `tests/registry/test_sources.py`

**Interfaces — Produces:**
- `SourceStore(root)`: `.put_archive(ref, blob: bytes)` — безопасно распаковывает tar.gz в
  `<root>/<name>/<version>/` (заменяя прежнее дерево атомарно); `.listing(ref) -> list[dict]`
  (`{"path", "size", "dir"}` по порядку); `.read(ref, path) -> bytes` (путь не выходит за корень);
  `.archive(ref) -> bytes` (tar.gz дерева); `.remove(ref)`.
- Маршруты (чтение — автор/админ, запись — владелец namespace/админ):
  `PUT /source/<ref>` (тело tar.gz), `GET /source/<ref>` → `{"files": listing}`,
  `GET /source/<ref>?path=<p>` → байты файла, `GET /source/<ref>?archive=1` → tar.gz.
- Клиент: `RemoteRegistry.push_source(name, version, blob)`, `.source_listing(ref)`,
  `.source_file(ref, path)`, `.source_archive(ref)`; push шлёт `PUT /source`, при 404/405 (старый
  пул) — прежнее вложение `source.tar.gz`; `hashengine source` берёт архив `GET /source/…?archive=1`,
  иначе вложение, иначе Taskfile.
- Веб-карточка: раздел «Исходники» — список файлов со ссылками на просмотр текста
  (`/web/images/source?ref=&path=`) и «скачать архив».

- [ ] Steps: тесты (распаковка/листинг/чтение/архив; выход за корень → ValueError; маршруты по
  ролям; клиент с фолбэком) → FAIL → реализация → PASS → commit.

**Interfaces — Produces:**
- `CatalogEntry`: новые поля `state: str = "approved"`, `approved_digest: str = ""`,
  `reason: str = ""`, `rejected_at: float = 0.0`; `as_dict()` их отдаёт; `available` =
  `has_approved and block_open and not hidden`, где `has_approved = bool(approved_digest)`.
- `Catalog.add_task(ref, digest, *, block_id=None, block_name=None, hidden=True, auto=False)`:
  новая запись → `pending` (или `approved` с `approved_digest=digest`, если `auto`); существующая
  → `pending` (или `approved`, если `auto`), `reason/rejected_at` сброшены, `approved_digest`
  сохранён.
- `Catalog.approve(ref) -> str | None` (вернёт digest, ставший одобренным; None — нет такого).
- `Catalog.reject(ref, reason, now) -> bool`.
- `Catalog.purge_rejected(now, ttl=REJECT_TTL) -> list[str]` (удалённые refs, только `rejected`).
- `set_layout` сохраняет все поля задания.
- `PoolSettings(path)`: `.auto_approve -> bool`, `.set_auto_approve(on: bool)`.
- `UserStore.auto_approve(user) -> bool`, `.set_auto_approve(user, on)`.

### Task 3: Маршруты пула

**Files:**
- Modify: `src/hashpass/registry/server.py`
- Test: `tests/registry/test_moderation_routes.py`

**Interfaces — Consumes:** Task 1, Task 2. **Produces:**
- `PUT /task/<ref>?publish=1` → `catalog.add_task(..., auto=pool.auto_approve or
  users.auto_approve(owner))`; при `auto` — `approved.take`.
- `POST /catalog/approve {ref}` (admin) → снимок + `catalog.approve`.
- `POST /catalog/reject {ref, reason}` (admin).
- `DELETE /task/<ref>` (владелец namespace или admin): образ (`store.remove`), снимок, вложения,
  запись каталога.
- `GET /pool/settings`, `PUT /pool/settings {auto_approve}` (admin);
  `PUT /users/<user>/auto-approve {on}` (admin).
- `GET /catalog`: студент — только `available`; автор — одобренные (+preview) и **свои** любые;
  админ — все. Отклонённые: автору свои, админу все; в строке `state, reason, rejected_at,
  expires_at, owner, pending_update`.
- `GET /image/<ref>`, `HEAD /image/<ref>`, `GET /task/<ref>`: «свежая» версия — если запрос от
  владельца или админа; иначе — снимок (если есть), иначе текущая при `state == approved`,
  иначе для `task` — 404.
- `purge_rejected` — при `make_server` и раз в час (поток в `cmd_serve` или таймер сервера).

- [ ] Step 1: tier2-тесты на живом сервере (фикстура `registry`): роли 401/403/200 у каждого
  маршрута; студент не видит pending; после approve видит; после обновления видит прежний digest
  в `HEAD /image` и прежний task; автор видит свежий; reject → в каталоге автора с причиной;
  DELETE своего 200, чужого 403; авто-одобрение по пулу и по автору.
- [ ] Step 2: FAIL. Step 3: реализация. Step 4: PASS + `pytest tests/registry`. Step 5: commit.
