# 1б+1в. Пользователи, курсы, роли и права — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans. Steps use `- [ ]`.

**Goal:** курсы (владелец, видимость, участники с ролями, заявки, приглашения, автообновление,
предложения) поверх реестра ревизий; права проверяются на всех маршрутах; пользователи — роли
`user`/`admin`, группы → комментарий, поиск только админу, зарезервированные логины.

**Architecture:** курс = метаданные `courses/<id>/course.json` + **свой `Catalog`**
(`courses/<id>/catalog.json`) — нынешний класс раскладки и модерации переиспользуется как есть:
`pending` без одобрения = предложение «добавить», `pending` поверх одобренной = «обновить»,
`approved` = ревизия курса (по `approved_digest`/`approved_image`), `rejected` + причина + 7 дней.
Автообновление = автоодобрение новой ревизии, если задание не закреплено. Курс по умолчанию
(`default_course` в `ServerConfig`) — его каталог = прежний `catalog.json` (переезд прода = запись
метаданных, §1г). Старые маршруты `/catalog*` и веб-редактор работают над курсом по умолчанию.

**Spec:** `docs/superpowers/specs/2026-10-21-курсы-и-рабочий-tui-design.md` §3–§9, §12, §13.

## Global Constraints

- Роли курса: `member` < `author` < `maintainer` < `owner`; админ сервера — всё.
- Видимость курса `public|private`; приватный — только участники; посторонний видит название,
  описание и «запросить доступ»; в поиске приватных нет.
- Приватный образ — только в приватный курс; публичный образ не на приватном родителе/базе.
- Зачёт — только из курса (`/submit` с `course`; без него — курс по умолчанию).
- Прогресс по `repo:tag`; попытки и прогресс пишут `course`.
- Искать пользователей — только админ. Логин удалённого пользователя зарезервирован.
- Тексты для людей — по-русски. Прод не трогаем.

## Review Focus

1. Студент не получает ревизию задания, которого нет ни в одном видимом ему курсе (`/task`, `/image`, `/closure`, `/submit`).
2. Приватный курс не протекает: ни через `/courses`, ни через `/images` (приватный образ), ни через `/progress`/`/solution`.
3. Повторная отправка задания, стоящего в двух курсах: в курсе с автообновлением — сразу новая ревизия, в закреплённом/без автообновления — предложение «обновить», студенты держат прежнюю.
4. Старый клиент (`/catalog` без курса, `/submit` без курса) работает как раньше на курсе по умолчанию.
5. Удаление ревизии, стоящей в чужом курсе — запрос админу; одобрение → задание убрано из курса + предложение `restore` на меньшую.

### Task 1: Пользователи (1б)

**Files:** `registry/passwords.py`, `registry/server.py`, `registry/web.py` (+шаблоны пользователей), tests `tests/registry/test_users_model.py`.
- `ROLES` → `("user", "admin")`; `role()` читает `student`/`author` как `user` (прежние записи
  не переписываются; поле `legacy_role` для миграции 1г). `/admin/role` принимает `user|admin`
  (и старые значения → `user`).
- `group` → при `add()` и в `/register` дописывается в начало `comment` (`"ИТ-21 · <comment>"`);
  `set_group` остаётся для старого веба (то же поведение). Фильтр дашборда — по подстроке
  комментария.
- `GET /users/search?q=` — только админ: `[{user, comment, role, created_at}]` (логин или
  комментарий содержат `q`, без регистра).
- Удаление пользователя (`/web/users/delete`, `delete-group`): логин → `reserved.json`
  (регистрация такого логина — 409 «логин занят»); снимаются членства/заявки/предложения во всех
  курсах; если у пользователя есть курсы — отказ «сначала удалите курсы».
- Права `_AUTHOR_ROLES` для API записи образов → «любой вошедший» (`push` в свой namespace,
  спека §3); веб-страницы автора — пока `author|admin|владелец/персонал хоть одного курса`.
- Tests: legacy-роли читаются как `user`; группа в комментарии; поиск 403 не-админу; удалённый
  логин не регистрируется; push обычным пользователем в свой namespace — 201.

### Task 2: Модель курса `registry/courses.py`

**Interfaces — Produces:**
```python
ROLE_ORDER = ("member", "author", "maintainer", "owner")
@dataclass
class CourseMeta:
    id: str; owner: str; name: str; title: str; description: str
    visibility: str            # public|private
    auto_accept: bool          # False
    auto_update: bool          # True
    invite: str                # token
    members: dict[str, str]    # user -> role (owner implicit)
    requests: list[dict]       # {user, comment, state, at, decided_by, decided_at}
    pinned: list[str]          # "repo:tag" pinned to their approved revision
    proposals_meta: dict[str, dict]   # "repo:tag" -> {by, comment, kind, at} (who proposed what)
    created_at: str; rev: int
class CourseStore:             # root = <store>/courses
    def __init__(self, root: Path, *, legacy_catalog: Path | None, default_ref: str) -> None
    def create(self, owner, name, title, *, visibility="public", description="") -> CourseMeta
    def get(self, ref: str) -> CourseMeta | None            # "owner/name"
    def by_id(self, cid: str) -> CourseMeta | None
    def all(self) -> list[CourseMeta]
    def catalog(self, meta: CourseMeta) -> Catalog          # the default course -> legacy catalog.json
    @contextmanager
    def edit(self, ref: str, expect_rev: int | None = None) -> Iterator[CourseMeta]  # flock; rev+1; 409 on mismatch
    def delete(self, ref: str) -> None
    def courses_with(self, ref_tag: str) -> list[CourseMeta]
    def role(self, meta: CourseMeta, user: str | None) -> str | None   # owner/maintainer/author/member/None
```
- Default course: `ServerConfig.default_course` (`""` → курса нет: старый каталог живёт как раньше
  без метаданных, все маршруты ведут себя как сейчас; миграция 1г его заводит).
- Tests: create/get/edit rev conflict; имя `[a-z0-9-]`, уникально у владельца; роли; default
  course catalog = legacy path.

### Task 4: Маршруты курсов (JSON API)

`/courses` GET (видимые + `?q=`), POST (создать). `/courses/<o>/<n>`: GET (вид для вызывающего:
блоки/задания со служебными полями для персонала, только открытое/одобренное для студента;
постороннему private — `{title, description, access: "request"|"requested"}`), PUT (настройки:
title, description, visibility с проверками §2.5, auto_accept, auto_update, `rotate_invite`).
`/courses/<o>/<n>/join` POST (`{invite?}`: public → «приступил»; private + верный invite →
участник). `/requests` POST (заявка, одна открытая, пауза сутки после отказа), `/requests/<user>`
POST `{accept|reject}`. `/members/<user>` PUT `{role}` / DELETE (owner). `/tasks` POST
`{repo, tag, n?, block_id}` (author+ → `add_task(auto=True)`; иначе предложение: `add_task(auto=False)`
+ `proposals_meta`; `auto_accept` → сразу). `/tasks/<repo:tag>` PUT `{hidden?, pinned?, approve?,
reject?, reason?, block_id?}` / DELETE (maintainer; автор — своё). `/blocks` POST/PUT/DELETE,
`/layout` PUT (maintainer). Предложения: строки каталога курса со `state` и `proposals_meta`.
- Видимость образов: `repo.visibility == private` → добавить можно только в private курс; смена
  видимости курса/образа с конфликтом — 409 со списком.
- Tests: каждый маршрут × роль (разрешено/403/404), предложение → принять → студент видит.

### Task 5: Ревизии курса, автообновление, раздача по курсу

- `_catalog_on_commit` → для каждого курса с этим тегом: `auto = meta.auto_update and ref not in
  meta.pinned` → `catalog.add_task(..., auto=auto)` (иначе — `pending` = предложение «обновить»).
  Старый `publish`/`--block` — только в курс по умолчанию (как сейчас).
- `_view_revision(user, name, version, course=None)`: автор/админ — что просят; иначе ревизия,
  одобренная в курсе `course_for(...)` (параметр `?course=o/n` у `/closure`, `/image`, `/task`;
  без него — первый видимый курс с этим тегом); тега нет ни в одном видимом курсе — 404.
  Приватный репозиторий: только владелец/админ/участники приватного курса с этой ревизией.
  Базовые образы (не задание, не приватные) — всем вошедшим и анонимам, как сейчас.
- `/submit`, `/attempt`: `course` в теле (нет → курс по умолчанию); проверка `can(play)` и
  наличия тега в курсе; запись прогресса/попытки получает `course`.
- `/progress`: студент — своё; персонал курса — студенты, приступившие к его курсам, только по
  тегам этих курсов; админ — всё. `/solution/<ref>?user=` — тем же правилом.
- `enrollments/<user>.json`: `join`, первая попытка/зачёт в курсе.
- Tests: Review Focus 1–3; двойной курс (auto vs pinned); прогресс персонала ограничен.

### Task 6: Удаление ревизии из чужого курса — запрос админу

- `DELETE /revisions/...`: если ревизия — одобренная в чужом курсе (не владельца репозитория) →
  202 `{"request": id}`, запись в `deletion-requests.json`; `DELETE /deletion-requests/<id>` —
  отзыв (владелец); `POST /deletion-requests/<id>` `{approve}` — админ. Одобрение: удалить
  ревизию; в каждом курсе, где она одобрена, — `remove_task` + предложение `restore` на
  предыдущую оставшуюся ревизию (`add_task(auto=False)` с её дайджестом, `proposals_meta.kind=restore`).
- Tests: Review Focus 5; свои курсы — удаляется сразу; отзыв.

### Task 7: Старые маршруты и клиенты на курсе по умолчанию

- `/catalog*`, `/web/catalog*`, `/web/blocks/*`, `/catalog/approve|reject` — над каталогом курса по
  умолчанию с проверкой `can(moderate|add)` вместо глобальных ролей.
- `hashengine catalog layout` — старый вызов: «раскладка курсов — в вебе: <ссылка>», 410.
- Весь tier1/tier2 зелёный; тесты старых маршрутов не меняют ожиданий там, где поведение то же.
