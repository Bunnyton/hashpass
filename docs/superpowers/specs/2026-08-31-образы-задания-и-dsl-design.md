# Образы, задания и DSL — дизайн

## 0. Цель и границы

**Цель.** Первоклассный авторинг:
1. **образов** — переиспользуемых окружений, наследуемых и композируемых (как в Docker);
2. **заданий** — слой поверх образа с эталонным решением, приёмом, ассетами и интерактивом;
3. **скрытого системного слоя** — невидимого студенту рабочего пространства (грейдеры/хуки/машинерия);
4. **интерактивной системы** — «система общается со студентом»: живой печатающий вывод, много
   подсказок по явным условиям, кастомные обработчики.

**Всего два действия** (никаких «режимов»):
- **`build`** — собрать образ (или задание = образ с логикой) из рецепта в слой.
- **`run`** — запустить контейнер из образа/задания. **Есть `stage` → задание** (полный цикл:
  проверка/прогресс/интерактив). **Нет `stage` → чистый образ** (просто среда, без проверки).

**Переиспользуем** (готово, планы 1–G на `main`): оверлей (`overlay.py`, `NspawnRunner.prepare(lowers)`),
`image.base.build_base`, деривация/бандл/приём (`taskcode/*`), ключи/evidence/сервер (`key`, `evidence`,
`server/verify`, `grade`), рантайм-цикл (`play.PlaySession`, `progress`, `hints`, `sync`), хуки и разбор
команд (`hooks.HookRegistry`, `cmd.Cmd`).

**Новое** (эта спека): формат рецептов + парсер, `build`, резолвер `FROM`-DAG → `lowers`, локальное
хранилище образов, скрытый системный слой в приватном namespace, контракт обработчиков, слой интерактива
(voice/условные подсказки/печатающий вывод) поверх `HookRegistry`.

**Вне рамок:** реестр push/pull (фаза 4); массовый авторинг 24 заданий (content-ops по плейбуку).

## 1. Концепции

- **Слой (layer)** — дельта ФС (overlay upperdir) из рецепта.
- **Образ (image)** — именованный версионированный слой-окружение.
- **Задание (task)** — образ с блоками `stage` (логика приёма/интерактива).
- **Скрытый системный слой** — стоячее рабочее пространство ядра, невидимое студенту (§4).

Единый формат: **`Imagefile` = `Taskfile`, один язык**; есть `stage` → задание, нет → образ.

## 2. Модель образов и слоёв

### 2.1 Самоимя и ссылка
- Рецепт **сам себя именует**: `image <name>:<ver>` (прямо в конфиге, не флаг сборки).
- `from <name>:<ver>[, …]` — **транзитивно и неявно**: `from nettools:1` тянет и всё, из чего собран
  `nettools` (его замыкание); предков перечислять не нужно. Push/pull по имени — реестр (фаза 4).

### 2.2 Семантика наследования (как Docker)
- **ФС КОПИТСЯ** вниз по цепочке (все `copy`/`run` в оверлей). Мульти-`from`: **порядок = приоритет**
  (правее = выше, побеждает при конфликте путей); на `build` — предупреждение о конфликте путей.
- **Логика ПОДМЕНЯЕТСЯ** (аналог `CMD`): `stage`/`voice`/интерактив берутся от верхнего слоя; ребёнок
  объявил свои — замещают родительские.
- **`run` запекается** в слой (среда, всегда у студента). **`solve` НЕ запекается** — эталон для
  деривации, решает студент. Стартовую наработку ребёнка кладут в `run`, не в `solve`.

### 2.3 Резолвер `FROM`-DAG → `lowers`
Разворачивает граф в **детерминированный упорядоченный дедуплицированный** список нижних слоёв
(топосортировка + порядок объявления как тай-брейк; общий предок — один, снизу). Результат — `lowers:
list[Path]` → `NspawnRunner.prepare(lowers)`.

### 2.4 `build`
1. Резолвер: `from` → упорядоченный `lowers`. 2. Смонтировать цепочку. 3. Выполнить `run`-шаги.
4. **upperdir = новый слой** → в хранилище под `image name:ver`. `solve`/интерактив на `build` не
исполняются (метаданные задания).

### 2.5 Хранилище
Локально `images/<name>/<ver>/layer/` + метаданные (`from`, чек-суммы). Реестр (фаза 4) — тот же формат.

## 3. DSL — синтаксис

**Строчный, с отступами** (блоки — по отступу). Англ. ключевые слова; содержимое реплик — любое.

### 3.0 Принцип: действия ЯВНЫЕ (очевидно с первого прочтения)
Никаких догадок «файл это или команда». Действие всегда `<verb> <kind> <value>`:

| действие | смысл |
|---|---|
| `say "текст"` | показать текст (печатающий вывод) |
| `show file <путь>` | показать файл (арт; большой → пейджер) |
| `exec <файл-или-команда>` | выполнить: если первый токен — **скрипт задания** (файл в `hidden`/скриптах или существующий путь) → выполнить **файл** (по shebang; остаток строки = аргументы); иначе → **shell-команда**. Результат — контракт §6 |

Т.е. `exec verify.sh` — «выполнить скрипт verify.sh» (авто-детект: файл, раз он есть у задания), а
`exec grep -q ERROR errors.txt` — «выполнить команду». Явного `file`/`cmd` не пишем — и так очевидно.
Значение директивы — либо **инлайн-литерал** (`"…"`), либо действие (`exec …`/`say`/`show file`).
Расширяемость: новый verb/событие — **аддитивная** правка парсера+модели, синтаксис остального не меняется.

### 3.1 Структура
```
image  log-archive:1
from   base, coreutils-lab
readme readme.txt                          # файл теории (или: readme exec make_readme.sh)
copy   assets/  /home/student/             # src dst — в слой (запекается)
run    mkdir -p /var/log/app               # build-time env (запекается)
hidden .work  grade/                       # <точка-монтирования> <источник> — скрытый слой (§4)
```

### 3.2 Блок `stage`
```
stage "Собери строки ERROR из /var/log/app в errors.txt"
  solve    grep -rh ERROR /var/log/app > errors.txt   # эталон (или: solve exec ref.sh)
  observe  errors.txt                                  # что сравнивать (файл/каталог/stdout)
  exclude  .cache *.log                                # шум выкинуть (для каталогов)
  neutral  ls cd cat pwd less head tail                # «осмотр» — НЕ считается попыткой
  on enter exec seed.sh                           # действие на входе
  on pass  say  "Первый пошёл 👊"
  on pass  show file art/ok1.txt
  hint  tries 5              say "Загляни в /var/log/app 👀"    # УСЛОВИЕ + действие
  hint  cmd grep missing -i  say "Добавь -i 🆘"
  hint  idle 90              exec idle.sh                  # текст динамически из файла
  check exec verify.sh                                    # приём кодом (exit 0 = принято)
```

- **`solve`** — эталон (для деривации), НЕ обязательная последовательность. Многокомандный — **блок**
  (`solve:` с отступом), команды в одном шелле (cwd/env живут внутри этапа). `<output>` = stdout
  **последней** команды.
- **`observe`** — какие пути сравнивать (файл, каталог, `stdout`). Каталог можно (рекурсивно), но лучше
  узкий путь + `exclude` (широкий `/home` тянет мусор; волатильное само обрежется §5, но сигнал
  размывается).
- **`check exec`** — escape для невыразимого/недетерминированного (напр. `.tar.gz` недетерминирован
  → сверять список `tar tzf | sort`). `exit 0` = принято.
- Гранулярность: многокомандный `solve` = один чекпоинт; несколько `stage` = проверять шаги отдельно.

### 3.3 На чём стоит приём
`solve` + `observe` → дифф-канонизация (§5 арх., план C/D) → толерантный инвариант (size-adaptive
Jaccard/MinHash; точный хэш — частный случай). **Требование:** наблюдаемый набор детерминирован (вывод в
файл; без времени/PID/случайности) — иначе `derive` бросит `vacuous canonical`. Приём — по **результату**,
не по совпадению команд.

## 4. Скрытый системный / рабочий слой

Стоячий слой ядра, несущий **машинерию** (инструментированная оболочка, чекер, движок хуков, канонайзер)
и **авторские скрипты/ассеты** (грейдеры, seed/verify, арт).

### 4.1 Чистые пути (не тянем старьё)
Прежние `/.hash/.cmd*`, `/.hash/dvs/`, `/.hash/.task/` — **отменяются**. Машинерия и состояние живут в
**скрытом слое** (приватный ns), видимую ФС студента НЕ засоряем. Схема (в приватном ns ядра):
```
/hp/bin/          # оболочка, чекер, хуки
/hp/task/         # приёмный бандл (checks и т.п.)
/hp/work/         # авторский скрытый слой (грейдеры/seed/verify/арт) — это твой `hidden`
/hp/state.json    # сессия (rw): попытки, показанные подсказки, «настроение»
```
В видимой среде студента остаётся лишь сама оболочка (его shell) в `PATH`; всё, что она читает/пишет —
в `/hp/*` скрытого слоя, которого в namespace студента нет.

### 4.2 Невидимость — через namespace, не через тайминг
Гарантия держится **изоляцией mount-namespace**, НЕ гонкой mount/unmount по времени (её ловит фоновый
`inotify`/поллер). Ядро гоняет команды по одной: команда студента → `nspawn` **без** `/hp`; проверка/хук →
**отдельный** запуск (свежий mount-ns) **с** `/hp`. Постоянной сессии студента для поллинга нет; в его ns
`/hp` **не существует by construction** — ни `ls`, ни фон, ни `inotify` не видят.

### 4.3 Root в контейнере
Namespace — про **видимость**, не про права: root в ns студента видит лишь свои монтирования; приватный ns
ядра ему не виден без `setns` (нужен fd + CAP в целевом user-ns), а pid-ns контейнера чужих процессов не
показывает → **легитимный root ничего не видит**. Оговорка: `nspawn` без `--private-users` — не жёсткая
граница против *враждебного* root в побеге; но модель это **не ломает** (гарантия — сервер, §5). Хотим
закрыть и враждебного root → образ с **`--private-users`** + seccomp. По умолчанию — как есть; «злые»/CTF —
с userns.

### 4.4 Оверхед
На команду — доп. изолированный запуск проверки/хука с `/hp`: старт nspawn (~0.1–0.3 с) + возможный mount.
Для интерактива незаметно. Смягчение: держать базовую цепочку **тёплой**, лишь добавлять/снимать
`/hp`-lower (или входить в готовый ns), а не пересобирать всё.

## 5. Безопасность / threat model

- **Гарантия — на сервере (§9 арх.):** глобальный ключ `HMAC(server_secret, student_id ‖ task_id)`, сервер
  **ре-верифицирует evidence** (план E); секрет только на сервере.
- **Локальное скрытие — анти-казуальный-чит и UX, НЕ гарантия.** Увидев локальный грейдер, ключ подделать
  нельзя.
- **Локальный ключ** — nonce (провизорный прогресс). **Интерактив/подсказки/условия — advisory**, приём не
  решают.
- `--private-users` — опция уровня образа для твёрдой локальной изоляции.

## 6. Обработчики — контракт делегирования

`exec <файл-или-команда>` — если первый токен это скрипт задания (существующий файл в `hidden`/скриптах),
выполняется **файл** (по shebang, остаток строки = аргументы); иначе — **shell-команда**. Явного `file`/`cmd` не пишем.

**Вход:**
| канал | что |
|---|---|
| `argv[1]` | текущая команда студента (сырая строка) |
| env `HP_TRIES` | реальные попытки на этапе (без `neutral`) |
| env `HP_LAST_OUT` | вывод последней команды |
| env `HP_HISTORY` | путь к файлу истории |
| env `HP_STATE` | путь к JSON сессии (**rw** → память между вызовами; это `/hp/state.json`) |
| env `HP_ROOTFS` | путь к ФС студента |
| env `HP_STAGE` | текущий этап |
| env `HP_ARG_*` | именованные параметры из DSL (`exec f.sh expected="a b"` → `HP_ARG_expected`) |

**Выход** (смысл — по директиве):
| директива | ответ |
|---|---|
| `hint`/`say`/`voice`/`readme` | **stdout** = текст показать |
| `check`/`condition`/`require` | **exit**: `0` = принято/разрешено |
| `solve` | **stdout** = команды эталона (или сам файл = скрипт-решение) |
| `on enter/pass`/`react`/`seed` | сайд-эффекты; `stdout` (если есть) — показать |

Потолка нет: состояние в `HP_STATE`, любой язык, полный контекст. Файлы — в скрытом слое (`/hp/work`).
```sh
#!/bin/sh
cmd="$1"                                   # команда студента
case "$cmd" in
  grep*) [ "${HP_TRIES:-0}" -ge 3 ] && echo "Ты близко — добавь -r 🔁" ;;
esac
```

## 7. Интерактив — «система общается»

Слой **событие → обработчик** поверх `HookRegistry` (план 2). События: `command(cmd,out)`,
`enter/pass(stage)`, `idle`, `output-match`. Директивы `voice`/`hint`/`say`/`show`/`react` — сахар,
регистрирующий обработчики; сложное — `exec` с полным контекстом (§6). (`on fail` пока не нужен;
если понадобится — аддитивно добавим событие, §3.0.)

### 7.1 Явные условия подсказок (голого `stuck` нет)
`hint <условие> <действие>`, условие — явный атом:
- `tries N` — после **N реальных попыток** на этапе (команды **без `neutral`**: `ls`/`cd`/… не считаются);
- `idle N` — после N секунд без прогресса;
- `cmd <база> [has <флаги>] [missing <флаги>]` — студент запустил `<база>` с/без флагов (над `cmd.Cmd`);
- `output "<подстрока>"` — вывод содержал подстроку.
Один атом на строку; комбинации → `hint <атом> exec f.sh` (файл до-проверяет) либо `react on command
exec f.sh` (файл решает всё). `neutral <список>` задаёт, что не считается попыткой (тот же список
кормит и шум дифф-канонизации §5).

### 7.2 Живой печатающий вывод (динамический voice)
Всё общение система→студент рендерится **печатающей машинкой** — символы/строки появляются последовательно
на читаемой скорости (как субтитры/чат в фильмах), с микро-паузами на пунктуации. Свойство рантайм-рендера.
**Настраиваемо, с режимами:**
```
settings
  type-mode  normal          # по умолчанию
  # режимы:  instant  — мгновенно (для длинных выводов КОМАНД студента — их не «печатаем»)
  #          normal   — читаемая скорость (реплики системы)
  #          dramatic — медленно, с паузами (важные/сюжетные реплики)
  type-speed 45              # символов/сек для normal (настраивается)
  pager on                   # show file большого размера → пейджер

voice
  hello  say "Йо! Сегодня приручаем логи 🧑‍💻"          # инлайн …
  hello  exec greet.sh                              # … или динамически (per-student)
  bye    say "Красава 🎉"
```
Вывод команд студента — `instant` (не печатаем построчно). Реплики системы — `normal`; отдельные — можно
пометить `dramatic` (напр. `say dramatic "…"`). `show file` большого — через пейджер.

или смешивать с `exec`.

## 9. Фазы реализации

1. **Образы:** формат рецепта + парсер, `build` (mount замыкания → `run` → upperdir=слой), резолвер
   `FROM`-DAG, локальное хранилище, самоимя/версии, мульти-`from` + конфликты. `run` образа без задания —
   чистая среда.
2. **Задание-на-образе:** блоки `stage`/`solve`/`observe`/`check`, деривация на смонтированной цепочке
   (переиспользуем `taskcode`), скрытый слой `/hp` + `on enter/pass` + контракт `HP_*`, чистые пути.
3. **Интерактив:** события поверх `HookRegistry`; условные `hint` (`tries`/`idle`/`cmd`/`output`,
   `neutral`); `say`/`show file`/`exec`; **печатающий рендер** (`settings.type-mode/type-speed`,
   пейджер); `voice`; `react`.
4. **Реестр:** push/pull образов по имени (§8 арх.), аутентификация записи.
5. **Миграция контента:** 24 задания по плейбуку, в первую очередь контейнерные/сетевые.

## 10. Зафиксированные решения
- Ключевые слова — **англ.** · блоки — **отступами** · делегирование — **`exec`** с явным `file`/`cmd`.
- Действия читаемы: `say`/`show file`/`exec …` — где `exec` авто-детектит (скрипт задания → файл; иначе команда), без явного `file`/`cmd`.
- Печать — режимы `instant`/`normal`/`dramatic` + `type-speed` + пейджер для `show file`.
- **Без режимов** `taskcreator`/`taskchecker` — только `build` (образ) и `run` (контейнер; нет `stage` →
  чистый образ). Синтаксис расширяемый: новое событие/verb — аддитивно.
