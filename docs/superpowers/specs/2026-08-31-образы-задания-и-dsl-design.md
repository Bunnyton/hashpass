# Образы, задания и DSL — дизайн

## 0. Цель и границы

**Цель.** Дать первоклассный авторинг:
1. **образов** — переиспользуемых окружений, наследуемых и композируемых (как в Docker);
2. **заданий** — слой поверх образа с эталонным решением, приёмом, ассетами и интерактивом;
3. **скрытого системного слоя** — невидимого студенту рабочего пространства для грейдеров/хуков;
4. **интерактивной системы** — «система общается со студентом»: живой печатающий вывод, много
   подсказок по явным условиям, кастомные обработчики-файлы.

**Переиспользуем** (готово в планах 1–G, на `main`): оверлей-механику (`overlay.py`,
`NspawnRunner.prepare(lowers)`), сборку базы (`image.base.build_base`), деривацию/бандл/приём
(`taskcode/*`), ключи/evidence/сервер (`key`, `evidence`, `server/verify`, `grade`), рантайм-цикл
(`play.PlaySession`, `progress`, `hints`, `sync`), движок хуков и разбор команд (`hooks.HookRegistry`,
`cmd.Cmd`).

**Новое** (эта спека): формат рецептов (парсер), исполнитель `build`, резолвер `FROM`-DAG →
`lowers`, локальное хранилище образов (+ реестр позже), скрытый системный слой в приватном
namespace, контракт обработчиков-файлов, слой интерактива (voice/условные подсказки/печатающий
вывод) поверх `HookRegistry`.

**Вне рамок этой спеки:** реестр push/pull (фаза 4, §8 арх.), массовый авторинг 24 заданий
(content-ops по плейбуку).

## 1. Концепции

- **Слой (layer)** — дельта ФС (overlay upperdir), собранная из рецепта.
- **Образ (image)** — именованный, версионированный слой-окружение (без логики задания).
- **Задание (task)** — слой с **логикой** (этапы/приём/интерактив) поверх выбранного образа.
- **Режим (mode)** — свойство композиции слоёв (`taskcreator`/`taskchecker`/`play`), §2 арх.
- **Скрытый системный слой** — стоячее рабочее пространство ядра, невидимое студенту (§4).

Единый формат: **`Imagefile` и `Taskfile` — один язык**; разница только в наличии блоков `stage`
(есть `stage` → это задание; нет → образ).

## 2. Модель образов и слоёв

### 2.1 Самоименование и ссылка
- Рецепт **сам себя именует**: `image <name>:<ver>` (не флаг сборки — прямо в конфиге).
- Ссылка — `from <name>:<ver>[, <name>:<ver> …]`. **Транзитивно и неявно**: `from nettools:1`
  подтягивает и всё, из чего собран `nettools` (его замыкание), перечислять предков не нужно.
- Push/pull по имени — реестр (фаза 4).

### 2.2 Семантика наследования (крадём у Docker)
- **Файловая система КОПИТСЯ** вниз по всей цепочке (все `copy`/`run` складываются в оверлей).
  При **мульти-`from`** порядок в списке = **приоритет**: правее = выше в оверлее, **побеждает при
  конфликте путей**. На `build` — предупреждение, если два образа кладут один и тот же путь.
- **Логика задания ПОДМЕНЯЕТСЯ** (аналог `CMD`): блоки `stage`/`voice`/интерактив **берутся от
  верхнего слоя**; ребёнок объявил свои — они замещают родительские (не складываются). Обычно
  композируют простые образы (логики нет), логику задают локально.
- **`run` запекается** в слой (env, всегда есть у студента). **`solve` НЕ запекается** — это эталон
  для деривации, решает студент. Наработку, которая должна быть в стартовой среде ребёнка, кладут в
  `run`, а не в `solve`.

### 2.3 Резолвер `FROM`-DAG → `lowers`
`from` образует граф именованных слоёв. **Резолвер** разворачивает его в **детерминированный
упорядоченный список нижних слоёв**: топологическая сортировка + порядок объявления как тай-брейк,
**дедуп общих предков** (если два образа тянут `base`, он один, снизу). Результат — `lowers:
list[Path]` → прямо в `NspawnRunner.prepare(lowers)`.

### 2.4 Модель `build`
`build <recipe>`:
1. Резолвер: `from` → упорядоченный `lowers` (замыкание).
2. Смонтировать цепочку (оверлей, как `prepare`).
3. Выполнить `run`-шаги в этой среде (через раннер).
4. **upperdir (дельта ФС) = новый слой** → в хранилище под `image name:ver`.
`solve`/интерактив на `build` НЕ исполняются — это метаданные задания (деривируются/грузятся отдельно).

### 2.5 Хранилище
Локально: `images/<name>/<ver>/layer/` + метаданные (`from`, чек-суммы). Реестр (фаза 4) — тот же
формат по сети.

## 3. DSL задания/образа

Синтаксис: **строчный, с отступами** (блоки — по отступу). Значение директивы — либо
**инлайн** (`"строка"` или голые токены-команда), либо **делегирование в файл** через `exec <путь>`
(**без стрелок**). Файлы-обработчики лежат в скрытом слое (§4), см. контракт §6.

### 3.1 Директивы-структура
```
image  log-archive:1                     # самоимя
from   base, coreutils-lab               # наследование (транзитивный DAG; ФС копится, порядок=приоритет)
readme readme.txt                        # теория (файл) | readme exec make_readme.sh (динамически)
copy   assets/  /home/student/           # src dst — в слой (запекается)
run    mkdir -p /var/log/app             # build-time env (запекается)
hidden .work  grade/                     # <точка-монтирования> <источник> — скрытый слой (§4)
```

### 3.2 Блок `stage`
```
stage "Собери строки ERROR из /var/log/app в errors.txt"
  solve    grep -rh ERROR /var/log/app > errors.txt   # эталон | solve exec ref.sh
  observe  errors.txt                                  # что сравнивать (файл/каталог/stdout)
  exclude  .cache *.log                                # шум выкинуть (для каталогов)
  neutral  ls cd cat pwd less head tail                # «осмотр» — НЕ считается попыткой
  on enter exec seed.sh                                # действие на входе (copy→run→remove в приватном ns)
  on pass  say "Первый пошёл 👊"
  on pass  show art/ok1.txt
  hint  tries 5              "Загляни в /var/log/app 👀"   # УСЛОВИЕ + текст (инлайн)
  hint  cmd grep missing -i  "Добавь -i 🆘"
  hint  idle 90              exec idle.sh                  # текст динамически из файла
  check exec verify.sh                                     # приём кодом (exit 0 = принято)
```

- **`solve`** — эталон (для деривации), НЕ обязательная последовательность. Многокомандный —
  **блок** (`solve:` с отступом), команды идут в одном шелле (cwd/env живут внутри этапа). `<output>`
  = stdout **последней** команды.
- **`observe`** — какие пути сравнивать (файл, `каталог`, или `stdout`). Каталог — можно (обходится
  рекурсивно), но лучше узкий путь + `exclude` (широкий `/home` тянет мусор; волатильное само
  обрежется §5, но сигнал размывается).
- **`check exec <файл>`** — escape для невыразимого/недетерминированного (напр. `.tar.gz`: gzip
  недетерминирован → скрипт сверяет **список** `tar tzf | sort`). `exit 0` = принято.
- **Гранулярность:** многокомандный `solve` = один чекпоинт; несколько `stage` = проверять шаги по
  отдельности.

### 3.3 Приём — на чём стоит
`solve` + `observe` → дифф-канонизация (§5 арх., план C/D) даёт **толерантный** приёмный инвариант
(size-adaptive Jaccard/MinHash; точный хэш — частный случай). **Требование:** наблюдаемый набор
детерминирован (вывод в файл; без времени/PID/случайности) — иначе `derive` бросит `vacuous
canonical`. Приём — по **результату**, не по совпадению команд.

## 4. Скрытый системный / рабочий слой

**Стоячий слой ядра** (`hidden`), несущий: системную машинерию (инструментированная оболочка,
чекер, движок хуков, канонайзер), носитель **режимов** (`taskcreator`/`taskchecker`/`play`, §2 арх.),
и авторские скрипты/ассеты (`grade/`, арт, seed/verify).

### 4.1 Невидимость — через namespace, не через тайминг
Гарантия «студент не увидит» держится **изоляцией mount-namespace**, а НЕ гонкой mount/unmount по
времени (её ловит фоновый `inotify`/поллер). Механизм:
- команда студента → `systemd-nspawn` **без** скрытого слоя;
- проверка/хук ядра → **отдельный** запуск (свежий mount-ns) **со** скрытым слоем.
Постоянной сессии студента, которую можно поллить, нет — ядро гоняет команды по одной и между ними в
приватном контексте дёргает рабочий слой. В namespace студента этого пути **нет by construction** —
`ls -la`/фон/`inotify` не видят.

### 4.2 Root внутри контейнера
Namespace — про **видимость**, не про права: root в namespace студента видит только свои
монтирования; чужой (приватный) namespace ядра ему не виден без `setns` (нужен fd + CAP в целевом
user-ns) — а pid-ns контейнера чужих процессов не показывает. Значит **легитимный root ничего не
видит**. Оговорка: `systemd-nspawn` **без `--private-users`** — не жёсткая граница против
*враждебного* root, целящегося в побег; но это **не ломает модель** — неподделываемость на сервере
(§5). Хотим закрыть и враждебного root локально → образ с опцией **`--private-users`** (root-в-
контейнере ≠ root-на-хосте) + seccomp. По умолчанию — как есть; «злые»/CTF — с userns.

### 4.3 Оверхед
На каждую команду — доп. изолированный запуск проверки/хука со скрытым слоем: старт nspawn (~0.1–0.3 с)
+ возможный mount hidden-lower. Для интерактива незаметно. Смягчение: держать базовую цепочку **тёплой**
и лишь добавлять/снимать hidden-lower (или входить в заранее готовый ns), а не пересобирать всё.

### 4.4 Соглашение путей
Системное — под `/.hash/…` (уже используется: `.cmd*`, бандл `.task/`). Скрытый слой монтируется в
приватном ns ядра; студенту `/.hash` в его ns не показывается оболочкой (полу-скрытие по соглашению),
а грейдер — вообще в приватном ns (полная невидимость).

## 5. Безопасность / threat model

- **Гарантия — на сервере (§9 арх.):** глобальный ключ = `HMAC(server_secret, student_id ‖ task_id)`,
  сервер **ре-верифицирует evidence** (план E). Секрет только на сервере.
- **Локальная невидимость/скрытие — анти-казуальный-чит и UX, НЕ гарантия.** Даже увидев локальный
  грейдер, глобальный ключ подделать нельзя.
- **Локальный ключ** — nonce, провизорный прогресс-токен (план E). **Интерактив/подсказки/условия —
  advisory**, приём не решают.
- Опция `--private-users` — уровень образа, для твёрдой локальной изоляции против враждебного root.

## 6. Обработчики — контракт делегирования

**`exec <файл>`** на любой директиве-значении (`hint`, `check`, `condition`, `solve`, `readme`,
`voice`/`say`, `on enter/pass`, `react`). Файл — **любой исполняемый** (интерпретатор по shebang:
`#!/bin/sh`, `#!/usr/bin/python3`, бинарь). Расширение косметическое.

**Вход:**
| канал | что |
|---|---|
| `argv[1]` | текущая команда студента (сырая строка) |
| env `HP_TRIES` | число реальных попыток на этапе (без `neutral`) |
| env `HP_LAST_OUT` | вывод последней команды |
| env `HP_HISTORY` | путь к файлу истории команд |
| env `HP_STATE` | путь к JSON сессии (**чтение-запись** → память между вызовами) |
| env `HP_ROOTFS` | путь к ФС студента |
| env `HP_STAGE` | текущий этап |
| env `HP_ARG_*` | именованные параметры из DSL (`exec f.sh expected="a b"` → `HP_ARG_expected`) |

**Выход** (смысл — по директиве):
| директива | ответ |
|---|---|
| `hint`/`say`/`voice`/`readme` | **stdout** = текст показать |
| `check`/`condition`/`require` | **exit-код**: `0` = принято/разрешено |
| `solve` | **stdout** = команды эталона (или файл = скрипт-решение) |
| `on enter/pass`/`react`/`seed` | сайд-эффекты; `stdout` (если есть) — показать |

**Потолка нет:** состояние в `HP_STATE` (адаптив/ротация/«настроение»), любой язык, полный контекст.
Файлы — в скрытом слое (§4). Пример:
```sh
#!/bin/sh
cmd="$1"                                   # команда студента
case "$cmd" in
  grep*) [ "${HP_TRIES:-0}" -ge 3 ] && echo "Ты близко — добавь -r 🔁" ;;
esac
```

## 7. Интерактив — «система общается»

Слой **событие → обработчик** поверх `HookRegistry` (план 2). События: `command(cmd,out)`,
`enter/pass/fail(stage)`, `idle`, `output-match`. Директивы `voice`/`hint`/`say`/`show`/`react` —
сахар, регистрирующий обработчики; сложное — `exec <файл>` с полным `ctx` (§6).

### 7.1 Никакого голого `stuck` — только явные условия
`hint <условие> <значение>`, условие — явный атом:
- `tries N` — после **N реальных попыток** на этапе (команды **без `neutral`**: `ls`/`cd`/… не
  считаются);
- `idle N` — после N секунд без прогресса;
- `cmd <база> [has <флаги>] [missing <флаги>]` — студент запустил `<база>` с/без флагов (над `cmd.Cmd`);
- `output "<подстрока>"` — вывод содержал подстроку.
Один атом на строку; **комбинации** («не тот grep И ≥3 попыток») → `hint <атом> exec file` (файл
до-проверяет) либо `react on command exec file` (файл решает всё). `neutral <список>` задаёт, что не
считается попыткой (тот же список кормит и шум дифф-канонизации §5 — одно понятие).

### 7.2 Живой печатающий вывод (динамический voice)
**Всё общение система→студент рендерится с эффектом «печатающей машинки»** — символы/строки появляются
последовательно на **читаемой скорости** (как субтитры/чат в фильмах), с микро-паузами на пунктуации
для «говорящего» ощущения. Свойство рантайм-рендера (оболочка/UI).
```
settings
  type-speed  45          # символов/сек по умолчанию (настраивается)
  type-pause  ".,!?" 180ms # пауза на пунктуации

voice
  hello  "Йо! Сегодня приручаем логи 🧑‍💻"      # инлайн …
  hello  exec greet.sh                            # … или динамически (per-student)
  bye    "Красава 🎉"
```
`voice`/`say` — динамические: текст может приходить из `exec`-файла; рендер — печатающий, скорость
настраиваемая (глобально `settings.type-speed`, при желании — на сообщение).

## 8. Что переиспользуем vs что новое

| Готово (планы 1–G) | Новое (эта спека) |
|---|---|
| overlay mount/umount, `prepare(lowers)`, `build_base` | резолвер `FROM`-DAG → `lowers`, исполнитель `build`, хранилище |
| `taskcode/*`: derive/bundle/checker/execute/codegen | парсер DSL → внутренняя модель; `exec`-делегирование |
| `PlaySession`/`progress`/`hints`/`sync`/`grade`/`server` | скрытый слой в приватном ns; контракт `HP_*` |
| `HookRegistry`, `cmd.Cmd` | слой интерактива: условные подсказки, печатающий рендер, `voice` |
| ключи/evidence/сервер (E) | опция `--private-users` на образ |

DSL и Python-билдер — **два фронта к одной модели** (`TaskCode`/`Bundle` + регистрации хуков); можно
писать хоть чистым DSL, хоть смешивать с `exec`-файлами.

## 9. Фазы

1. **Образы:** формат рецепта + парсер, `build` (mount замыкания → `run` → upperdir=слой),
   резолвер `FROM`-DAG, локальное хранилище, самоимя/версии, мульти-`from`+конфликты.
2. **Задание-на-образе:** блоки `stage`/`solve`/`observe`/`check`, деривация на смонтированной цепочке
   (переиспользуем `taskcode`), скрытый слой + `on enter/pass`, контракт `HP_*`.
3. **Интерактив:** события поверх `HookRegistry`, условные `hint` (`tries`/`idle`/`cmd`/`output`,
   `neutral`), `voice`/`say`/`show`, **печатающий рендер** (`settings.type-speed`), `react exec`.
4. **Реестр:** push/pull образов по имени (§8 арх.), аутентификация записи.
5. **Миграция контента:** 24 задания по плейбуку (`docs/Миграция контента …`), в первую очередь
   контейнерные/сетевые.

## 10. Открытые вопросы (на твоё решение)

1. **Ключевые слова DSL — англ. (`stage/solve/hint`) или рус. (`этап/решение/подсказка`)?**
2. **`settings.type-speed`** — единая скорость печати ок, или нужна и «мгновенно» (для длинных
   выводов команд), и «медленно» (для драматичных реплик)? Пейджер для больших файлов в `show`?
3. **Блок-синтаксис** — отступами (как здесь) или явные `end`/скобки?
4. **`exec`** как ключевое слово делегирования — норм, или другое (`via`/`call`)?
5. Нужен ли `on fail` (реакция на неверный шаг) как отдельное событие сразу, или через `react`?
