# Всё раздаётся образами: база и обновления заданий с пула — дизайн

Дата: 2026-09-27. Статус: принят к реализации после двух обзоров Codex (сессия
`01a0e2c4-57fd-7250-bd60-9c04e66b364f`): находки первого — §3, второго — §3a.

## 1. Проблема

Сегодня:

- Базовый образ `debian:trixie` не раздаётся. Каждая машина собирает его сама из
  `base/rootfs.tar` через apt (~2 мин, ~35 пакетов) и пересобирает при каждой смене
  стампа runtime (`runtime/etc/hp-base-version`). Любая правка консоли = apt-сборка у
  каждого студента при следующем запуске (`cli.ensure_base_image`, `image/base.py`).
- Образ задания клиент тянет только если ref отсутствует локально
  (`cli.cmd_pool_run`, `remote.pull_many`). Перезалитый `bunnyton/x:1` до тех, у кого он
  уже есть, не доходит; обновляется только бандл задания (по digest в каталоге).
- Скачанные блобы распаковываются от имени пользователя (`remote.RemoteRegistry.sudo`
  = False, `blob.unpack_image`): владельцы и setuid теряются. Для базы это фатально
  (`sudo`, systemd). Сервер при PUT тоже распаковывает без sudo.
- Блобы — несжатый tar; слой базы 133 МБ.

Требование автора: «чтобы гибкость была, нужно, чтобы раздавалось всё как образы» —
и база, и обновления заданий приезжают с пула, без ручного бампа версий; со сжатием.

## 2. Решения (кратко)

1. **Сервер хранит залитый блоб как есть и никогда его не распаковывает.** Файл
   называется по содержимому: `<ref>/blob-<sha256>.tar.gz`. Digest = sha256 файла.
2. **Атомарная публикация поколения**: PUT пишет во временный файл с подсчётом sha256,
   валидирует структуру архива, переименовывает в `blob-<digest>.tar.gz`, затем одним
   `os.replace` подменяет `meta.json`, где записаны `digest` и `blob` (имя файла).
   GET читает `meta.json` один раз и отдаёт ровно тот файл, который в нём назван —
   пара «тело + заголовок digest» всегда из одного поколения. Старые `blob-*.tar.gz`
   удаляются после успешной публикации (best effort).
3. **Digest в протоколе**: `HEAD`/`GET /image/<ref>` отдают `X-Image-Digest`; строки
   `/images` получают поле `digest`.
4. **Клиент помнит `pool_digest`** в локальном `meta.json`; образ «устарел», если пул
   сообщает digest и он отличается от локального. Без digest на пуле (старые заливки)
   образ никогда не перетягивается.
5. **Base ref включает стамп runtime**: `debian:trixie-<stamp>` (сейчас `trixie-18`).
   Один helper `base_ref()`; через него идут ВСЕ точки входа: `cmd_build`, `_run_task`,
   `_run_image`, `push base`. Несовпадение стампов невозможно по построению; внутри
   одного стампа обновление — по digest.
6. **Студенческий `run`** тянет образ задания и базу, если их нет или они устарели.
   `pull_new` (обновление каталога в TUI) — то же правило.
7. **Распаковка с сохранением владельцев**: блобы с root-owned членами клиент
   распаковывает через `sudo tar`, замена слоя — переименованием в том же каталоге
   (атомарно, без `sudo rm`). Точная команда — §5.
8. **Потоки, не память, в обе стороны**: `pack_image_to_file` пишет tar.gz на диск;
   PUT отправляет файл потоком (`Content-Length` + file object); сервер читает
   `request.stream` в файл; GET отдаёт файл `send_file`; клиент качает в файл, считая
   sha256, и сверяет с `X-Image-Digest`.
9. **Сжатие**: pack пишет `tar.gz`; unpack автоопределяет (и `tarfile`, и GNU `tar -x`
   читают gz и plain). Старые несжатые блобы читаются как раньше.
10. **Без пула** (машина автора, тесты) база собирается локально, как сегодня.

## 4. Сервер (`registry/server.py`, `registry/blob.py`, `imagestore/store.py`)

**Хранилище сервера** — `ImageStore` в `env.registry / "store"` (как сегодня; это
отдельный от авторского `images/` каталог). Запись образа:

```
<store>/<ns>/<name>/<ver>/
  meta.json          {name, version, parents, digest, blob: "blob-<digest>.tar.gz"}
  blob-<digest>.tar.gz
  task/              (бандл задания, как сегодня)
  layer/             (только у legacy-записей, залитых до этой версии)
```

- **PUT `/image/<ns>/<name>/<ver>`** (author/admin):
  1. `request.stream` → `<dir>/incoming-<uuid>.tmp`, попутно sha256.
  2. Валидация `tarfile.open(tmp)` без извлечения: есть член `meta.json`; есть член
     `layer` (каталог); каждый член — `meta.json` или под `layer/`; нет абсолютных путей
     и `..`; `meta.name:meta.version` == ref из URL. Нарушение → tmp удалён, `400`,
     текущее поколение не тронуто.
  3. `os.replace(tmp, <dir>/blob-<digest>.tar.gz)`; `meta.json` пишется во временный
     файл и `os.replace` → публикация. Затем удаляются `blob-*.tar.gz`, не названные в
     новой meta (best effort, ошибки игнорируются).
  4. Ответ `201`, заголовок `X-Image-Digest`.
- **HEAD**: `200` + `X-Image-Digest`, если meta содержит `digest`; `200` без заголовка
  для legacy-записей (`layer/` без digest); `404` иначе.
- **GET**: meta читается один раз; если в ней `blob` — `send_file(<dir>/<blob>)` с
  `X-Image-Digest`; иначе legacy: `pack_image` на лету (plain tar, без заголовка).
- **`/images`**: поле `digest` (или `null`).
- **`ImageStore`**: `list()` считает образом каталог с `meta.json` и (`layer/` или файлом
  `blob-*.tar.gz`); `get()` возвращает `digest` и `blob`; `set_pool_digest(ref, digest)`
  пишет `pool_digest` в meta; `save()` без изменений (локальные сборки автора).
- `closure_refs` (meta.parents), `push_task`/`task GET` (`<dir>/task`), каталог, web-карточка,
  attachments — работают без `layer/`; для них добавляются blob-only тесты (§9).

## 5. Клиент (`registry/remote.py`, `registry/blob.py`, `cli.py`)

- `RemoteRegistry.image_digest(ref) -> str | None` (HEAD; `None` = нет заголовка).
- `download_image(ref, dest: Path) -> str`: поток в файл + sha256; если сервер прислал
  `X-Image-Digest` и он не совпал → файл удалён, `ValueError("digest mismatch")`.
  Возвращает digest (или `""` для legacy).
- `pull_many(refs, store, *, refresh=False)`: ref нужен, если его нет локально ИЛИ
  (`refresh` и `image_digest(ref)` не None и ≠ `store.get(ref).pool_digest`). После
  распаковки — `store.set_pool_digest(ref, digest)`. `pull()` — то же для одного ref.
- `blob.blob_needs_root(path) -> bool`: True, если у любого члена `uid == 0` (кроме
  самого `meta.json`) или установлен setuid/setgid-бит.
- `blob.unpack_image_file(path, store, *, sudo)`:
  - `sudo=False` (слои без root-owned членов): как сегодня — `tarfile`, `filter=
    "fully_trusted"`, во временный каталог, затем `store.save(...)`.
  - `sudo=True`:
    ```
    incoming = <dir>/layer.incoming-<uuid>      # mkdir от пользователя
    sudo tar -xpf <blob> --same-owner --strip-components=1 -C <incoming> layer
    ```
    (`-x` автоопределяет gz/plain; `layer` — селектор членов; `--strip-components=1`
    снимает префикс `layer/`; `--same-owner` действует, т.к. tar запущен от root;
    каталог `<incoming>` создан пользователем, поэтому его можно переименовать в
    том же родителе). Затем: если есть `layer/` → `os.rename(layer, layer.old-<uuid>)`;
    `os.rename(incoming, layer)`; `meta.json` (name, version, parents, pool_digest)
    пишется через tmp + `os.replace`; старый слой удаляется `sudo rsync -a --delete
    <пустой>/ layer.old-<uuid>/` + `os.rmdir`. Если удаление старого не удалось —
    предупреждение, слой уже актуален; следующий pull доубирает `layer.old-*`.
  - `unpack_image(bytes, ...)` остаётся тонкой обёрткой (пишет bytes во временный файл
    и зовёт `unpack_image_file`) — для тестов и legacy-вызовов.
- `pack_image_to_file(img, dest: Path) -> Path`: `tar.gz` (`tarfile` `w:gz`, либо
  `sudo tar -czf - …` для слоёв с нечитаемыми файлами, как сегодня, но с `-z`).
  `pack_image(img) -> bytes` остаётся обёрткой. `_put_image` шлёт файл потоком
  (`Request(data=fileobj)`, `Content-Length`).
- `cmd_pool_run`: `pull_many([task_ref, base_ref()], store, refresh=True)`, затем
  `_run_task(..., pool=client)`.
- `pull_new`: `refresh=True`.

## 6. База (`cli.py`, `image/base.py`)

- `base_ref() -> str` = `f"{_BASE_NAME}:{_BASE_VERSION}-{runtime_stamp()}"`, стамп читается
  из `runtime/etc/hp-base-version` (`image/base.py` уже умеет).
- `ensure_base_image(env, store, *, pool: RemoteRegistry | None = None) -> Path`:
  1. Есть локально `base_ref()`: при `pool` — если `pool.image_digest(base_ref())`
     известен и ≠ локальному `pool_digest` → `pull_many([base_ref()], refresh=True)`;
     вернуть слой.
  2. Нет локально, `pool` дан и `pool.image_digest(base_ref())` не `None` (пул знает
     ref) → pull → вернуть.
  3. Иначе — локальная сборка из `rootfs.tar` (как сегодня), сохранение под
     `base_ref()`; при `pool` печатается: «база для runtime N на пуле не найдена,
     собираю локально».
- Все вызовы `ensure_base_image(env, store)` — `cmd_build`, `_run_task`, `_run_image` —
  получают `pool` там, где он есть (`cmd_pool_run` → `_run_task`); авторские пути
  зовут без пула.
- Старые записи `debian:trixie` в локальных store игнорируются.
- `_base_layer_current` (стамп внутри слоя) остаётся проверкой для локальных сборок.

## 7. Автор и деплой

- `hashengine push base [registry] [--force]`: в `hashengine/cli.py` позиционный `ref`
  равен `base` → `cli.cmd_push_base(env, registry, force)`: `ensure_base_image(env,
  store)` (локальная сборка при необходимости) → `cmd_push(env, base_ref(), …)`.
  `_attach_taskfile` для базы молчит (у базы нет Taskfile).
- `content/tasks/deploy.sh`: первым шагом `hashengine push base --force`, дальше задания
  как сейчас. `--force` для заданий больше не нужен для доставки обновлений (digest
  меняется сам), но остаётся для перезаписи повреждённых блобов.
- Порядок выкладки после изменения runtime: обновить пакет на сервере (если менялся
  серверный код) → `push base` → задания → релиз клиента. Студент со старым клиентом
  продолжает тянуть свою `trixie-<старый стамп>`, пока не обновится.

## 8. Совместимость

| Клиент \ Сервер | старый сервер | новый сервер |
|---|---|---|
| старый клиент (0.3.4) | как сегодня | GET отдаёт gz-блоб — `tarfile.open(mode="r")` читает; заголовок игнорируется; базу собирает сам (`debian:trixie`) |
| новый клиент | HEAD без digest → ничего не перетягивает; базы `trixie-18` на пуле нет → локальная сборка | полный режим |

Legacy-записи на новом сервере (только `layer/`): GET пакует на лету, digest нет →
клиенты их не перетягивают до перезаливки автором.

## 9. Проверка

- Tier1: `ImageStore.list/get/set_pool_digest` для blob-only и legacy записей;
  `blob_needs_root` (uid 0, setuid, обычный слой); валидация PUT-архива (нет `layer/`,
  путь вне `layer/`, несовпадение name:version → отказ); sha256 при потоковой записи;
  gz/plain автоопределение; `base_ref()` из стампа.
- Tier2 (loopback-пул, фикстура `registry`): PUT → HEAD/GET с digest → pull записывает
  `pool_digest` → повторный PUT изменённого слоя → `refresh` перетягивает, без изменений
  не перетягивает; PUT битого архива → 400, HEAD/GET по-прежнему старое поколение;
  GET legacy-образа без digest и его pull новым клиентом; несовпадение sha256 при
  скачивании → ошибка, файл удалён; blob-only записи: `/images`, web-карточка,
  attachments, task PUT/GET, публикация в каталог, closure; `ensure_base_image(pool=…)`
  тянет базу, не тянет при совпадающем digest, собирает локально без базы на пуле;
  «старый клиент»: текущий `unpack_image(bytes)` читает gz и plain блобы.
- Tier3: `unpack_image_file(sudo=True)` на слое с root-owned каталогами, setuid-файлом
  и симлинками: владельцы и биты сохранены (`stat -c %U:%a`); повторный pull поверх
  существующего root-owned слоя; прерванная уборка `layer.old-*` доубирается следующим
  pull; консоль грузится с базы, скачанной с пула.
- Живая проверка `expect`-ом: чистый `HASHPASS_HOME`, пул на loopback, `hashpass run`
  тянет базу и задание, решает, финал.

## 10. Вне рамок

- Раздача `rootfs.tar` (нужен только автору для локальной сборки базы).
- Дедупликация слоёв между образами, докер-совместимые манифесты.
- Удаление orphan-записей `debian:trixie` из старых store.
