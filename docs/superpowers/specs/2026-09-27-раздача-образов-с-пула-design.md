# Всё раздаётся образами: база и обновления заданий с пула — дизайн

Дата: 2026-09-27. Статус: на ревью у автора. Обзор дизайна делал Codex (сессия
`01a0e2c4-57fd-7250-bd60-9c04e66b364f`); его находки учтены в §3.

## 1. Проблема

Сегодня:

- Базовый образ `debian:trixie` не раздаётся. Каждая машина собирает его сама из
  `base/rootfs.tar` через apt (~2 мин, ~35 пакетов) и пересобирает при каждой смене
  стампа runtime (`runtime/etc/hp-base-version`). Любая правка консоли = apt-сборка у
  каждого студента при следующем запуске (`cli.ensure_base_image`, `image/base.py`).
- Образ задания клиент тянет только если ref отсутствует локально
  (`cli.cmd_pool_run`, `remote.pull_many`). Перезалитый `bunnyton/x:1` до тех, у кого он
  уже есть, не доходит; обновляется только бандл задания (по digest в каталоге).
- Скачанные блобы распаковываются от имени пользователя (`remote.RemoteRegistry.sudo`
  = False, `blob.unpack_image`): владельцы и setuid теряются. Для базы это фатально
  (`sudo`, systemd). Сервер при PUT тоже распаковывает без sudo.
- Блобы — несжатый tar; слой базы 133 МБ.

Требование автора: «чтобы гибкость была, нужно, чтобы раздавалось всё как образы» —
и база, и обновления заданий приезжают с пула, без ручного бампа версий; со сжатием.

## 2. Решения (кратко)

1. **Сервер хранит залитый блоб как есть** (`<ref>/blob.tar.gz`) и отдаёт его байт в
   байт. Слой на сервере не распаковывается. Digest = sha256 файла блоба.
2. **Атомарная замена**: PUT пишет во временный файл, считает sha256 на лету, затем
   `os.replace` блоба, потом `meta.json` (+ digest). Читатели старого файла дочитывают
   старый inode.
3. **Digest в протоколе**: `HEAD`/`GET /image/<ref>` отдают `X-Image-Digest`; строки
   `/images` получают поле `digest`.
4. **Клиент помнит `pool_digest`** в локальном `meta.json`; образ «устарел», если пул
   сообщает digest и он отличается от локального. Без digest на пуле (старые заливки)
   образ никогда не перетягивается.
5. **Base ref включает стамп runtime**: `debian:trixie-<stamp>` (сейчас `trixie-18`).
   Клиент тянет ровно свою версию базы; несовпадение стампов невозможно по построению.
   Внутри одного стампа обновление — по digest (автор перезалил базу с фиксом).
6. **Студенческий `run`** тянет образ задания и базу, если их нет или они устарели.
   `pull_new` (обновление каталога в TUI) — то же правило.
7. **Распаковка с сохранением владельцев**: блобы с root-owned файлами клиент
   распаковывает через `sudo tar`, замена слоя — переименованием в том же каталоге
   (атомарно, без `sudo rm`).
8. **Потоки, не память**: PUT читает `request.stream` в файл; GET отдаёт файл
   `send_file`; клиент качает в временный файл, считая sha256, и проверяет его с
   `X-Image-Digest`.
9. **Сжатие**: pack пишет `tar.gz`; unpack автоопределяет (tarfile и GNU tar читают
   и gz, и plain). Старые несжатые блобы читаются как раньше.
10. **Без пула** (машина автора, тесты) база собирается локально, как сегодня.

## 4. Сервер (`registry/server.py`, `registry/blob.py`, `imagestore/store.py`)

- **PUT `/image/<ns>/<name>/<ver>`** (author/admin): поток → `<dir>/blob.tar.gz.<uuid>.tmp`
  с подсчётом sha256; из блоба читается только член `meta.json` (через `tarfile`, без
  извлечения остального) для `name`/`version`/`parents`; проверка, что `name:version`
  совпадает с URL; `os.replace` → `blob.tar.gz`; затем `meta.json` = `{name, version,
  parents, digest}` (tmp + replace). Ответ `201` с `X-Image-Digest`.
- **HEAD**: `200` + `X-Image-Digest`, если есть `meta.json` с digest; `200` без заголовка
  для legacy-образов (только `layer/`); `404` иначе.
- **GET**: если есть `blob.tar.gz` — `send_file` + `X-Image-Digest`; иначе legacy: `pack_image`
  на лету без заголовка (старые заливки продолжают скачиваться).
- **`/images`**: поле `digest` (или `null`).
- **`ImageStore`**: `list()` считает образом каталог с `meta.json` и (`layer/` или
  `blob.tar.gz`); `get()` возвращает `digest`; новый `set_pool_digest(ref, digest)`;
  `save()` без изменений (локальные сборки автора).
- `closure_refs`, `push_task`, каталог, attachments — без изменений (им нужен только
  `meta.json` и `task/`).
- Локальный реестр автора (127.0.0.1:8080) — тот же код: рядом с собранным `layer/`
  появится `blob.tar.gz`. Это удвоение диска только у автора; приемлемо.

## 5. Клиент (`registry/remote.py`, `cli.py`)

- `RemoteRegistry.image_digest(ref) -> str | None` (HEAD).
- `_get_image_to_file(ref, dest)`: поток в файл + sha256; при расхождении с заголовком —
  `ValueError("digest mismatch")`, файл удаляется.
- `pull_many(refs, store, *, refresh=False)`: при `refresh=True` ref считается нужным,
  если его нет локально ИЛИ `image_digest(ref)` известен и ≠ `store.get(ref).digest`
  (локальное поле `pool_digest`). После распаковки — `store.set_pool_digest`.
- `unpack_image_file(path, store, *, sudo)`:
  - `sudo=False`: как сегодня (`tarfile`, `filter="fully_trusted"`), для слоёв без
    root-owned файлов.
  - `sudo=True`: `mkdir <dir>/layer.incoming-<uuid>` (владелец — пользователь), затем
    `sudo tar -xpf <blob> --same-owner --strip-components=1 -C <incoming> layer`;
    `os.rename(layer → layer.old-<uuid>)`, `os.rename(incoming → layer)` — оба в одном
    родительском каталоге, поэтому доступны владельцу каталога; старый слой удаляется
    `sudo rsync -a --delete <пустой>/ layer.old/` + `rmdir`. Ни `sudo rm`, ни `chown`.
  - Нужен ли sudo — по членам архива: если у любого члена `uid == 0` или есть
    setuid/setgid-биты → `sudo=True`. Для базы это всегда так.
- `cmd_pool_run`: `pull_many([task_ref, base_ref], store, refresh=True)`;
  `ensure_base_image(env, store, pool=client)` — см. §6.
- `pull_new`: `refresh=True` для образов каталога.

## 6. База (`cli.ensure_base_image`, `image/base.py`)

- `base_ref() = f"debian:trixie-{stamp}"`, стамп читается из `runtime/etc/hp-base-version`.
- `ensure_base_image(env, store, *, pool: RemoteRegistry | None = None)`:
  1. Локально есть `base_ref` → при `pool` проверить digest (обновить, если устарела) →
     вернуть слой.
  2. Иначе при `pool` и `pool.image_digest(base_ref)` не None → `pull_many([base_ref],
     refresh=True)` → вернуть.
  3. Иначе (нет пула, или базы под этот стамп на пуле нет) — локальная сборка из
     `rootfs.tar`, как сегодня; сохраняется под `base_ref`. Студенту печатается одна
     строка: «база для runtime N на пуле не найдена, собираю локально» — сигнал автору.
- Старые записи `debian:trixie` в локальных store игнорируются (можно удалить руками;
  `hashengine images` их всё ещё покажет — это нормально).
- Стамп-проверка `_base_layer_current` остаётся для локальных сборок.

## 7. Автор и деплой

- `hashengine push base [--force]` — новая форма: собирает базу локально при
  необходимости и пушит `debian:trixie-<stamp>`. `pack_image` для root-owned слоя идёт
  через `sudo tar -czf -`.
- `content/tasks/deploy.sh`: первым шагом `hashengine push base --force`, дальше задания
  как сейчас; `--force` для заданий больше не обязателен для доставки обновлений (digest
  меняется сам), но остаётся для перезаписи повреждённых блобов.
- Порядок выкладки после изменения runtime: обновить пакет на сервере (если менялся
  серверный код) → `push base` → задания → релиз клиента (GitHub Release). Студент со
  старым клиентом продолжает тянуть свою `trixie-<старый стамп>`.

## 8. Совместимость

| Клиент \ Сервер | старый сервер | новый сервер |
|---|---|---|
| старый клиент (0.3.4) | как сегодня | GET отдаёт gz-блоб — `tarfile` читает; заголовок игнорируется; базу собирает сам (ищет `debian:trixie`) |
| новый клиент | HEAD без digest → ничего не перетягивает; базы `trixie-18` на пуле нет → локальная сборка | полный режим |

Legacy-образы на новом сервере (только `layer/`): GET пакует на лету, digest нет →
клиенты их не перетягивают до перезаливки автором.

## 9. Проверка

- Tier1: `ImageStore.list/get/set_pool_digest`; выбор sudo по членам архива; sha256 при
  потоковой записи; gz/plain автоопределение; `base_ref()` из стампа.
- Tier2 (loopback-пул): PUT → HEAD с digest → pull записывает `pool_digest` → повторный
  PUT изменённого слоя → `refresh` перетягивает; PUT с битым блобом → 400, старый блоб
  цел; GET legacy-образа без digest; `ensure_base_image(pool=…)` тянет базу вместо
  сборки и не тянет при совпадающем digest; несовпадение sha256 → ошибка, файл удалён.
- Tier3: `sudo tar`-распаковка базы сохраняет владельцев (`stat -c %U /usr/bin/sudo` =
  root, setuid на месте) и консоль грузится с базы, скачанной с пула.
- Живая проверка `expect`-ом: чистый `HASHPASS_HOME`, пул на loopback, `hashpass run`
  тянет базу и задание, решает, финал.

## 10. Вне рамок

- Раздача `rootfs.tar` (он нужен только автору для локальной сборки базы).
- Дедупликация слоёв между образами, докер-совместимые манифесты.
- Удаление orphan-записей `debian:trixie` из старых store.
