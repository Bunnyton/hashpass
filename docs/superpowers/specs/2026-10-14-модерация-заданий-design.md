# Модерация заданий на пуле: одобрение, отклонённые, about.md, просмотрщик

Дата: 2026-10-14. Статус: дизайн одобрен пользователем в чате, спецификация на просмотре.

## Зачем

Пул стал общим: на нём задания нескольких авторов (`4istBorw/root-tour` рядом с курсом
`bunnyton/*`). Сейчас любое опубликованное задание после «Показать» сразу видно студентам, его
описание правится в веб-карточке, а удалить задание может только админ раскладкой каталога.
Пользователь хочет (2026-10-14):

1. **about.md** — в каждом задании; при push он становится описанием задания на пуле (как README
   на GitHub). Поле описания в вебе убираем; правка — через консоль (about.md + push).
2. **Одобрение.** Задание видно студентам, только если админ его одобрил или для него включено
   авто-одобрение. Одобрять/отклонять админ может из hashpass. Автор кладёт задание в любой блок
   и создаёт свои блоки, но студенты увидят его только после одобрения.
3. **Удаление.** Автор удаляет с пула только свои задания — «это важно».
4. **Отклонённые.** Отклонённое задание лежит в блоке «Отклонённые» неделю и удаляется. В
   hashpass блок виден при включённой опции «показать отклонённые» (по умолчанию включена).
   Об отклонении автор узнаёт там же.
5. **Просмотрщик** в hashpass: каталоги задания, Taskfile и все остальные файлы.

Ответы пользователя на уточнения:

- обновление одобренного задания **одобряется заново**; до этого студенты видят прежнюю
  одобренную версию;
- авто-одобрение — **и общий переключатель пула, и отметка у автора**; админ — тоже автор и
  тоже выбирает себе авто-одобрение; **по умолчанию выключено у всех, даже у админа**: свои
  задания админ одобряет сам;
- причину отклонения админ пишет **по желанию**.

Допущения (пользователь не возражал): флаг «скрыто» остаётся у автора для обкатки — студенту
задание видно, когда оно одобрено **и** не скрыто, а блок открыт; блок «Отклонённые» и
просмотрщик — для автора задания и админа, студентам не показываются.

## Как устроено сейчас

- Каталог — `catalog.json` (`registry/catalog.py`): блоки с флагом `open`, в них задания
  `{name, version, digest, hidden}`. Студенту (`GET /catalog`) отдаются только
  `available = block.open and not hidden`; автор/админ видят всё с пометкой `preview`.
- Образ задания — одно поколение на ref в `ImageStore`: блоб слоя + каталог `task/` рядом
  (`PUT /image/…`, `PUT /task/…?publish=1&block=…`). Запись — только в свой namespace
  (`_authorize_write`), без namespace — только админ.
- Вложения — `AttachmentStore`: описание + файлы (Taskfile, `source.tar.gz` с ca3a28b);
  читать — авторам и админам.
- Пользователи — `UserStore` (`users.json`): роль `student|author|admin`, группа, комментарий.
- hashpass TUI (`tui.py`): каталог по блокам, клавиша `h` — скрыть/показать (для персонала).

## Решение: снимок одобренной версии (подход A)

Рассматривались: A — снимок при одобрении; B — хранилище поколений (каждый push — поколение,
каталог указывает одобренное; гибче, но переделка `ImageStore` и всех маршрутов); C — не хранить
старое (пользователь отказался). Выбран **A**.

### Данные

`catalog.json`, запись задания — новые поля (старые записи читаются со значениями по умолчанию):

| Поле | Значение |
|---|---|
| `state` | `pending` \| `approved` \| `rejected` |
| `approved_digest` | digest поколения, которое видят студенты (`null` — ещё ни разу не одобрено) |
| `reason` | причина отклонения (может быть пустой) |
| `rejected_at` | время отклонения (unix), для чистки через 7 дней |
| `owner` | логин автора (namespace ref-а; для ref без namespace — `admin`) |

Пул (`pool-settings.json` рядом с `catalog.json`): `{"auto_approve": false}`.

`users.json`, запись пользователя: `auto_approve: false` (по умолчанию у всех, включая админа).

**Миграция:** при первом чтении старого каталога каждое задание получает `state = approved`,
`approved_digest = digest` — курс у студентов не пропадает; одобренный снимок для таких записей
создаётся лениво (см. «Снимок»).

### Снимок

Каталог снимков: `<root>/approved/<name>/<version>/` — копия блоба слоя (как в `ImageStore`:
`layer.blob` + `meta.json` с digest) и каталога `task/`. Делается в момент одобрения (и при
авто-одобрении — сразу после push). Повторное одобрение заменяет снимок атомарно (копия во
временный каталог → `rename`).

Раздача:

- **студент** — `GET /image/<ref>`, `GET /task/<ref>`, `GET /closure/<ref>` для задания из
  каталога отдаются из снимка; нет снимка и `approved_digest` совпадает с текущим digest
  (мигрированная запись) — из текущего поколения; задание не одобрено — 404;
- **автор задания и админ** — текущее (свежее) поколение, как сейчас; так автор обкатывает
  обновление, а админ проверяет то, что одобряет;
- другие авторы — как студенты (видят одобренное).

Образы, которые не задания (база `bunnyton/debian:trixie`), не модерируются.

### Видимость и состояния

```
push (новое задание)        → pending  (или approved, если авто-одобрение)
push (одобренное)           → pending, студенты видят снимок прежней версии
admin approve               → approved, снимок := текущее поколение
admin reject [причина]      → rejected, rejected_at := now; студентам — прежний снимок, если был
push (отклонённое)          → pending (reason/rejected_at сбрасываются)
rejected 7 дней             → удаление: образ, task/, снимок, вложения, запись каталога
```

Авто-одобрение срабатывает, если `pool.auto_approve` **или** `users[owner].auto_approve`.

`available` для студента = есть одобренная версия **и** не `hidden` **и** блок открыт. Блок,
в котором нет ни одного доступного студенту задания, студенту не отдаётся (как сейчас для
закрытых). Блоки по-прежнему создаёт `push --block <имя>`; автор может класть задание в любой
блок.

Ответ `GET /catalog` для персонала добавляет к строке `state`, `reason`, `rejected_at`,
`expires_at`, `owner`, `pending_update` (есть одобренная версия, а свежая ждёт). Отклонённые
задания идут виртуальным блоком «Отклонённые» в конце списка — автору только свои, админу все.

### Маршруты (новые)

| Маршрут | Кто | Что |
|---|---|---|
| `POST /catalog/approve {ref}` | admin | одобрить: снимок, `state=approved` |
| `POST /catalog/reject {ref, reason?}` | admin | отклонить |
| `DELETE /task/<ref>` | автор своего namespace, admin | удалить задание целиком (образ, task/, снимок, вложения, запись) |
| `PUT /pool/settings {auto_approve}` | admin | общий переключатель |
| `PUT /users/<user>/auto-approve {on}` | admin | отметка автора (в т.ч. себе) |

Права проверяются на сервере; клиентские кнопки — лишь удобство. Удаление чужого задания
автором — 403 с понятной причиной (как `_ownership_message`).

Чистка отклонённых: функция `purge_rejected(now)` — при старте пула и раз в час в фоновом
потоке (`cmd_serve` уже держит поток `watch_for_updates`).

### about.md

- `hashengine build` запоминает рядом с Taskfile путь задания (уже: `taskfile_path`);
  `hashengine push` читает `about.md` из каталога задания и шлёт его описанием
  (`PUT /attachment/<ref>?description=1`, тело — текст about.md; сервер кладёт его в
  `AttachmentStore.set_description`, права — как у прикрепления Taskfile). Нет `about.md` — описание не трогается.
- Веб-карточка: форма описания убирается, описание показывается как Markdown (только чтение) с
  подписью «правится в about.md задания».
- В hashpass описание задания показывается в карточке/предпросмотре задания (если есть).
- Каждому заданию курса — свой `about.md` (2–4 строки: тема, что делает студент); линт
  `tests/content/` — у каждого задания есть непустой `about.md`.

### hashpass (TUI)

- Строка задания для персонала: пометка `· на проверке` / `· обновление на проверке` /
  `· отклонено: <причина> · удалится через N дн.`; одобренное — без пометки.
- Клавиши (русская раскладка — тоже, как у остальных):
  - админ: `a` — одобрить; `r` — отклонить (диалог с полем причины, Enter — без причины);
  - автор/админ: `Del` — удалить своё задание (диалог подтверждения; чужое — сообщение «это
    задание автора X»);
  - все из персонала: `x` — показать/скрыть блок «Отклонённые» (по умолчанию показан;
    состояние сохраняется в `tui.json`, как тема);
  - автор/админ: `v` — просмотрщик.
- **Просмотрщик:** отдельный экран. Слева — дерево файлов задания из `source.tar.gz` (скачивается
  через `GET /attachment/<ref>?name=source.tar.gz`, распаковывается в кэш
  `~/.hashpass/sources/<ref>/` с безопасной распаковкой); справа — содержимое выбранного файла
  (текст с подсветкой Markdown/шелла; бинарный — «двоичный файл, N байт»). Нет архива — дерево из
  одного Taskfile. `Esc`/`q` — назад.
- Флаги авто-одобрения — в веб-разделе «Пользователи» (там уже роли) и общий переключатель там же.

### Совместимость

- Старые клиенты: сервер решает видимость сам и отдаёт студенту только одобренное — ломаться
  нечему. Старый hashpass просто не покажет новые пометки и клавиши.
- Старые записи каталога мигрируют как одобренные (см. «Данные»).
- `hashengine catalog layout` (админ) сохраняет `state`/снимки при перестановке.

### Ошибки

- Одобрение/отклонение несуществующего ref — 404; не админ — 403.
- Сбой копирования снимка — одобрение не применяется (каталог не меняется), ответ 500 с
  причиной; прежний снимок остаётся.
- Чистка отклонённых не трогает задание, если его успели перезалить (`state != rejected`).

## Проверка

- tier1: модель каталога (переходы состояний, миграция, авто-одобрение по пулу/автору, чистка
  через 7 дней, виртуальный блок), `about.md`-линт.
- tier2 (живой сервер `registry` фикстуры): роли на новых маршрутах (401/403/200), студент не
  видит pending, видит снимок прежней версии при pending-обновлении, автор удаляет своё и
  получает 403 на чужое, отклонённое видно автору и админу.
- Живая проверка на локальном пуле двумя логинами (автор + админ + студент): push → студент не
  видит → одобрение в hashpass (pty) → видит → обновление → студент видит старое → отклонение →
  «Отклонённые» с причиной → удаление своего; просмотрщик открывает Taskfile и `data/`.

## Вне рамок

- Уведомления по почте/мессенджерам об отклонении.
- История версий и откат на произвольное старое поколение.
- Модерация базовых образов.
