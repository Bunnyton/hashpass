# Курсы, ревизии образов и рабочий TUI `hashengine` — дизайн

Дата: 2026-10-21. Статус: на ревью у пользователя (вычитан Codex, замечания учтены).
Кампания из 4 этапов (§14), у каждого свой план.

## 0. Зачем

Пользователь, 2026-10-21:
- «Сделать интерфейс отдельный рабочий. Не смешивать всё в одну корзину».
- «Внутри платформы всё будет состоять исключительно из образов и тегов. Всё остальное — доп.
  накрутки… Простота, элегантность и удобство».
- «Этот проект — объединение github и docker, и потом будет docker-compose».
- «В курс и во всё остальное добавляем только через веб-интерфейс… Можно пушить образы (задания)».
- «hashpass позволяет выбрать курс и блок… там есть поиск. В зависимости от ссылки можно установить и
  скачать сразу с нужным пулом и курсом».
- «Сохраняем логику docker с хэшами и тегами… можно образу и заданию в любой момент времени навесить
  любой тег (если этот образ тебе принадлежит)».

Сейчас: один каталог на пул; раскладывает и одобряет только админ; авторы — серверная роль; `push`
перезаписывает `name:version`; локально автор работает через ручной пул `:8090` и `deploy.sh` с
массивом `BLOCKS`.

## 1. Модель: три слоя

| Слой | Аналог | Что это |
|---|---|---|
| **Образ** | Docker-образ | Неизменяемое содержимое (слои + `task/`), адресуется хешем. Имена — теги-указатели (§2) |
| **Курс** (`bunnyton/linux`) | Репозиторий GitHub | Владелец, видимость, участники с ролями, блоки → задания (ссылки на ревизии), предложения |
| **Compose** | docker-compose | Несколько машин в задании. *Потом; в модели только место* |

Реестр образов — ядро, курсов не знает. Курсы, предложения, порядок, прогресс — слой над реестром,
ссылающийся на ревизии. Студенту задание доступно **только через курс**.

## 2. Образы: хеши, теги, ревизии

Как в Docker: содержимое хранится по хешу, имена — указатели.

- **Репозиторий** — `owner/name` (`bunnyton/git-init`). Писать в него может только владелец namespace.
- **Тег** — `owner/name:tag` (`:1`, `:stable`, `:latest`) — указатель на линию ревизий.
- **Ревизия** — `owner/name:tag_vN`, N = 1, 2, 3… Каждый `push` в тег создаёт **новую неизменяемую**
  ревизию `_v(N+1)`; перезаписи больше нет. Старые ревизии хранятся.
- **`_latest`** — `owner/name:tag` без суффикса = `owner/name:tag_latest` = последняя ревизия тега.
  `hashpass run bunnyton/git-init:1` скачивает последнюю.
- **Суффиксы `_vN` и `_latest` зарезервированы**: тег, оканчивающийся на `_v<цифры>` или `_latest`,
  создать нельзя (ошибка при `build`/`push`/`tag`).
- **`hashengine tag <src> <dst>`** — навесить тег на любую свою ревизию, в любой момент (локально и в
  пуле; новая ревизия тега `dst` указывает на тот же хеш — данные не копируются). Только в своём
  namespace.
- **Чужой образ** при `pull` хранится под своим именем; переименовать/перетегировать его локально
  нельзя (`tag` в чужой namespace — отказ). Свой — можно.
- Хранилище: `blobs/<sha256>` (слои и `task/`), `repos/<owner>/<name>/tags.json`:
  `{tag: {"revisions": [{"n": 1, "digest": "…", "at": "…", "by": "…"}, …]}}`.
- Миграция: каждый нынешний `name:version` → тег `version` с единственной ревизией `_v1`.
- **Видимость репозитория**: `public` (по умолчанию; видят все вошедшие, как Docker Hub) или
  `private` (видит только владелец). Владелец делится приватным образом через **приватный курс**:
  его участники видят и проходят ревизии, стоящие в этом курсе, — и только их.
- **Приватный образ можно поставить только в приватный курс.** В публичный — отказ: «сделайте образ
  публичным». Сделать образ приватным, пока он стоит в публичных курсах, нельзя (покажет, в каких);
  сделать курс публичным, пока в нём есть приватные образы, — тоже (покажет, какие).
- Предложить чужой приватный образ нельзя (его не видно); владелец может предложить свой приватный
  в чужой приватный курс — тогда при принятии его участники получат доступ к этой ревизии.

### Удаление ревизии

Право владельца. Перед удалением показывается, в каких курсах ревизия используется.
- Не используется или только в своих курсах — удаляется сразу (свои курсы переключаются на
  последнюю оставшуюся ревизию тега; нет такой — задание убирается из курса).
- Используется в **чужих** курсах — становится **запросом на удаление** админу; владелец может его
  отменить, пока админ не решил. После одобрения чужие курсы переключаются так же, а их персонал
  видит пометку «ревизия удалена владельцем».
- Удаляется последняя ссылка на хеш — хеш удаляется из хранилища.

## 3. Пользователи

- Серверных ролей две: **пользователь** и **админ**. Роль `author` — устаревшая: в переходный период
  старые токены и записи с `author` работают как «пользователь»; миграция §12 даёт им роль автора в
  курсе `bunnyton/linux`. В коде `ROLES`/`_AUTHOR_ROLES` (`passwords.py:17`, `server.py:78`) —
  заменить проверками §5.
- **Любой пользователь** может отправлять образы в свой namespace и создавать курсы.
- **Группы упраздняются**: поле `group` переносится в начало комментария (`comment`) — туда можно
  писать что угодно. Вместо фильтра групп — **поиск пользователей** по логину и комментарию (ввёл
  «ИТ-21» — нашлись все из группы); из результатов можно добавить всех найденных в приватный курс.
- Удалить пользователя, у которого есть курсы, нельзя — сначала удалить курсы (их владелец — он).
  Его образы в чужих курсах — по правилам удаления ревизии (§2). Попытки и прогресс — как сейчас.

## 4. Курс

Хранится в `courses/<id>.json`; `id` неизменяем, `owner/name` — адрес. Переименование и передача —
не в первой версии (§13).

```json
{
  "id": "c-7f3a", "owner": "bunnyton", "name": "linux", "title": "Linux", "description": "…",
  "visibility": "public", "auto_accept": false,
  "members": {"alice": "author", "bob": "maintainer", "eve": "member"},
  "blocks": [{"id": "b1", "name": "Git", "open": true,
              "tasks": [{"repo": "bunnyton/git-init", "tag": "1", "rev": 3,
                         "hidden": false, "added_by": "bunnyton"}]}],
  "proposals": [ … §6 … ],
  "created_at": "…"
}
```

- Имя курса — `[a-z0-9-]`, уникально у владельца.
- `public` — видят и проходят все пользователи пула; `private` — владелец и `members`.
- **Заявка на доступ** к приватному курсу: по ссылке курса посторонний видит название, описание и
  кнопку «Запросить доступ» (с комментарием); сопровождающий/владелец принимает → пользователь
  становится участником, или отклоняет. В поиске курсов приватные не показываются — только по
  ссылке. Запись: `requests: [{"user", "comment", "state": "open|accepted|rejected", "at", "decided_by"}]`;
  у пользователя не больше одной открытой заявки на курс.
- Задание курса указывает на **ревизию** (`repo:tag_vN`). Порядок в блоке = номер для студента.
- Удалить можно только **пустой** блок.

## 5. Роли в курсе и проверка прав

| Роль | Видит/проходит | Предлагает | Добавляет сам, обновляет свои | Принимает/отклоняет, убирает, переставляет чужое, блоки | Видимость, участники, заявки*, удаление курса |
|---|---|---|---|---|---|
| любой (public) / участник (private) | ✓ | ✓ | | | |
| посторонний (private) | название, описание | | | | |
| **автор** | ✓ | ✓ | ✓ | | |
| **сопровождающий** | ✓ | ✓ | ✓ | ✓ | |
| **владелец** | ✓ | ✓ | ✓ | ✓ | ✓ |

\* Заявки на доступ принимают и сопровождающий, и владелец. Админ сервера — всё во всех курсах.

Одна функция решает доступ: `can(user, action, course)`. Ею проверяются **все** маршруты, включая
старые: `/catalog`, `/progress`, `/solution(s)`, `/attempt`, исходники и вложения, веб-страницы.
`/task/<ref>` для студента отдаёт ревизию, только если она стоит в курсе, который ему виден (или он
владелец образа / персонал такого курса). `/images`, `pull`, поиск, карточка образа — приватный
репозиторий видят только владелец, админ и участники приватных курсов, где стоит его ревизия
(и только эти ревизии).

## 6. Предложения

Аналог pull request; ключ — `(курс, repo:tag)`, у пары не больше одного открытого предложения.

```json
{"id": "p17", "kind": "add|update", "repo": "alice/regex", "tag": "1", "rev": 2,
 "block_id": "b1", "by": "alice", "comment": "…", "state": "open|accepted|rejected|withdrawn",
 "reason": "…", "at": "…", "decided_by": "…", "decided_at": "…"}
```

- **Добавить**: веб, «Предложить в курс» (со страницы курса или карточки образа) → образ, ревизия
  (по умолчанию последняя), блок, комментарий. Предлагать может любой, кто видит курс. Сервер
  проверяет, что ревизия существует, и фиксирует её номер в момент создания.
- Автор, сопровождающий, владелец добавляют **сразу**.
- **Обновить**: вышла новая ревизия тега, который стоит в курсе, — в курсе открывается предложение
  `update` до этой ревизии (если открытое уже есть — оно сдвигается на новую). Принимать не
  обязательно: курс остаётся на прежней ревизии, предложение можно отклонить. Для задания, которое
  автор+ добавил сам, он переключает ревизию сам (кнопка «обновить до vN» на месте предложения).
  Рассылка делается при `push` по индексу «тег → курсы» (`courses/index.json`); сбой записи одного
  курса не мешает остальным — при открытии курса недостающее предложение досоздаётся сверкой
  «последняя ревизия ≠ ревизия курса».
- Решают сопровождающий и владелец (админ). Отклонённые видны автору предложения 7 дней.
- `auto_accept` (настройка курса, **по умолчанию выключено**) — принимать предложения сразу.
- Автор предложения может отозвать его (`withdrawn`).
- Персонал перед решением может запустить предлагаемую ревизию («посмотреть, потрогать»).

## 7. Кого видно

- **Админ** видит всех пользователей и ищет по ним.
- Владелец, сопровождающий, автор курса видят **приступивших** к курсу (добавил курс или запустил
  в нём задание) — профиль, прогресс и попытки **по заданиям этого курса** — и ищут по ним, а для
  добавления участников в приватный курс — по всем пользователям (логин + комментарий).
- Обычный пользователь видит только себя.

## 8. Прогресс и исходники

- Прогресс — по `repo:tag` (без ревизии): решённое на `_v1` решено и на `_v3`, во всех курсах.
  Попытка хранит ревизию, на которой была. Прогресс по курсу — пересечение с его заданиями.
- «Приступил» — `enrollments/<user>.json: {course_id: at}`.
- Исходники (Taskfile, `hp/`, решения) видят: владелец образа, админ, автор+ любого курса, где стоит
  ревизия этого тега (для приватного образа — того приватного курса, куда его поставили).
- **Известное ограничение (отдельная задача после кампании):** скрытый слой `hp/` уезжает к студенту
  внутри задания (`blob.py:pack_task`) и читается с его хоста в `~/.hashpass/images/…/task/hp/`.
  Курсы его не закрывают.

## 9. `hashpass` у студента

- **Один сервер.** Список — курсы, которые студент добавил на своём пуле.
- Внутри курса — блоки и задания, как сейчас каталог; прогресс, «Решено», загрузки — без изменений.
- **Поиск** (`/`): публичные курсы пула и курсы, где студент участник (название, описание,
  владелец), и задания внутри открытого курса.
- Ссылка на приватный курс без доступа — «Запросить доступ» прямо из TUI (с комментарием); статус
  заявки виден в списке курсов.
- **Новая ревизия**: курс переключили на новую — студент видит «доступна новая версия» и решает,
  скачать ли; начатая старая работает.
- **Ссылка курса** `https://<pool>/c/<owner>/<name>`: на странице курса — команда установки, которая
  ставит `hashpass`, настраивает пул и добавляет курс. Уже установленный: `+` в TUI → ссылка, или
  `hashpass add <ссылка>`. Ссылка на другой пул — смена пула (с подтверждением).
- Совместимость: старый клиент (без курсов) получает **курс по умолчанию**: `/catalog` без параметра
  отдаёт `default_course` (новое поле `ServerConfig`, `config.py`; на проде `bunnyton/linux`);
  `/task/name:version` без суффикса отдаёт ревизию, стоящую в этом курсе.

## 10. `hashengine` — только образы

Курсов, блоков, номеров и предложений в `hashengine` нет. Без аргументов на TTY — рабочий TUI
(Textual), две вкладки (`Tab`):

**«Локально»** — `~/.hashpass/images`, как `docker images`: репозитории → теги → ревизии; задания
деревом по `from`, базовые образы отдельно.

| Клавиша | Действие |
|---|---|
| `Enter` | запустить локально (`cmd_run`, TUI сворачивается на время консоли) |
| `p` | отправить в пул (новая ревизия) |
| `t` | навесить тег (только свой образ) |
| `d` | удалить локальную ревизию (подтверждение) |
| `v` | исходники |
| `/` | поиск |

**«Пул»** — образы пула: свои и чужие.

| Клавиша | Действие |
|---|---|
| `l` | скачать к себе (`pull`) |
| `t` | навесить тег на свою ревизию в пуле |
| `d` | удалить свою ревизию (покажет курсы; в чужих — запрос админу) |
| `v` | исходники (если есть право, §8) |
| `o` | открыть образ в вебе |

Пул один — тот, где вошёл (`L` — войти в другой). Подкоманды остаются; новые `hashengine tag`,
`hashengine rm`; `catalog layout` удаляется (раскладка — в вебе). Ручной пул `:8090` больше не нужен.

## 11. Веб

- `/c` — видимые курсы с поиском; `/c/new` — создать.
- `/c/<owner>/<name>` — курс: описание, блоки и задания, «Пройти» (команда установки / ссылка); у
  приватного без доступа — «Запросить доступ»; для персонала — «Предложения», «Заявки»,
  «Участники» (поиск пользователей, добавить найденных), «Студенты», «Настройки» (видимость,
  `auto_accept`).
- Редактор курса — нынешний редактор каталога (перетаскивание, меню «⋯», скрыть/открыть блок),
  с правами §5.
- Карточка образа `/web/image/<ref>`: теги и ревизии, видимость (публичный/приватный), «в каких
  курсах», «Предложить в курс…», удаление ревизии.
- `/web/users` — админ: поиск по логину и комментарию; запросы на удаление ревизий.

## 12. Переезд прода

Одноразовая идемпотентная миграция при старте нового сервера, с резервной копией данных:
- образы: `name:version` → тег `version`, ревизия `_v1` (хеши — нынешние blob-ы); все репозитории
  `public` (студентам они и сейчас видны только через каталог);
- `catalog.json` → курс `bunnyton/linux` («Linux»), `public`, владелец `bunnyton`; блоки, порядок,
  `hidden`/`open` как есть; задание курса = `_v1`. Где одобренная версия отличается от текущей
  (лежит в `approved/`): одобренная → `_v1` в курсе, текущая → `_v2` + открытое предложение `update`;
  ожидающие новые → предложения `add`; отклонённые → отклонённые предложения;
- `author` → пользователь + автор в `bunnyton/linux`; `group` → начало `comment`;
- `default_course = bunnyton/linux`.
Тест миграции — на обезличенном снимке данных прода. Прод — только по слову пользователя.

## 15. Тесты

- Ревизии: push → `_v(N+1)`; `_latest`; зарезервированные суффиксы отвергаются; `tag` своего/чужого;
  `pull` чужого без переименования; удаление (свои курсы / чужие курсы → запрос, отмена, одобрение →
  переключение), последняя ссылка удаляет хеш.
- Права: матрица §5 (роль × действие), public/private, каждый старый маршрут под `can`.
- Приватные образы: не видны чужим ни в `/images`, ни в `pull`, ни в поиске; видны участникам
  приватного курса — только ревизии этого курса; приватный образ в публичный курс — отказ; смена
  видимости образа/курса с конфликтом — отказ со списком.
- Заявки: создать (одна открытая), принять → участник, отклонить; приватный курс не в поиске.
- Предложения: add/update/withdraw, одно открытое на пару, сдвиг на новую ревизию, auto_accept,
  отклонённые 7 дней, досоздание при сверке.
- Видимость пользователей §7, поиск по комментарию.
