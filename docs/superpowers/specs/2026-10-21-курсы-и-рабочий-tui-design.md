# Курсы, ревизии образов и рабочий TUI `hashengine` — дизайн

Дата: 2026-10-21. Статус: на ревью у пользователя. Вычитан дважды (Codex; Codex + чистый Claude),
замечания учтены, спорные решены пользователем. Кампания из 4 этапов (§15), у каждого свой план.

## 0. Зачем

Пользователь, 2026-10-21:
- «Сделать интерфейс отдельный рабочий. Не смешивать всё в одну корзину».
- «Внутри платформы всё будет состоять исключительно из образов и тегов. Всё остальное — доп.
  накрутки… Простота, элегантность и удобство».
- «Этот проект — объединение github и docker, и потом будет docker-compose».
- «В курс и во всё остальное добавляем только через веб-интерфейс… Можно пушить образы (задания)».
- «hashpass для работы с курсами уже непосредственно. Оттуда уже запускать курс».
- «Сохраняем логику docker с хэшами и тегами… можно образу и заданию в любой момент времени навесить
  любой тег (если этот образ тебе принадлежит)».
- «Можно сделать fork от задания с доработкой, только так можно его скопировать и доделать. А затем
  отправить fork на слияние (типа пул реквеста), и пользователь, если одобрит, — будет новая версия».

Сейчас: один каталог на пул; раскладывает и одобряет только админ; авторы — серверная роль; `push`
перезаписывает `name:version` (`server.py:1130-1164`, `store.py:278-301`); локально автор работает
через ручной пул `:8090` и `deploy.sh` с массивом `BLOCKS`.

## 1. Модель: три слоя

| Слой | Аналог | Что это |
|---|---|---|
| **Образ** | Docker-образ | Неизменяемое содержимое, адресуется хешем; имена — теги-указатели (§2) |
| **Курс** (`bunnyton/linux`) | Репозиторий GitHub | Владелец, видимость, участники, блоки → задания (ссылки на ревизии), предложения (§4) |
| **Compose** | docker-compose | Несколько машин в задании. *Потом; в модели только место* |

Реестр образов — ядро, курсов не знает. Курсы, предложения, порядок, прогресс — слой над реестром.
**Студент проходит задания только через курс** (§9); запуск образа по имени — инструмент автора (§10).

## 2. Образы: хеши, теги, ревизии

### 2.1 Имена

- **Репозиторий** — `owner/name`. Писать в него может только владелец namespace (логин).
- **Тег** — `owner/name:tag` (`:1`, `:stable`) — линия ревизий.
- **Ревизия** — `owner/name:tag_vN`, N = 1, 2, 3…, **неизменяема**; номера не переиспользуются
  (удалённая `_v3` не появится снова).
- **`_latest`**: `owner/name:tag` = `owner/name:tag_latest` = последняя ревизия тега.
- **Суффиксы `_v<цифры>` и `_latest` зарезервированы**: такой тег нельзя создать (`build`, `push`,
  `tag`). Миграция переименует существующие (§13).

### 2.2 Хранение

- Ревизия = запись `{n, image_digest, task_digest, parents: [{repo, tag, n}], at, by}` в
  `repos/<owner>/<name>/tags.json`; содержимое — `blobs/<sha256>`.
- **Имя не зашито в содержимое.** Сейчас `meta.json` внутри blob несёт `name`/`version`
  (`blob.py:164-166`), сервер сверяет их с URL (`server.py:161-165`), клиент раскладывает по ним
  (`blob.py:220`). Новый формат: в blob только содержимое и закреплённые родители; имя приходит из
  запроса. Старому клиенту сервер отдаёт blob с `meta.json`, переписанным под запрошенное имя.
- **Родители закрепляются**: при `build`/`push` `from bunnyton/debian:trixie` фиксируется как
  конкретная ревизия (`…:trixie_v4`). Новый базовый образ не меняет уже отправленные задания;
  потомок переходит на него при пересборке.

### 2.3 `push`

- Один `push` = одна ревизия, атомарно: клиент загружает образ, `task/`, исходники и вложения в
  **черновик** (`staging/<id>`), затем `POST …/commit`; сервер под блокировкой репозитория
  проверяет черновик, присваивает `_v(N+1)` и публикует. Незавершённые черновики удаляются через сутки.
- Содержимое совпадает с последней ревизией тега (`image_digest` и `task_digest`) — **ничего не
  происходит**: новой ревизии и предложений нет (как сейчас пропуск по дайджесту, `remote.py:400-431`).
- Старый `hashengine` (без commit): ревизию фиксирует `PUT /task` (последний шаг старого push); его
  `--block` игнорируется с предупреждением в ответе.

### 2.4 `tag`

`hashengine tag <src-ревизия> <dst>` — только в своём namespace: создаёт в теге `dst` новую ревизию
с теми же хешами (данные не копируются). Чужой образ при `pull` лежит под своим именем;
перетегировать его нельзя (отказ: «образ принадлежит <owner>»).

### 2.5 Видимость

- Репозиторий `public` (по умолчанию; видят все вошедшие) или `private` (владелец, админ и участники
  приватных курсов, где стоит его ревизия — только эти ревизии).
- **Приватный образ — только в приватный курс**; в публичный — отказ «сделайте образ публичным».
- **Публичный образ нельзя строить на приватном** (`push` отклоняется), приватным нельзя сделать
  образ, у которого есть публичные потомки или публичные курсы (отказ со списком). Сделать курс
  публичным, пока в нём приватные образы, нельзя (отказ со списком).
- Видимость родителей транзитивна: кто видит ревизию, тот получает её закреплённых родителей
  (`/closure`).

### 2.6 Исходники и README

- **`README.md` виден всегда** (кто видит образ). Нынешний `about.md` переименовывается в
  `README.md` (движок читает оба на переходе; задания в `content/tasks` переименовываются).
- Остальные исходники (Taskfile, `data/`, `hp/`, финал) — **по умолчанию видны всем**, кто видит
  образ, как на GitHub. Настройка репозитория «скрыть служебные файлы» оставляет видимыми только
  `README.md` — исходники тогда видят владелец и админ.
- Известное ограничение (отдельная задача после кампании): скрытый слой `hp/` всё равно уезжает к
  студенту внутри задания (`blob.py:pack_task`) и читается с хоста.

### 2.7 Удаление ревизии

Право владельца. Перед удалением показывается, где ревизия используется: курсы (названия чужих
приватных курсов скрыты — «ещё 2 приватных курса») и образы-потомки.
- На ревизию ссылаются **образы через `from`** — удалить нельзя (как сейчас, `server.py:1185-1199`).
- Не используется или только в своих курсах — удаляется сразу.
- Используется в **чужих** курсах — **запрос на удаление админу**; владелец может отозвать его до
  решения. После одобрения ревизия удаляется.
- В каждом курсе, где стояла удалённая ревизия, задание **убирается из курса**, а персоналу курса
  приходит предложение `restore`: вернуть задание на предыдущую оставшуюся ревизию (меньший N), если
  она есть. Свежие ревизии не подставляются (их никто не проверял).
- Удаляется последняя ссылка на хеш — хеш удаляется из хранилища.

### 2.8 Форк и запрос на слияние

**Форк — единственный способ скопировать чужое задание и доработать его** (перетегировать или
переименовать чужое нельзя, §2.4).
- «Форкнуть» (веб, карточка образа; `hashengine fork <ref>`): ревизия `alice/git-init:1_v3` →
  репозиторий `bob/git-init` (имя можно сменить), тег `1`, ревизия `_v1` с теми же хешами и
  закреплёнными родителями — данные не копируются. Репозиторий помнит происхождение:
  `fork_of: {repo, tag, n}`; на карточке — «форк alice/git-init:1_v3».
- Форкнуть можно ревизию, которую видишь **и чьи исходники видишь** (§2.6): без Taskfile доработать
  нечего. Форк приватного образа — приватный; форк публичного — публичный по умолчанию.
- Дальше форк — обычный свой репозиторий: `hashengine source bob/git-init:1` → правка →
  `hashengine build` → `push` (новые ревизии форка).
- **Запрос на слияние** (merge request, аналог pull request; веб, карточка ревизии форка —
  «Предложить автору»): ревизия форка → тег исходного репозитория, с комментарием. Хранится в
  исходном репозитории: `repos/<owner>/<name>/merges.json`:
  `{id, from: {repo, tag, n}, to_tag, by, comment, state: open|merged|rejected|withdrawn, reason,
  at, decided_by, decided_at}`. Не больше одного открытого запроса от пары (форк-тег → тег); новый
  `push` в форк его не сдвигает — автор запроса обновляет его сам («обновить до vN»).
- Владелец исходного репозитория видит разницу исходников (Taskfile, `data/`, `hp/`, README — по
  файлам, как diff на GitHub), может запустить ревизию форка (`hashengine run`, без зачёта) и
  принять или отклонить с причиной.
- **Принял** → в исходном теге появляется новая ревизия `_v(N+1)` с хешами ревизии форка (как
  `tag`, данные не копируются), `by` = принявший, `merged_from` = ревизия форка. Дальше — обычный
  путь новой ревизии: курсы видят предложение `update` (§6).
- Отклонённые видны автору запроса 7 дней; автор может отозвать открытый запрос.
- Удаление форка не трогает исходный репозиторий; ревизия, принятая слиянием, живёт в исходном
  независимо (общие хеши удаляются, только когда на них нет ни одной ссылки).

## 3. Пользователи

- Серверных ролей две: **пользователь** и **админ**. `student` и `author` (`passwords.py:17`) —
  устаревшие, читаются как «пользователь»; `_AUTHOR_ROLES` (`server.py:78`) заменяется проверками §5.
- **Любой пользователь** может отправлять образы в свой namespace и создавать курсы.
- **Группы упраздняются**: `group` переносится в начало `comment` — при миграции и при регистрации
  старым клиентом (он присылает `group`, `remote.py:230`).
- **Искать пользователей** (по логину и комментарию) может **только админ**.
- **Удаление пользователя**: нельзя, пока у него есть курсы. При удалении снимаются его членства,
  заявки и предложения; образы — по правилам §2.7 (с запросом админу, если в чужих курсах); логин
  **резервируется** — зарегистрировать его снова нельзя (иначе новый владелец получил бы чужой
  namespace). Попытки и прогресс удаляются, как сейчас (`server.py:1654-1655`).

## 4. Курс

`courses/<id>.json`; `id` неизменяем, `owner/name` — адрес. Переименование и передача — не сейчас.

```json
{
  "id": "c-7f3a", "owner": "bunnyton", "name": "linux", "title": "Linux", "description": "…",
  "visibility": "public", "auto_accept": false, "invite": "<токен ссылки-приглашения>",
  "members": {"alice": "author", "bob": "maintainer", "eve": "member"},
  "blocks": [{"id": "b1", "name": "Git", "open": true,
              "tasks": [{"repo": "bunnyton/git-init", "tag": "1", "n": 3,
                         "hidden": false, "added_by": "bunnyton"}]}],
  "proposals": [ … §6 … ],
  "requests": [{"user": "…", "comment": "…", "state": "open|accepted|rejected", "at": "…",
                "decided_by": "…"}],
  "rev": 42, "created_at": "…"
}
```

- Имя — `[a-z0-9-]`, уникально у владельца. Порядок в блоке = номер для студента. Удалить можно
  только **пустой** блок.
- Запись курса — под блокировкой файла; `rev` растёт с каждой записью; веб и клиенты передают
  ожидаемый `rev`, при расхождении — «курс изменился, обновите».
- **Как попадают в курс** (людей в курс не добавляют — приходят сами):
  - **публичный**: студент добавляет курс себе (`hashpass` / веб / ссылка);
  - **приватный**: по **ссылке-приглашению** (`/c/<owner>/<name>?invite=<токен>`, владелец может
    сменить токен) — сразу участник; или **заявкой** «Запросить доступ» (с комментарием) —
    принимает сопровождающий/владелец. Одна открытая заявка на человека; после отклонения повторная
    — не раньше чем через сутки.
  - Роли (автор, сопровождающий) владелец назначает уже вступившим.
- Приватный курс не показывается в поиске; посторонний по ссылке видит название, описание и
  «Запросить доступ».

## 5. Роли в курсе и проверка прав

| Роль | Видит/проходит | Предлагает | Добавляет сам, обновляет свои | Принимает предложения и заявки, убирает/переставляет чужое, блоки | Видимость, роли, приглашение, удаление курса |
|---|---|---|---|---|---|
| посторонний (private) | название, описание | | | | |
| любой (public) / участник (private) | ✓ | ✓ | | | |
| **автор** | ✓ | ✓ | ✓ | | |
| **сопровождающий** | ✓ | ✓ | ✓ | ✓ | |
| **владелец** | ✓ | ✓ | ✓ | ✓ | ✓ |

Админ сервера — всё во всех курсах.

Доступ решают две функции, и **каждый** маршрут, включая старые, проходит через них:
- `can(user, action, course)` — действия с курсом;
- `visible_revision(user, repo, tag, n, purpose)` — можно ли получить ревизию: `run` (задание —
  только если ревизия стоит в курсе, который пользователю виден, или он владелец/админ/персонал
  такого курса; базовый образ — если виден потомок), `pull` (автор: видимость §2.5), `sources` (§2.6).

Маршруты: `/catalog`, `/task`, `/image`, `/closure`, `/submit`, `/attempt`, `/progress`,
`/solution(s)`, исходники и вложения, `/images`, все `/web/*`. Сейчас они проверяют роль и общий
каталог (`server.py:916-1013`, `1223-1260`, `1284-1346`) — это заменяется.

## 6. Предложения

Аналог pull request; ключ — `(курс, repo:tag)`, у пары не больше одного открытого предложения.

```json
{"id": "p17", "kind": "add|update|restore", "repo": "alice/regex", "tag": "1", "n": 2,
 "block_id": "b1", "by": "alice", "comment": "…", "state": "open|accepted|rejected|withdrawn",
 "reason": "…", "at": "…", "decided_by": "…", "decided_at": "…"}
```

- **add**: веб, «Предложить в курс» (со страницы курса или карточки образа) → ревизия (по умолчанию
  последняя), блок, комментарий. Предлагать может любой, кто видит курс и ревизию; сервер проверяет
  это и фиксирует N при создании. Автор/сопровождающий/владелец добавляют **сразу**.
- **update**: вышла новая ревизия тега, стоящего в курсе, — в курсе появляется предложение обновить
  до неё; открытое — сдвигается на новую. Принимать не обязательно. Для задания, которое автор+
  добавил сам, он переключает сам (кнопка «обновить до vN»). Предложения `update` **вычисляются**
  сверкой «последняя ревизия ≠ ревизия курса» при открытии курса и в списке курсов персонала —
  отдельной рассылки при `push` нет (нечему ломаться).
- **restore**: после удаления ревизии (§2.7).
- Решают сопровождающий и владелец (админ). Отклонённые видны автору предложения 7 дней. Автор
  предложения может отозвать его.
- `auto_accept` (по умолчанию **выкл.**) — принимать `add`/`update` сразу.
- Перед решением персонал может запустить ревизию («посмотреть, потрогать»).

## 7. Кого видно

- **Админ** — всех пользователей; только он ищет по ним.
- Владелец, сопровождающий, автор курса — **приступивших к курсу** (добавил курс или запустил в нём
  задание): профиль, прогресс и попытки **этого курса**.
- Обычный пользователь — только себя.

## 8. Прогресс и попытки

- **Зачёт только из курса**: решение засчитывается, когда задание запущено из курса (`hashpass`) на
  ревизии курса. Запуск по имени (`hashengine run`) — без зачёта.
- Прогресс хранится по `repo:tag` (без ревизии): решённое на `_v1` решено и на `_v3`, во всех курсах
  с этим тегом. Запись хранит `course_id` и ревизию, на которой решено.
- Попытки хранят `course_id` и ревизию; персонал видит попытки **своего** курса.
- «Приступил» — `enrollments/<user>.json: {course_id: at}`; старый клиент записывается в курс по
  умолчанию при первом обращении.

## 9. `hashpass` — только курсы

- **Один сервер.** Главный экран — мои курсы; внутри — блоки и задания, как сейчас каталог.
- Запуск задания — **из курса**, на ревизии курса, с зачётом. Команды «запустить образ по имени» у
  `hashpass` нет (`hashpass run <ref>` → подсказка: «задания запускаются из курса; образ по имени —
  `hashengine run`»).
- **Поиск** (`/`): публичные курсы пула и мои курсы; задания внутри открытого курса.
- **Новая ревизия в курсе**: «доступна новая версия» — студент решает, скачать ли; начатая работает.
- **Ссылка курса** `https://<pool>/c/<owner>/<name>` (у приватного — с `?invite=`): страница курса
  показывает команду установки (ставит `hashpass`, настраивает пул, добавляет курс). Установленный:
  `+` в TUI или `hashpass add <ссылка>`. Ссылка на другой пул — смена пула с подтверждением.
  Приватный без приглашения — «Запросить доступ» из TUI, статус заявки в списке курсов.
- **Совместимость со старым клиентом** (обновляется сам с `main`, но может отставать):
  `/catalog`, `/task`, `/image`, `/closure`, `/submit` без курса работают в **курсе по умолчанию**
  (`default_course` — новое поле `ServerConfig`, `config.py:7-20`; не задан — первый публичный курс
  админа); имя без суффикса = ревизия этого курса.

## 10. `hashengine` — только образы

Курсов, блоков, номеров и предложений нет. Без аргументов на TTY — рабочий TUI (Textual), две
вкладки (`Tab`):

**«Локально»** — `~/.hashpass/images`: репозитории → теги → ревизии; задания деревом по `from`,
базовые образы отдельно.

| Клавиша | Действие |
|---|---|
| `Enter` | запустить (`hashengine run`: без зачёта; TUI сворачивается на время консоли) |

## 11. Веб

- Редактор курса — нынешний редактор каталога (перетаскивание, меню «⋯», скрыть/открыть блок),

## 12. Ошибки и конкурентность

- Номер ревизии выдаётся только в `commit` под блокировкой репозитория.
- Курс пишется под блокировкой с проверкой `rev` (§4).
- Миграция (§13) работает до открытия порта; при сбое сервер не стартует и пишет причину.

## 13. Переезд прода

Одноразовая идемпотентная миграция при старте нового сервера, после резервной копии данных:
- образы: `name:version` → тег `version`, ревизия `_v1` (хеши — нынешние blob-ы), все `public`;
  образ без namespace → владелец `bunnyton` (админ); версия с зарезервированным окончанием
  (`…_v2`, `…_latest`) → `…-v2`, `…-latest` со старым именем-псевдонимом для старых клиентов;
- `about.md` в `task/` читается как `README.md`;
- `catalog.json` → курс `bunnyton/linux` («Linux»), `public`, владелец `bunnyton`; блоки, порядок,
  `hidden`/`open` как есть. Одобренная = текущая → `_v1` в курсе. Одобренная ≠ текущая (копия в
  `approved/`): одобренная → `_v1` в курсе, текущая → `_v2` (+ открытое `update`, или отклонённое,
  если обновление отклонено). Ожидающие новые → предложения `add`; отклонённые → отклонённые `add`;
- роли `student`/`author` → пользователь; бывшие `author` → автор в `bunnyton/linux`; `group` →
  начало `comment`; все пользователи с прогрессом → «приступил» к `bunnyton/linux`;
- `default_course = bunnyton/linux`.

Тест — на обезличенном снимке данных прода; повторный запуск ничего не меняет. Прод — только по
слову пользователя (переустановка сервера, перезапуск без `--reset-admin`).

## 16. Тесты

- Ревизии: push → `_v(N+1)`; повтор без изменений — ничего; две параллельные отправки → `_v2` и
  `_v3`, не два `_v2`; незавершённый черновик не виден; `_latest`; зарезервированные суффиксы;
  `tag` своего/чужого; закреплённые родители не сдвигаются от нового базового образа.
- Форк и слияние: форк — те же хеши, `fork_of`; без доступа к исходникам — отказ; форк приватного —
  приватный; одно открытое слияние на пару; принято → новая ревизия исходного тега с хешами форка и
  `merged_from` → в курсах `update`; отклонено/отозвано; diff исходников по файлам.
- Видимость: приватный не виден чужим ни в `/images`, ни в `pull`, ни в `/closure`; публичный на
  приватном — отказ; смены видимости с конфликтом — отказ со списком; README виден всегда;
  «скрыть служебные файлы».
- Удаление: потомки по `from` — отказ; свои курсы — сразу; чужие — запрос, отзыв, одобрение →
  задание убрано + `restore` на меньшую ревизию; номера не переиспользуются.
- Права: матрица §5 (роль × действие); каждый маршрут §5 под проверкой (студент не получает
  ревизию вне своего курса).
- Курс: приглашение, заявка (одна открытая, пауза после отказа), приватный не в поиске, `rev`.
- Предложения: add/update/restore/withdraw, одно открытое на пару, update вычисляется сверкой,
  auto_accept, отклонённые 7 дней.
- Зачёт: из курса — да, `hashengine run` — нет; прогресс по `repo:tag`; попытки по `course_id`.
- Пользователи: поиск только админу; удаление с курсами — отказ; логин зарезервирован.
- Миграция на снимке прода (включая одобренная ≠ текущая, без namespace, зарезервированные
  окончания); повторный запуск — без изменений; старый клиент видит курс по умолчанию и прежний
  прогресс, `--block`/`catalog layout`/`group` обрабатываются.
- TUI: `run_test` + `pilot`; живой `expect` в pty против тестового сервера.
