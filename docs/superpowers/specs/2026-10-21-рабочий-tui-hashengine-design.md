# Рабочий TUI `hashengine` и блок как метка образа — дизайн

Дата: 2026-10-21. Статус: на ревью у пользователя.

## Зачем

Авторы и админы сейчас работают командами (`hashengine build/push/pull/catalog layout`), скриптом
`content/tasks/deploy.sh` с ручным массивом `BLOCKS` и вручную поднятым локальным пулом на `:8090`
(с модерацией, которая локально не нужна). Пользователь, 2026-10-21: «Предлагаю сделать интерфейс
отдельный рабочий. Не смешивать всё в одну корзину… Минимальное движение в hashengine pull, push и
остальное»; «По сути, внутри платформы всё будет состоять исключительно из образов и тегов. А всё
остальное — доп. накрутки… Простота, элегантность и удобство».

## Принципы

1. **Ядро — образы и метки.** Собранное задание — это образ на диске (как в Docker: файлы, никакого
   сервера и порта). Куда оно относится, знает сам образ: метка `block`. Каталог пула, номера,
   модерация, скрытие — надстройки пула над образами, в хранилище образов их нет.
2. **Локально — только файлы.** Локального пула нет. Блоки локально выводятся из меток, номеров нет,
   одобрения нет — на своей машине видно всё.
3. **Номер — только у пула.** Место задания в блоке пула назначается при отправке.
4. **Существующие подкоманды остаются** для скриптов; TUI — тонкая оболочка над теми же функциями.

## 1. Метка блока в образе

**Taskfile.** Новая директива верхнего уровня:

```
label block "Git"
```

Форма `label <ключ> "<значение>"` — аналог `LABEL` в Dockerfile; сейчас известен один ключ, `block`
(другие ключи — ошибка разбора). Отдельное слово `label`, потому что `block` уже занят директивой
этапа (`block <cmd> match|unless …`). Нет метки — блок «Архив».

**Где хранится.** В `meta.json` образа (`imagestore/store.py`, рядом с `name/version/parents/
build_key`) полем `labels: {"block": "Git"}`. Не в `task/`: дайджест задания (`taskdigest.py`)
хеширует всё под `task/`, и смена блока тогда требовала бы нового одобрения и перекачки у студентов,
хотя проверять нечего. Метка не входит и в ключ сборки (`build.py:_build_key`): правка одной строки
`label` → `hashengine build` переписывает только `meta.json`, слои те же — как `docker tag`.

**Не наследуется через `from`**: у каждого задания свой блок (иначе всё дерево потомков `intro`
уехало бы за ним).

## 2. Порядок

**Локально** порядок в блоке выводится: родитель по `from` раньше потомка (топологически), задания
без связи — по имени. Порядок блоков локально — по имени, «Архив» последним.

**В пуле** у каждого задания номер — его место в блоке (1, 2, …), как сейчас порядок в
`catalog.json`. Правила при отправке:

| Отправка | Номер не задан | Номер свободен | Номер занят |
|---|---|---|---|
| первая | в конец блока метки | на это место | вопрос (ниже) |
| повторная, метка та же | остаётся где стоит | переезжает на место | вопрос |
| повторная, метка сменилась | в конец нового блока | на место в новом блоке | вопрос |

Вопрос при занятом номере: «вставить перед» (остальные сдвигаются) / «вставить после» / «не
вставлять» (задание отправлено, место не меняется; при первой отправке — конец блока).
В командной строке: `hashengine push <ref> --pos N [--insert before|after|skip]`; без `--insert` при
конфликте — сообщение с вариантами и выход 1, задание не отправлено. «Номер свободен» = N больше
числа заданий в блоке (тогда — в конец).

Ручная перестановка админом в пуле главнее метки: повторная отправка с той же меткой задание не
двигает. Двигает только **смена** метки — для этого пул помнит у записи каталога, с какой меткой
задание пришло в прошлый раз (`label_block`).

Блоки в пуле: блок метки, которого нет, создаётся в конце каталога (открытым, как сейчас
`_target_block`); переставлять блоки — админ в TUI. Переносить чужие задания между блоками и задавать
номер может только админ; автору с `--pos`/сменой метки пул отвечает понятной ошибкой, при этом
первая отправка автора кладёт задание в блок метки (как сейчас `--block`).

## 3. Изменения на сервере пула (минимальные)

Отправка уже передаёт блок: `push_task(..., block=)` → `PUT /task/...?publish=1&block=…` →
`catalog.add_task(block_name=…)`. Меняется:
- клиент берёт блок из метки образа (флаг `--block` остаётся и перекрывает метку);
- новый ref без блока → «Архив» (сейчас — последний блок);
- `add_task` хранит `label_block` и двигает запись только при его смене;
- параметры `pos` и `insert`; конфликт без `insert` → `409 {"error", "taken_by": ref}`;
- нужен перезапуск прод-сервера (только по слову пользователя).

`catalog.json` остаётся единственным местом надстроек пула (порядок, открытость блоков, скрытие,
модерация). `hashengine catalog layout` остаётся для админа.

## 4. TUI `hashengine`

`hashengine` без аргументов на TTY открывает рабочее приложение (Textual, как `hashpass`; без TTY —
текущая справка). Модуль `src/hashengine/tui.py`; общие куски (дерево каталога, `LoginScreen`,
`ConfirmScreen`, `ReasonScreen`, просмотр исходников) берутся из `hashpass` — при необходимости
выносятся в общий модуль, без копирования.

Верхняя строка: `Пул: <url> (<user>, <role>)`. Две вкладки, `Tab` переключает.

**«Локально»** — образы из `~/.hashpass/images` (`ImageStore.list()`): дерево блоков по меткам,
задания помечены, базовые образы — отдельной ветвью «Образы».

| Клавиша | Действие |
|---|---|
| `Enter` | запустить локально (`cmd_run`, TUI на время консоли сворачивается) |
| `p` | отправить в пул (спросит номер; пусто — авто; при конфликте — перед/после/не вставлять) |
| `d` | удалить локальную копию (подтверждение; нужен `ImageStore.remove`, его пока нет) |
| `v` | исходники (`taskfile_path` из `meta.json`) |
| `r` | обновить |

**«Пул»** — каталог выбранного пула для автора/админа (всё: неодобренное, скрытое, отклонённое).
Действия и клавиши — те же, что в TUI `hashpass` (`a`/`n` одобрить/отклонить, `x` скрыть, `o` открыть
блок, `Shift+↑↓` переставить, `Delete` удалить, `v` исходники), плюс:

| Клавиша | Действие |
|---|---|
| `Enter` | запустить версию из пула (админ/автор — последнюю отправленную) |
| `l` | скачать к себе (`pull`), появится во «Локально» |
| `B` / `R` | создать / переименовать блок (админ) |
| `P` | выбрать пул: те, куда уже входил (`creds.json`), и «новый…» с формой входа |

Выбранный пул `hashengine` хранит отдельно от студенческого (`~/.hashpass/engine.json`), чтобы
рабочий выбор не сбивал `hashpass`.

## 5. Что уходит

- Ручной локальный пул `:8090` для сборок: собранное и так лежит на диске и запускается.
  (Идентичность сборки — логин выбранного пула `hashengine`, как сейчас `HASHPASS_POOL`.)
- `BLOCKS` и шаг `catalog layout` в `deploy.sh`: задания несут `label block`, скрипт становится
  «собрать всё → отправить всё».
- В skill `task-authoring` и `dsl-reference.md` — строка про `label block`.

## 6. Ошибки

- Пул недоступен / токен истёк — вкладка «Пул» показывает причину и `L` для входа; «Локально»
  работает без сети.
- Сборки нет локально при `p` — невозможно (список из диска); образ без задания отправляется как
  образ (`push` без `--task`).
- Конфликт номера, гонка с другим админом — сервер решает по своему состоянию, клиент показывает
  его ответ.

## 7. Тесты и проверка

- DSL: разбор `label block`, ошибки (неизвестный ключ, без значения); метка в `meta.json`, не в
  ключе сборки и не в дайджесте задания.
- Каталог: таблица §2 целиком (первая/повторная/смена метки × номер не задан/свободен/занят ×
  before/after/skip), «Архив» по умолчанию, ручная перестановка не сбивается повторной отправкой.
- TUI: `run_test` + `pilot` со стаб-клиентом и временным `ImageStore` (как `tests/test_tui*.py`).
- Живая проверка: `expect` по настоящему `hashengine` в pty против локального тестового сервера —
  сборка → «Локально» → запуск → отправка с номером и конфликтом → одобрение во вкладке «Пул».

## 8. Порядок реализации

1. `label block` в DSL и `meta.json`; `ImageStore.remove`.
2. Сервер и клиент: «Архив», `label_block`, `pos`/`insert`, флаги `push`.
3. TUI: вкладка «Локально».
4. TUI: вкладка «Пул», выбор пула.
5. `content/tasks`: `label block` во всех Taskfile, упрощённый `deploy.sh`, skill.

Каждый шаг — тесты, живая проверка, отдельный коммит. Прод — только по слову пользователя.
