# Репозитории, версии, соавторы и единый `hashpass` — дизайн

Дата: 2026-10-23. Продолжение спеки `2026-10-21-курсы-и-рабочий-tui-design.md`.

## 0. Что сказал пользователь

> Получается, что курс, что образ будут репозиториями как таковыми, в которые можно публиковать и
> предлагать новые версии (это вместо коммитов будет). У версии может быть комментарий — типо что
> поменялось. Будут команды hashpass push, hashpass pull, hashpass clone. Отправляется она как
> предложение об изменении. Там автор уже принимает или если у пользователя есть права — получает.
> Управление курсами только из веба. Если принимаются изменения (можно сравнить 2 версии как в
> github), то новая версия выходит и у неё есть автор. В образе и курсе должны быть отображены
> пользователи. Смесь docker и github.

> Добавь возможность добавления пользователей в курс и образ контрибьютерами (с разными степенями
> прав).

Решения (вопросы 2026-10-23):

1. **Один бинарь `hashpass`.** `hashengine` убираем.
2. **Версия курса — журнал изменений**, а не номерные снимки: студенты всегда видят текущий курс.
3. **Push без прав в чужой образ — сразу предложение** (без ручного fork).
4. **Роли образа — как в курсе**: участник · автор · сопровождающий · владелец. Соавтор видит у себя
   в профиле репозитории, где он соавтор, и курсы, где они используются.

## 1. Единый `hashpass`

Все команды автора переезжают в `hashpass`. `hashengine` остаётся **тонким устаревшим псевдонимом**:
печатает «теперь это `hashpass …`» в stderr и вызывает то же самое. Причина — совместимость: прод
запущен `python3 -m hashengine serve`, и самообновление перезапускает `-m hashengine`; удалить модуль
сразу = прод не поднимется после обновления. Из установщика, помощи, документации и skill
`hashengine` исчезает.

| Команда | Что делает |
|---|---|
| `hashpass` | TUI студента (курсы, как сейчас) |
| `hashpass work` | рабочий экран автора (бывший `hashengine` без аргументов): вкладки «Локально» / «Пул» |
| `hashpass build <Taskfile> [-t имя:тег]` | собрать образ/задание |
| `hashpass push <ref> [-m "что поменялось"]` | отправить новую версию (§3); без прав — предложение |
| `hashpass pull` | без аргумента — задания текущего курса (как сейчас) |
| `hashpass pull <ref>` | скачать образ/задание с пула |
| `hashpass clone <ref> [папка]` | скачать исходники задания (бывший `hashengine source`) |
| `hashpass run <номер\|ref>` | задание курса — с зачётом в курс; любой другой образ — без зачёта (говорит об этом) |
| `hashpass tag`, `rm`, `fork`, `images`, `remote` | как в `hashengine` |
| `hashpass serve`, `migrate-courses` | пул: как в `hashengine` |
| `hashpass login/logout/register/add/search/courses/solution/config` | как сейчас |

Флаг `engine.enabled` / `HASHENGINE_ENABLE` больше ничего не закрывает: публиковать в своё
пространство может любой пользователь (спека 2026-10-21 §3). `catalog layout` — только у пула без
курсов, остаётся скрытой командой.

## 2. Роли в образе (репозитории)

`repo.json` получает `members: {login: role}`; владелец — хозяин пространства имён.

| Роль | Может |
|---|---|
| участник | видеть приватный образ, скачивать, запускать |
| автор | + публиковать новые версии (`push` идёт сразу версией) |
| сопровождающий | + принимать/отклонять предложения, ставить теги, просить удалить версию |
| владелец | + настройки (видимость, служебные файлы), роли, удаление |

Админ пула может всё. Проверка прав в одном месте (`repo_access.can(user, server_role, repo, action)`),
по образцу `access.can` для курсов.

Веб, карточка образа — раздел **«Участники»**: список с ролями виден всем, кто видит образ;
владелец добавляет по логину, меняет роль, убирает. Профиль `/u/<login>`: в «Заданиях» и «Образах»
— свои и те, где человек соавтор (с плашкой роли); «Используется в курсах» — по всем им.

## 3. Версии с комментарием, push как предложение

- `push -m "…"` кладёт комментарий в версию (`message` в записи версии). Без `-m` — пусто.
- **Право публиковать** (автор+): `push` создаёт новую версию, как сейчас; у версии автор = кто
  отправил.
- **Без права**: пул кладёт присланное как версию в форк `<я>/<имя>` (создаёт форк, если нет) и
  открывает **предложение** (существующий запрос на слияние) владельцу с этим комментарием. Клиент
  печатает «отправлено как предложение в alice/lab — решит владелец; посмотреть: <ссылка>».
- **Принятие** (сопровождающий+): выходит новая версия исходного образа; её автор — **предложивший**,
  комментарий — из предложения; кто принял — отдельным полем.
- **Сравнение двух версий** — страница `/web/image/<repo>/compare?from=<tag_vN>&to=<tag_vM>`: список
  изменённых файлов и diff (`tree_diff`, как в предложениях). В таблице версий у каждой — «сравнить
  с предыдущей»; в предложении — «сравнить с текущей».

Старые клиенты (`hashengine push` без `-m`) работают как раньше: версия без комментария; чужое
пространство имён у старого клиента — прежний отказ 403 (новое поведение включает новый клиент
флагом `propose=1` в `begin`), чтобы не превращать старые ошибки в неожиданные предложения.

## 4. Курс: участники и журнал изменений

- **Добавить участника** по логину с ролью (сейчас в вебе можно только менять роль существующим).
  Список участников с ролями виден всем, кто видит курс (не только владельцу).
- **Журнал изменений** `course.history`: каждая правка курса — запись `{at, by, what, comment}`,
  где `what` — человеческое описание: «добавлено bob/git-init:1 в блок Git», «bob/git-init:1 →
  версия 3», «блок Git переименован в Git: основы», «порядок заданий изменён», «настройки: приватный».
  Принятие предложения пишет обоих: «предложил kid, принял bob». Необязательный комментарий к
  правке — поле в формах добавления/обновления.
- Веб, курс — раздел **«История»**: лента записей (новые сверху), у записей про версию задания —
  ссылка «сравнить версии» (§3).
- Предложения курса остаются как есть (спека 2026-10-21 §6); журнал — их итог.

## 5. Совместимость и выкатка

- Сервер: новые поля (`members`, `message`, `history`) необязательны; старые данные читаются как
  «без участников / без комментария / журнал пуст». Миграция не нужна.
- Старые клиенты не меняют поведения (§3). `hashengine` — псевдоним (§1).
- Пушить в `main` по этапам; каждый этап — тесты + живая проверка на `:8090`.

## 5а. Уточнения после вычитки Codex

- **Псевдоним `hashengine`**: `hashengine <args>` ≡ `hashpass <args>` (те же аргументы и код
  возврата), предупреждение — одна строка в stderr. `hashengine` без аргументов ≡ `hashpass work`.
  `python3 -m hashengine serve` продолжает работать; самообновление пула перезапускает тот же модуль,
  которым он запущен, поэтому цикла нет. Локальный автозапуск пула (`cli.py`) — уже `-m hashpass`.
- **`run`** переопределяет запрет прошлой спеки (2026-10-21, «hashpass run не запускает образы»):
  решение пользователя 2026-10-23 — один бинарь. Зачёт по-прежнему только из курса: номер или
  задание текущего курса → с зачётом; иначе — запуск автора без зачёта, с предупреждением.
- **`merges.json`** пишется под fcntl-блокировкой с атомарной заменой (как `repo.json`);
  `members` и `history` — только внутри блокировки своего файла.
- **Принять/отклонить предложение** — сопровождающий+ (не только владелец); новая версия: `by` =
  предложивший, `accepted_by` = принявший, `message` = из предложения.
- **Приватный образ** видят его участники (любая роль) и, как раньше, те, кто играет курс с ним.
- Список участников курса API отдаёт всем, кто может `view`.

## 6. Этапы

1. Единый `hashpass` (+ псевдоним `hashengine`, установщик, помощь, skill, README).
2. Роли образа + раздел «Участники» + профиль соавтора.
3. Версии с комментарием, push-предложение, сравнение версий.
4. Курс: добавление участников, участники видны, журнал изменений.
