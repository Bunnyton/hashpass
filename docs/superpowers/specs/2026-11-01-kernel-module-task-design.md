# Задание «Свой модуль ядра» (kmod) — дизайн

Дата: 2026-11-01. Просьба пользователя: «отдельно сделай задачу-образ для сбора собственного
модуля ядра… скрой решения. Теорию там же рассказывай, но без ничего лишнего, и дай возможность
этот модуль внедрить, оттестировать». Цель — своё **символьное устройство**. Пока одно задание;
дальше ждать указаний.

## Ограничение
Консоль hashpass — контейнер systemd-nspawn на ядре ученика: `insmod` из контейнера попал бы в
ядро хоста (и nspawn его не даёт: нет CAP_SYS_MODULE). Поэтому модуль собирается под ядро
маленькой ВМ QEMU внутри задания и грузится только в ней. KVM в контейнере нет → TCG.

## Образ (`content/tasks/kmod`, `image kmod:1`, на базе `bunnyton/debian:trixie`)
- `run apt-get install`: `linux-image-amd64` (ядро ВМ, /boot/vmlinuz-*), `linux-headers-amd64`
  (kbuild под ТО ЖЕ ядро), `build-essential`, `qemu-system-x86`, `busybox-static`, `cpio`.
- Хелпер `/usr/local/bin/vm` (shell): собирает initramfs (busybox + /init), монтирует каталог
  ученика `~/kmod` в ВМ (9p virtfs, `-virtfs local,path=…,mount_tag=host,security_model=none`)
  в `/mnt`, `-nographic -append "console=ttyS0 quiet"`, `-m 256`. В ВМ — шелл busybox от root:
  `insmod /mnt/hello.ko`, `dmesg`, `cat /dev/…`, `rmmod`, `poweroff`. Ядро упало — ВМ
  перезапускается. Если 9p в ядре Debian модулем — грузить 9p/9pnet_virtio из initramfs.
- Хелпер `vm-check <модуль.ko>` (неинтерактивный): та же ВМ, init-скрипт грузит модуль,
  читает/пишет устройство, печатает результат в консоль и выключает ВМ. Его вывод — то, что
  принимается.

## Шаги (теория дозами; бриф — только база)
1. **Собрать модуль-«привет»** (`~/kmod/hello.c` готов как каркас? — нет: бриф даёт форму
   модуля на других именах; ученик пишет сам). Принято: `observe bool ~/kmod/hello.ko`
   (+ `accept cmd make ok`). Доза: kbuild `obj-m`, `make -C /lib/modules/<ver>/build M=$PWD`.
2. **Загрузить в ВМ и увидеть своё сообщение** — `vm-check hello.ko` / `vm`. Принято по выводу
   (`accept output` со строкой из dmesg ученика — любой текст printk). Доза: `module_init/exit`,
   `printk`, `dmesg`.
3. **Символьное устройство** `/dev/hashpass`: `register_chrdev` (или cdev + class/device для
   автосоздания узла; в busybox-ВМ есть devtmpfs → `device_create` создаёт узел сам), `read`
   отдаёт строку. Принято: `vm-check` печатает то, что выдал `cat /dev/hashpass`, и это
   совпадает с ожидаемой строкой.
4. **Запись**: `write` запоминает присланное, `read` отдаёт его обратно (эхо-устройство).
   Принято: `vm-check` пишет случайную строку и читает её назад.

## Решения скрыты

## Открытые вопросы
- Время загрузки ВМ в TCG (ожидаем 5–20 с) и размер образа (+ ядро, headers, qemu ≈ 300–400 МБ).
- Подделка вывода `vm-check`: `block echo/printf` с той же строкой.
- Как сборка задания (`solve`) запускает QEMU при build (эталон для приёмки) — или приёмка по
  фиксированной строке без эталона.

## Итог реализации (после ревью Codex и живого прогона)
- Устройство — misc (`module_misc_device`): `/dev/hashpass` создаётся сам; строка шага 3 —
  `Hello, kernel!`.
- Отдельного `vm-check` нет: ученик пользуется одной командой `vm`; шаги 2–4 принимаются по
  `accept cmd "vm" ok` + `check exec`, который в СВЕЖЕЙ ВМ (`vm --run`, `hp/vmrun`) грузит его
  `hello.ko` и проверяет: свой текст в dmesg + rmmod / `cat` = Hello, kernel! / запись-чтение двух
  разных строк. Пока `vm` не запускали, проверка не стартует (accept cmd проверяется первым).
- Эталоны — `solve` с `printf` в Taskfile (`#include` вне кавычек был бы комментарием).
- Живые находки: QEMU в проверке — только с `</dev/null`; вывод SeaBIOS — escape-коды, их режет
  `vmrun`; busybox ash зовёт апплет `poweroff` мимо PATH → `/init` ловит USR1/USR2/TERM и
  делает `poweroff -f`; `hint output` — подстрока, не регулярка.
