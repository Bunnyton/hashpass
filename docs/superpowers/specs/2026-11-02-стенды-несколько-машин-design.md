# Стенды: несколько машин в одной сети — design

Дата: 2026-11-02. Статус: черновик на согласование.

## 1. Зачем

Сейчас задание = один образ = одна машина (консоль студента), и эта машина делит сеть с
компьютером студента. Для лаб, где нужна сеть (ping/ssh/веб-сервер на соседней машине, DNS,
маршрутизация между подсетями, файрвол), нужен аналог docker-compose: **несколько машин,
поднятых одновременно и связанных изолированной сетью**, а студент сидит в одной из них.

Пользователь (2026-11-02): «связь нескольких контейнеров и их одновременный запуск с целью
прохождения лаб, где нужна сеть… это будет задание, но не образ, а пул образов».

## 1а. Решение пользователя (2026-11-02) — ПЕРЕКРЫВАЕТ §2–§5 ниже

«По аналогии с docker-compose, только не для Dockerfile, а для Taskfile»; на узлы — только
по сети (ssh). Значит:

- Новый файл **`Labfile`** — аналог `docker-compose.yml`. Он и есть задание: в нём
  `lab <имя>:<версия>`, блоки `machine <имя>` и вся логика задания (say/read/stage/settings/
  hidden/readme — как в Taskfile; проверки на машинах — `check live on <машина>`).
- Каждая машина собирается из **своего Taskfile** (`build <каталог|путь к Taskfile>` — как
  `build:` в compose) или берётся готовым образом (`image <ref>` — как `image:` в compose).
  Taskfile машины — обычный рецепт образа (`from`/`run`/`copy`), без `stage` (lint).
  Общие машины переиспользуются между заданиями курса через общий каталог (`build ../_net/web`)
  или опубликованный образ — как в compose.
- Одна машина помечена `console` — за ней сидит студент.
- `net`, `gw`, `hostname`, `settings hosts off`, `check live on` — как в §3, но внутри
  `machine`.
- **Хранение — без изменений на сервере.** `hashengine build Labfile` собирает образы машин,
  затем ref стенда = образ, у которого родитель = образ консоли, а слой = только
  `/.hp-nodes/<машина>/` (дельта цепочки образа машины над базой, слитая снизу вверх) +
  `lab.json`. Пул видит обычный образ-задание; closure = стенд + цепочка консоли. Маска
  `/.hp-nodes` для консоли — как в §4. Наследование стенда через `from` (§2) **отпадает**:
  переиспользование — через общие Taskfile машин.
- Запуск/сеть/канал проверки/хуки на узлах — §6–§8 без изменений.

Пример:

```
lab net-hello:1

machine pc
  console
  build pc                 # pc/Taskfile: from bunnyton/debian:trixie, run apt-get install -y curl openssh-client
  net lan 10.0.0.10/24

machine web
  build web                # web/Taskfile: nginx + openssh-server
  net lan 10.0.0.20/24

hidden hp
say "В соседней комнате стоит сервер web…"

stage
  say "Открой сайт на машине web"
  solve curl -s http://web/
  check live on web grep -q 'GET / ' /var/log/nginx/access.log
```

## 2. Новое понятие — стенд (первоначальный вариант; см. §1а)

**Стенд** — образ, в котором кроме консоли лежат ещё машины (узлы) и описание сети.
Снаружи это по-прежнему ОДИН ref (`bunnyton/net-hello:1`): каталог, курсы, прогресс, пул,
ревизии, модерация, форки работают без изменений. Внутри — пул образов: корневая ФС консоли
плюс дельта каждого узла и `lab.json` с адресами.

- Образ без узлов — как сегодня (одна машина, сеть хоста). Ничего не меняется.
- Образ/задание с хотя бы одной строкой `net` или блоком `node` — стенд.
- Стенд наследуется через `from`: задание `from net-hello:1` получает его узлы и сеть и
  может доописать узел (добавить шаги) или добавить новый. Так курс по сетям строит 5–10
  заданий на одной топологии, как сейчас задания-продолжения наследуют консоль.
- Стенд-заготовка без `stage` (Imagefile с узлами) тоже допустим — задания строятся `from` него.

### Почему не отдельная сущность со своим ref

Отдельный «Standfile» со своим типом ref потребовал бы новых маршрутов пула, closure по
новым рёбрам, изменения ревизий/закреплений родителей, веба, каталога, курсов — и всё это
деплоится на prod с каждым пушем в main. Стенд-внутри-образа даёт то же переиспользование
(через `from`) при **нуле изменений на сервере**. (Мой выбор; см. §11, вопрос 1.)

## 3. Синтаксис (Taskfile / Imagefile)

```
image net-hello:1
from bunnyton/debian:trixie
run apt-get install -y curl openssh-client     # шаги консоли — как раньше

net lan 10.0.0.10/24          # top-level: интерфейс консоли (это и делает образ стендом)
hostname pc                   # имя консоли в стенде (по умолчанию pc)

node web
  run apt-get install -y nginx openssh-server
  copy data/index.html /var/www/html/index.html
  net lan 10.0.0.20/24

node router
  net lan 10.0.0.1/24
  net wan 192.168.50.1/24
  gw 192.168.50.254             # маршрут по умолчанию (необязательно)

node db
  from bunnyton/pg-base:1       # снимок чужого образа как основа узла (необязательно)
  net wan 192.168.50.30/24
  gw 192.168.50.1

settings
  hosts off                     # не писать /etc/hosts (для заданий про DNS); по умолчанию on

stage
  say "Открой сайт на машине web"
  solve curl -s http://web/
  check live on web test -s /var/log/nginx/access.log
```

Правила:
- `node <name>` — блок с отступом; внутри `from`, `run`, `copy` (как у образа), `net`, `gw`.
  Имя узла — hostname: `[a-z][a-z0-9-]{0,14}`, уникально, ≠ имени консоли.
- `net <сеть> <ip>/<prefix>` — интерфейсы `eth0, eth1…` в порядке строк. Имя сети
  `[a-z][a-z0-9-]{0,11}`. Все адреса одной сети — в одной подсети, без повторов (lint).
- `gw <ip>` — default route; адрес должен лежать в одной из сетей машины.
- `from` в узле — основа узла = снимок дельт указанного образа (его цепочка выше базы,
  без его собственных узлов) на момент сборки. Без `from` узел начинается с базы
  (или с узла того же имени из родительского стенда).
- `check live on <node> <cmd>` — то же, что `check live`, но внутри узла.
- Пределы: ≤ 8 узлов, ≤ 4 сетей, ≤ 4 интерфейсов на машину.

## 4. Хранение

В слое образа-стенда — каталог `/.hp-nodes/`:

```
.hp-nodes/lab.json         # полная (с учётом родителей) конфигурация стенда этого образа
.hp-nodes/web/…            # дельта узла web, построенная в этом образе (rootfs-слой)
.hp-nodes/router/…
```

- `lab.json`: `{console: {name, nets:[{net, addr}], gw}, nodes: {web: {nets, gw, fresh}}, hosts}`.
  `fresh: true` — в этом слое у узла задан `from` (или он впервые появился): ниже по цепочке
  его слои не берутся.
- Цепочка узла `n` во время запуска = `L/.hp-nodes/n` для слоёв консоли сверху вниз, пока не
  встретился слой с `fresh` для `n`, + база. Тот же overlay-механизм, что у консоли.
- Конфигурация стенда = `lab.json` самого верхнего слоя цепочки, где он есть.
- **Маска.** Консоль не должна видеть `/.hp-nodes`. Поверх цепочки консоли кладётся крошечный
  нижний слой-маска (whiteout `.hp-nodes`, char 0:0, создаётся один раз через `sudo tar`)
  — во время запуска, вывода приёмки, сборки детей и правки образа. В `ls /`, `df`, `mount`
  ничего нового.
- Пул хранит/раздаёт обычный слой — **сервер не меняется**, digest/ревизии/approved работают.

Ключ кэша сборки включает спецификации узлов (шаги, `from`-образы, сеть).

## 5. Сборка

`build()` после шагов консоли, для каждого узла, объявленного в этом Taskfile:
1. нижние слои узла = цепочка узла из родителей (или снимок `from`-образа) + база;
2. overlay + шаги `run`/`copy` узла (non-boot nspawn, сеть хоста — apt работает);
3. upper узла кладётся в upper консоли как `.hp-nodes/<name>/` (sudo rsync), рядом `lab.json`;
4. `store.save` как обычно.
Прогресс: `узел web: шаг 1/2: выполняю: apt-get install -y nginx`.

Вывод приёмки (derive) идёт по-прежнему на одной консоли без сети. Значит шаги, которым нужна
сеть стенда, принимаются `check live` / `check live on` / `accept cmd|output` — это правило
уходит в skill `task-authoring` и в lint (предупреждение: `observe`-стадия в стенде, у
которой solve обращается к узлу по имени/IP).

## 6. Запуск (сеть без следов на хосте)

Проверено прототипом 2026-11-02 на этой машине (debian 13, docker на хосте, networkd выключен).

Почему не мост на хосте: Docker держит `bridge-nf-call-iptables=1` и `FORWARD DROP` —
кадры через мост в сетевом пространстве хоста дропаются (проверено: 100% loss даже с
`nf_call_iptables 0` на самом мосту). Плюс трогать сеть хоста студента нельзя.

Схема — всё в отдельных сетевых пространствах, через одни лишь `sudo systemd-nspawn`/`machinectl`:
1. **Держатели netns.** На каждую машину (консоль + узлы) и на «коммутатор» — `systemd-nspawn
   --private-network --read-only -D <base> sleep infinity`, зарегистрированная машина
   `hpn-<pid>-<rand>`. Несколько держателей на одной read-only базе работают (проверено).
2. **Проводка.** Один `systemd-nspawn --capability=CAP_NET_ADMIN,CAP_SYS_ADMIN
   --network-namespace-path=<коммутатор>` с `--bind=/proc/<pid>/ns/net:/run/netns/<машина>`
   на каждую машину: в коммутаторе мост на каждую сеть, veth-пары `p<i>` ↔ `eth<k>` в netns
   машины, адреса, `up`, default route. В свежем netns iptables пуст — пакеты ходят
   (проверено: ping 0% loss). Сеть хоста не видит ни мостов, ни veth.
3. **Канал проверки.** Консоль в своём netns не достаёт до `127.0.0.1` хоста. Сервер
   проверки для стенда слушает unix-сокет в рабочем каталоге сессии; в netns консоли
   поднимается реле `systemd-socket-activate -l 127.0.0.1:<port>
   systemd-socket-proxyd /run/hp-grade/sock` (оба бинаря уже в базе; отдельная машина `hpn-`,
   сокет привязан только к ней). `hp-io` в консоли не меняется: `127.0.0.1:$HP_PORT`
   (проверено: ответ прошёл через реле).
4. **Подготовка ФС.** Для каждой машины — overlay по её цепочке; в неё пишется `/etc/hosts`
   (все машины стенда, если `hosts on`).
5. **Узлы** грузятся в фоне: `systemd-nspawn -b -M hp-<pid>-<rand> --hostname=<node>
   --network-namespace-path=<держатель>`. Сеть уже готова к моменту старта служб (nginx
   слушает свой адрес сразу). Ждём регистрации всех узлов, печатаем «поднимаю стенд: web, db…».
6. **Консоль** — как сегодня, foreground `systemd-nspawn -b`, плюс
   `--network-namespace-path=<держатель консоли> --hostname=<имя консоли>`.
7. **Разбор** (finally): узлы → реле → держатели (вместе с ними исчезают мосты и veth) →
   overlay. `reap_orphans` знает и `hpn-`-имена; `no_room` считает только `hp-` (держатели
   без systemd не тратят inotify).

Звук (unix-сокет PulseAudio), TERM, эмуляция на ARM — как у консоли; узлам те же
`nspawn_emulation_args`.

## 7. Проверки

- `check live on <node> <cmd>` — `NspawnRunner.check_live` раннера узла (у него
  `live_machine` = имя узла), т.е. тот же код, что для консоли.
- Всё остальное (`observe`, `accept`, подсказки, block/allow/deny) — про консоль, как сегодня.
- Состояние узлов живёт до конца сессии; следующие задания наследуют образы узлов, а не их
  состояние (как у консоли: что нужно — запекается шагами узла).

## 8. Как студент попадает на узлы

Только по сети, как в жизни: `ssh student@web` (пароль `student` — пользователь уже есть в
базе), `curl http://web/`, `ping db`. sshd/клиент ставит автор шагами узла/консоли.
(Мой выбор; см. §11, вопрос 2.)

**Проверка по каждой команде и на узлах.** Иначе после `ssh web` консоль видит одну долгую
команду `ssh`, и до выхода из неё нет ни приёмки, ни подсказок. Поэтому реле канала проверки
поднимается в netns КАЖДОЙ машины, а `HP_PORT` + `HP_NODE=<имя>` попадают в login-шеллы
узла (файл `/run/hp/port` пишется в ФС узла до загрузки; хук `hp-bashrc` уже стоит во всех
шеллах базы). Команда с узла приходит на хост с именем машины:
- пишется в историю/транскрипт как `web$ systemctl restart nginx`;
- после неё перепроверяется текущая стадия (для `check live`/`check live on`), считаются
  попытки, срабатывают подсказки (`tries`, `idle`, `output`, `cmd`);
- `observe`/`accept cmd`/`accept file`/block/allow/deny — только для команд консоли (они
  про ФС и командную строку консоли); lint предупреждает, если стадия стенда с проверкой
  на узле принимается только ими.
Текст ответа (pass, подсказка) печатается в тот терминал, где набрана команда, — т.е. в
ssh-сессию.

**Права на узлах** — как в консоли (student + sudo, «как в жизни»); подделать `check live`
root-ом можно так же, как и сегодня в консоли. Ответы в узлы не запекаются.

## 8а. Края

- **Несколько `from`.** Стендом может быть не больше одного родителя (lint/ошибка сборки);
  остальные родители — обычные образы.
- **Старый клиент.** Сервер не меняется; новые стенды скрыты, пока их не откроет
  пользователь, а клиенты обновляются сами. Отдельной фазы совместимости нет.
- **Правка образа** (`hashpass run <образ-стенд>` без stage): одна консоль, как сейчас, с
  маской; узлы правятся только через Taskfile; коммит берёт upper консоли — `.hp-nodes` туда
  попасть не может (путь замаскирован).
- **Продолжения.** Решение прошлого задания, сделанное на узле, при сборке не прогоняется —
  нужное состояние узла автор запекает шагами `node` (правило в skill `task-authoring`).

## 6а. Интернет (пользователь, 2026-11-02: «хочу, чтобы был интернет. В docker-compose он же есть»)

Как в docker-compose: у каждой IPv4-сети стенда первый адрес (`.1`) — шлюз наружу, он стоит на
мосту сети в netns коммутатора. Машина без `gw` получает маршрут по умолчанию через шлюз своей
первой сети, где он есть. Если `.1` занимает машина стенда, она и есть маршрутизатор этой сети:
шлюза-коммутатора там нет. DNS: всем машинам пишется `/etc/resolv.conf` → `100.64.250.3`.

Выход наружу: ещё один помощник `hpn-` на сети хоста запускает `slirp4netns` из базы
(`--configure --disable-host-loopback --cidr=100.64.250.0/24 --netns-type=path`) в netns
коммутатора. Получается `tap0` с маршрутом по умолчанию; коммутатор делает
`ip_forward=1` и `nft … oifname tap0 masquerade`. Трафик идёт через обычные сокеты хоста
(userspace NAT, как у rootless podman): ни маршрутов, ни правил firewall, ни интерфейсов на хосте.
Loopback хоста из стенда закрыт. Диапазон `100.64.250.0/24` — служебный, в Labfile запрещён.
Проводка ждёт до 15 с маршрута через `tap0`, так что первая команда студента уже выходит наружу.
`settings internet off` — без шлюзов, NAT и slirp. В базе (runtime 50) — `nftables`, `slirp4netns`.

Приглашение в стенде (runtime 50): каждой машине кладётся `/etc/hp-lab`, и hp-bashrc ставит
имя машины первым: `pc ~ ❯`.

## 9. Цели / не-цели / анти-цели

Цели: стенд из 2–8 машин, несколько подсетей и маршрутизатор, проверки внутри узлов,
наследование стенда заданиями курса, ноль изменений на сервере пула, ноль следов в сети хоста.

Не-цели (сейчас): `apply on <node>`; отдельные терминалы на узлах из TUI; DHCP; IPv6-адресация (link-local есть);
показ топологии в вебе.

Анти-цели: любые изменения iptables/sysctl/интерфейсов хоста; видимые студенту следы
(`/.hp-nodes`, лишние маунты, процессы проверки); поломка обычных заданий (без `net`/`node`
путь запуска побайтно прежний — сеть хоста, TCP-сервер проверки).

## 10. Тестирование

- unit: парсер (`node`, `net`, `gw`, `hostname`, `hosts`, `check live on`), lint (адреса,
  подсети, имена, пределы), сериализация `lab.json`, вычисление цепочек узлов (наследование,
  `fresh`, `from`), генерация `/etc/hosts`, план проводки (команды для helper-а), ключ кэша.
- tier3 (реальный nspawn): собрать стенд консоль+web (+router с двумя сетями), поднять,
  `ping web`/`ping` через роутер, `check live on web` принимает и отвергает, `/.hp-nodes`
  не виден в консоли, после разбора не осталось машин `hp*-<pid>-`, мостов и маунтов.
- live: демо-задание `content/tasks/net-hello` (скрытое, не на prod), пройти через `expect`
  в реальном pty: ssh/curl на web, проверки по каждой команде, `exit`, чистый разбор.
- регрессия: обычное задание (например, `docker-web`) запускается как раньше.

## 11. Решения, которые я принял сам (проверь при чтении)

1. Стенд — это образ с узлами внутри (один ref), а не отдельный тип ref/файла.
2. На узлы — только по сети (ssh ставит автор).
3. Стенд без интернета.
4. Синтаксис: top-level `net`/`hostname` = консоль; `node` = блок; `check live on`.
5. Имя консоли по умолчанию `pc`; интерфейсы `eth0…` по порядку строк `net`.
6. Демо-задание `net-hello` — одно, скрытое, только локально; на prod — по твоему слову.
