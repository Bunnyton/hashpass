# Визуализация стендов (Labfile): машина-наблюдатель — design

Дата: 2026-11-05. Статус: MVP сделан (локальный main), на prod не выкатывался. Основа — вариант 1 из
`2026-11-04-визуализация-стендов-варианты.md` (машина-наблюдатель с зеркалом).

## 1. Решения (координатор, 2026-11-05)

Ответы на четыре вопроса документа вариантов:

1. **Полный трафик**: в интерфейс наблюдателя приходит копия кадров (как SPAN-порт), а не
   только сводка потоков. `tcpdump -i mon0`, tshark, свой разбор — всё работает.
2. **Где смотреть**: браузер на компьютере студента. Консоль печатает адрес при подъёме стенда.
3. **Управление**: статус, `link` (кабель вкл/выкл), `netem` (задержка/потери). Остановки и
   запуска машин нет.
4. **Назначение**: и инструмент задания (студент разбирает трафик), и наглядность стенда.

## 2. Синтаксис Labfile

Три новые строки в блоке `machine`:

```
machine mon
  build ../../machines/labview      # стандартный просмотрщик (или свой Taskfile/образ)
  net lan 10.20.0.30/24              # необязательно: наблюдателю сеть не нужна
  observe all                        # зеркало сетей + лента статуса + канал управления
  view 8080                          # этот порт машины открыть в браузере студента
  control link, netem                # что наблюдателю можно менять
```

| Строка | Где | Смысл |
|---|---|---|
| `observe all` / `observe <сеть> [<сеть>…]` | одна машина на стенд | машина — наблюдатель: интерфейс `mon0` с копией кадров названных сетей, `/run/hp-lab/` (лента + управление) |
| `view <порт>` | любая машина, одна строка | порт машины открывается на компьютере студента: `http://127.0.0.1:<порт>/` |
| `control <оп>[, <оп>…]` | только у наблюдателя | разрешённые операции: `link`, `netem`; `status` есть всегда |

Правила (ошибка парсера, по-русски):
- `observe` — не больше чем у одной машины; сети `observe` должны быть в стенде; `all` — все.
- `view` — порт 1…65535, одна строка на машину.
- `control` без `observe` в той же машине — ошибка; неизвестная операция — ошибка.
- Наблюдатель может не иметь ни одной `net` (чистый SPAN-порт), консоль — нет (как раньше).

`lab.json` получает у машины поля `observe` (список сетей, `all` раскрыт), `view`, `control`.
Старый клиент их не читает — стенд у него поднимется без наблюдения (без ошибок).

## 3. Зеркало трафика (в netns коммутатора)

Весь трафик стенда идёт через мосты коммутатора (§6 спеки стендов), поэтому зеркало ставится
там же, в `wire_script`, после veth-пар:

```
ip link add vmon type veth peer name mon0 netns <наблюдатель>
ip netns exec <наблюдатель> sysctl -qw net.ipv6.conf.mon0.disable_ipv6=1
ip -n <наблюдатель> link set mon0 arp off up      # mon0 только слушает: ни ARP, ни IPv6
ip link set vmon up
# каждый кадр — ровно один раз:
tc qdisc add dev v<i>e<k> clsact                  # порт машины (кроме самого наблюдателя)
tc filter add dev v<i>e<k> ingress matchall action mirred egress mirror dev vmon
tc qdisc add dev br-<сеть> clsact                 # кадры самого коммутатора (шлюз, интернет)
tc filter add dev br-<сеть> egress matchall action mirred egress mirror dev vmon
```

- **Ровно одна копия.** Кадр от машины входит в мост через её порт (ingress) один раз; кадры,
  которые порождает коммутатор (шлюз `.1`, ответы из интернета), уходят через `br-<сеть>` egress.
  Пересылка мостом между портами egress моста не проходит — дублей нет (проверено пробой
  2026-11-05: 3 ping = 6 ICMP + ARP, по одной копии).
- **Порты наблюдателя не зеркалятся**: иначе `ssh mon` + `tcpdump -i mon0` — петля обратной
  связи (вывод tcpdump порождает пакеты ssh, они попадают в mon0…). `vmon` не в мосту — его
  самого зеркалить нечем.
- `mon0` без адреса, `arp off`, без IPv6: наблюдатель ничего не отвечает на копии. Даже если
  root наблюдателя сам пошлёт кадр в `mon0`, тот придёт в `vmon`, а `vmon` не в мосту — кадр
  никуда не уходит. Вмешаться в сеть через зеркало нельзя.
- Широковещательный кадр машины (ARP who-has) входит в мост тоже один раз — через её порт.
  Пересылка из `tap0` в сеть идёт маршрутом коммутатора → через `br-<сеть>` egress.
- Модули `act_mirred`, `cls_matchall`, `sch_ingress` (clsact), `sch_netem` грузятся ядром по
  запросу; `tc` уже в базе (iproute2). **Пересборка базы не нужна.**

## 4. Лента статуса

Хост раз в секунду пишет `status.json` (атомарно: временный файл + `rename`) в каталог
`<sock_dir>/observe/`, который смонтирован в наблюдатель **только для чтения** как `/run/hp-lab`.
Тот же документ отдаёт `GET /status` канала управления.

```json
{
  "version": 1,
  "lab": "net-view", "ts": 1762300000.5,
  "networks": [{"name": "lan", "subnet": "10.20.0.0/24", "gateway": "10.20.0.1"}],
  "machines": [
    {"name": "pc", "console": true, "observer": false, "state": "running",
     "ifaces": [{"iface": "eth0", "net": "lan", "addr": "10.20.0.10/24",
                 "link": "up", "netem": {"delay_ms": 0, "loss_pct": 0},
                 "rx_bytes": 1234, "tx_bytes": 567, "rx_packets": 10, "tx_packets": 8}]}
  ],
  "observer": {"name": "mon", "iface": "mon0", "networks": ["lan"],
               "control": ["link", "netem"]},
  "views": [{"machine": "mon", "port": 8080}]
}
```

- `state`: `running` | `starting` | `stopped`. Консоль — `running`, пока идёт сессия; узлы —
  по `machinectl show -p State` их машин.
- Счётчики — из `/proc/<держатель машины>/net/dev` (держатель живёт в netns машины; файл
  читается обычным пользователем — проверено), т.е. со стороны машины: `rx` = машина приняла.
  Каталог `/proc/<pid>` открывается один раз при старте (fd): переиспользованный PID чужого
  процесса прочитать нельзя; держатель пропал — счётчики нулевые.
- `link`/`netem` — что выставил канал управления (по умолчанию `up` и нули).
- Формат версионируется полем `version`; новые поля добавляются, старые не меняют смысла.

## 5. Канал управления

Unix-сокет `/run/hp-lab/control.sock` (в том же read-only каталоге: `connect()` к сокету на
read-only монтировании разрешён), HTTP/1.0, JSON. Им пользуется любой процесс наблюдателя:

```
curl -s --unix-socket /run/hp-lab/control.sock http://lab/status
curl -s --unix-socket /run/hp-lab/control.sock http://lab/link  -d '{"machine":"web","net":"lan","state":"down"}'
curl -s --unix-socket /run/hp-lab/control.sock http://lab/netem -d '{"machine":"web","net":"lan","delay_ms":200,"loss_pct":10}'
```

| Запрос | Тело | Ответ |
|---|---|---|
| `GET /status` | — | документ §4 |
| `POST /link` | `machine`, `net`, `state`: `up`/`down` | `{"ok": true}` |
| `POST /netem` | `machine`, `net`, `delay_ms` 0…5000, `loss_pct` 0…100 | `{"ok": true}`; оба нуля — снять |

Ошибки: `400` (не тот JSON/поле), `403` (операции нет в `control`), `404` (нет такой машины/
сети у машины), `500` (не удалось выполнить) — тело `{"ok": false, "error": "…"}` по-русски.

**Исполнение — на хосте.** Сервер канала — поток процесса `hashpass run`; запрос проверяется по
`control` из `lab.json` и по модели стенда (имена только из модели — в команды не попадает ни
одной строки из запроса), затем хост запускает одноразовый помощник `systemd-nspawn
--capability=CAP_NET_ADMIN --network-namespace-path=<коммутатор>` (как проводка) с командой:

- `link`: `ip link set v<i>e<k> down|up` — порт коммутатора к машине («выдернуть кабель»: у
  машины `eth<k>` становится NO-CARRIER).
- `netem`: `tc qdisc replace dev v<i>e<k> root netem delay <d>ms loss <l>%` (снять —
  `tc qdisc del … root`). Очередь стоит на выходе коммутатора к машине: задержка/потери
  действуют на кадры, идущие **к машине**; RTT до неё растёт на `delay`. Машина qdisc не видит
  и снять не может.

Запросы выполняются по одному (замок). Сервер: одно соединение — один запрос (HTTP/1.0), тело
только с `Content-Length` и не больше 4 КиБ (иначе `413`), таймаут клиента 5 с. `link`/`netem` в
ленте — применённое состояние: оно меняется только после успешного выполнения помощника.

Права на сокет — `0666`: право даёт Labfile **машине**-наблюдателю, а не отдельному процессу в
ней (студент на mon — тоже наблюдатель). Другие машины сокета не видят: каталог смонтирован
только в наблюдатель. Наблюдатель не получает ни `CAP_NET_ADMIN` в коммутаторе,
ни доступа к хосту: только две операции, разрешённые автором.

## 6. Просмотр в браузере студента

`view <порт>` у машины `m`:
1. Держатель `m` (он в netns машины) поднимает второе реле:
   `systemd-socket-activate -l /run/hp-grade/view-m.sock systemd-socket-proxyd 127.0.0.1:<порт>`
   — как канал проверки, только в обратную сторону — и открывает сокет `chmod 666` (сокет
   создаёт root с 0644, umask socket-activate не слушает — найдено живым прогоном). Служба машины
   должна слушать `127.0.0.1` или `0.0.0.0`.
2. Процесс `hashpass run` слушает **только** `127.0.0.1:<порт хоста>` и перекачивает каждое
   соединение в `view-m.sock` (до 5 с ждёт, пока реле появится). Порт хоста — тот же номер, если
   свободен, иначе любой свободный.
3. При подъёме стенда консоль печатает адрес с **действительно занятым** портом:
   `▸ просмотр mon: http://127.0.0.1:8080/`.

На хосте — только слушатель на loopback внутри процесса студента; ни мостов, ни правил.

## 7. Стандартный просмотрщик

Общая машина `content/machines/labview/` (Taskfile + `labview.py` + `hp-labview.service`),
подключается строкой `build ../../machines/labview` — как общие машины в §1а спеки стендов.
Taskfile ставит `python3`, `tcpdump`, кладёт службу на порт 8080.

`labview.py` (python3, без зависимостей), служба от root:
- ловит кадры с `mon0` сырым сокетом `AF_PACKET`; разбирает Ethernet/ARP/IPv4/ICMP/TCP/UDP;
  держит последние 200 пакетов и счётчики потоков «откуда → куда, протокол/порт»;
- `GET /` — страница: схема (сети-шины, машины-блоки, цвет — состояние, кабель вкл/выкл,
  задержка/потери), таблица потоков, лента последних пакетов; кнопки `link`/`netem`, если они
  разрешены (`observer.control` ленты);
- `GET /api/state` — лента + потоки + пакеты одним JSON (страница опрашивает раз в секунду);
- `POST /api/link`, `POST /api/netem` — пересылает в `control.sock`.

**Свой просмотрщик** — любой Taskfile/образ: служба на порту `view`, читает `mon0` и
`/run/hp-lab/`. Отличие от стандартного — одна строка `build`/`image` в Labfile.

## 8. Жизненный цикл (runtime.py)

`LabRuntime.start(port)`:
1. файлы машин (как раньше);
2. держатели: у машины с `view` — оба реле (`sh -c 'umask 0; … & exec …'`);
3. проводка (с зеркалом);
4. для наблюдателя: каталог `observe/`, первый `status.json`, сокет управления (0666);
   загрузка наблюдателя с `--bind-ro=<observe>:/run/hp-lab`;
5. поток ленты (1 с) и переадресация `view`.

`stop()`: поток ленты, сервер управления, слушатели `view` закрываются до держателей; каталог
сокетов удаляется как раньше.

## 9. Не-цели / анти-цели

Не-цели (MVP): остановка/запуск машин; `netem rate`/дубли/порча; несколько наблюдателей;
зеркало в несколько машин; запись pcap на хост; просмотр в консоли (carbonyl — позже, тем же
`view`); eBPF/NFLOG-режимы (варианты 2, 4).

Анти-цели: изменения сети хоста (кроме loopback-слушателя `view`); права наблюдателя на
коммутатор; любые следы в стенде без `observe`/`view` (путь без них побайтно прежний).

## 10. Тестирование

- unit: парсер (`observe`/`view`/`control`, ошибки), `lab.json` туда-обратно, `wire_script`
  (зеркало: порты, мосты, без портов наблюдателя; без `observe` — без `tc`), документ статуса,
  разбор `/proc/net/dev`, канал управления (права, проверки, скрипты `ip`/`tc`), HTTP по
  unix-сокету, переадресация `view` (на локальном эхо-сервере).
- live (pexpect, демо `content/tasks/net-view`): трафик pc→web виден в `tcpdump -i mon0`,
  `status.json` в mon, `control link down` рвёт ping pc→web, `curl` с хоста открывает
  просмотрщик и его `/api/state`.

## 11. Решения, принятые без пользователя

1. Стандартный просмотрщик — общая машина в `content/machines/labview`, а не служба базы
   (база без python3; так не нужна пересборка базы и prod-деплой).
2. `netem` — на выходе коммутатора к машине (одно направление).
3. Канал управления — HTTP по unix-сокету в `/run/hp-lab`, а не TCP-адрес: его видит только
   наблюдатель.
4. Порты наблюдателя не зеркалятся (петля).

## 12. Вычитка codex (2026-11-05) — что учтено

Принято: лимиты и таймаут канала управления (п. 6); проверка только по модели стенда —
`(машина, сеть)` → имя порта из модели, строки запроса в команду не попадают (п. 7); состояние
`link`/`netem` меняется только после успешной команды (п. 8); счётчики через fd `/proc/<pid>`
(п. 9); порядок остановки: лента, `view`, сервер управления, fd — до держателей (п. 11); печать
действительного порта, повтор подключения к реле, привязка только к `127.0.0.1` (пп. 12, 13, 15).

Отклонено с причиной: «ровно одна копия» под сомнением (пп. 2–3) — подтверждено живым прогоном
(`tcpdump -i mon0`: каждый `seq` ICMP по разу в каждую сторону) и разбором путей моста (§3);
«наблюдатель может слать кадры в mon0» (п. 4) — они уходят в `vmon` вне моста; права `0666` на
сокет (пп. 5, 14) — доверие выдаётся машине, а не процессу (§5); отдельный держатель на реле
`view` (п. 13) — реле живёт в уже существующем держателе машины, нового процесса-машины нет.
Пункт 1 (не реализовано) относился к моменту вычитки.
