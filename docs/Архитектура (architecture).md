# Архитектура и принципы hashpass

Связанные заметки: [[Создание заданий (tasks)]] · [[Хуки (hooks)]] · [[Образы (images)]] · [[Приложение для запуска заданий (Production)]]

---

## 1. Модель исполнения

- **Офлайн-first.** Задания тянутся с сервера (реестр образов), но **исполняются локально в `systemd-nspawn` без интернета**. Полный Linux внутри — своя настройка, пакеты, сервисы.
- **Неизменяемый base-образ → единая среда у всех.** Это замораживает локаль, пакеты, конфиги, порядок сортировки и т.п. — фундамент детерминизма проверок.
- **Сеть нужна максимум для финального зачёта** (см. §7), не для решения.

## 2. Образы и слои

- overlay-слои: наследование от любого образа + дополнение (`base → simple → task`).
- **Технические слои = режимы.** Наследование/запуск определённого слоя включает режим (`taskcreator` / `taskchecker`): режим — свойство композиции слоёв, а не отдельный флаг.
- **Образ = окружение (rootfs).** Логика задания живёт в коде/бандле (§3), а не в бинарном слепке состояния.
- Слои хранятся/раздаются через реестр (pull/push, зависимые слои). См. [[Образы (images)]].

## 3. Задание-как-код и генерация

**Единый источник истины — код задания**, версионируется в git.

Секции кода:
- `setup/infra` — генерация стартовой ФС (**seeded**, см. ниже);
- `stages` — эталонные шаги решения + брейкпоинты (этапы = точки проверки);
- `observe` — наблюдаемый набор файлов/путей на каждом этапе (курируется, см. ниже);
- `checks` — приёмные сигнатуры/условия (деривируется, §4/§5);
- `conditions` — политика команд (§4);
- `hints` — интерактивные подсказки `(триггер → сообщение)` (§7);
- `actions` / сообщения.

Принципы:
- **Режим создания = кодогенератор.** Автор демонстрирует решение (как в [[Создание заданий (tasks)]]), система эмитит **читаемый, редактируемый код** по транскрипту команд + изменениям.
- **Из кода деривится всё остальное автоматически:** прогон в среде (k дифф-пассов, §5), канонические per-stage сигнатуры, конфиг, обвязка чекера, evidence-схема, серверная проверка.
- Сигнатуры/конфиг — **build-артефакты**, руками не правятся: *меняешь код → регенеришь*.
- **Авторский контракт:** убедиться, что генерация верна (демонстрация → нужный код; код → воспроизводимое прохождение + стабильный инвариант). Остальное — автоматом.

**Курация наблюдаемого набора (шаг генерации).** После дифф-прогонов система показывает кандидатные изменённые файлы и помечает, какие поля пережили канонизацию (стабильные), а какие обрезаны (инцидентные). Автор перед финалом делает **include/exclude**; тул подсказывает (стабильное → включить, обрезанное → исключить). Это интерактивная форма `observe_list`/`exclude_list`.

**Разделение образа и логики (стоимость правок).** Образ = только окружение. Логика задания (`checks`, `conditions`, `hints`, `actions`, hooks) — отдельный **config-бандл** (в git), применяется к контейнеру **на старте с хоста** (bind-mount/копия в `/.hash/.task/`), **не запекается в образ**. Три уровня стоимости правок:
1. **подсказки/сообщения/условия/actions** (текст) → правка бандла → **мгновенно, без пересборки**;
2. **приём** (`checks`/сигнатуры) → перегенерация деривацией, **без пересборки окружения**;
3. **окружение** (пакеты, base fs) → **пересборка образа**.

Бандл разбит: `checks.*` (деривится, руками не трогать) / `hints.*` / `conditions.*` (правятся свободно) — чтобы правка подсказок не задевала деривированные проверки.

Границы кодогена:
- Командные решения берутся нативно (транскрипт есть). Интерактив/непереигрываемое (vim, TUI) → recorded-artifact ассерт **или** ручной `@check`.
- Infra для дифф-пассов **seeded**. Свойство задания: **fixed infra → проверка сигнатурой/хэшем**; **per-student random infra → проверка кодом** (`@check` из сида).

## 4. Приём этапа

- **Основа — толерантное сравнение результата** (состояние ФС + вывод последней команды) по **канонической форме**. Path-invariant: принимает нужное состояние независимо от пути.
- **Мера похожести — size-adaptive (см. §5):** Jaccard над шинглами; порог = доля Jaccard. Допуск — чтобы мелкая некритичная разница не заваливала верное решение.
  - **exact crypto-hash** — частный случай (threshold = 1.0) для точных этапов (напр. права `0640`);
  - **ssdeep** — опция для крупных бинарно-фрагментных.
- **Условия метода поверх сравнения (декларативно, `conditions`):** allow/deny-команды, обязательные/запрещённые флаги, упоминания, предикаты. Runtime backed by `@command` (перехват до выполнения: блок/замена/подсказка). **Advisory** — педагогический ограничитель, не защита.
- **`@check` — escape / частный случай:** код для невыразимого (динамика, негатив, randomized-infra). `True/False/None`, `None` → отдать сравнению. См. [[Хуки (hooks)]].
- **Ключ — отдельно:** приёмный хэш только для *проверки*; ключ = детерминированный **nonce** (§6), из нечёткой сигнатуры не выводится.
- **Честная граница:** результат — **authoritative**; метод — **advisory**. Свободный порог прощает «почти-верное» — порогом владеет автор.

## 5. Канонизация и сравнение

**Канонизация (без ручных фильтров по умолчанию):**
- Инвариант выводится **дифференциально**: эталон гоняется **k ≥ 2** раз с безобидным ортогональным шумом (случайные процессы, `create+delete` вне цели). Изменившиеся поля **выбрасываются**. Остаётся стабильная каноническая форма.
- Неизменяемый образ (§1) замораживает среду; дифф-прогоны ловят время/энтропию/порядок (`mtime`, `PID`, `$RANDOM`, `UUID`, `readdir`). Вместе покрывают почти всё.
- Хвост (ручной override — редкость): multi-arch → дериви per-arch; сетевые/временные задания → серверная проверка.
- Guardrail: шум оседает/убирается **до** захвата на брейкпоинте.
- Заменяет ручные `@filter` дефолтом; `@filter` остаётся как override.

**Сравнение канонической формы — толерантное, size-adaptive:**
- вход → **множество шинглов** (символьные n-граммы для коротких, слова/строки для длинных);
- **мелкое → точный Jaccard**; **крупное → MinHash** (оценка Jaccard);
- порог = **доля Jaccard ≥ threshold** — единый интерпретируемый «процент»;
- **exact crypto-hash** = частный случай (threshold = 1.0); **ssdeep** — опция для крупных бинарно-фрагментных.
- **Компаратор + порог пинуются per-stage на генерации** → клиент и сервер сравнивают одинаково.

## 6. Ключи (два уровня)

- **Локальный ключ — подделываемый прогресс-токен** (офлайн-UX): детерминированный **nonce**, выдаётся по факту прохождения, в памяти, **нигде не хранится**, общего мастер-ключа нет. Из приёмного (нечёткого) хэша не выводится.
- **Глобальный ключ — неподделываемый зачёт:** сервер **перепроверяет evidence** и подписывает `HMAC(server_secret, student_id + task_id)`. Секрет только на сервере; привязка к личности → делиться нельзя.
- **Evidence** (per-stage): нечёткий этап — сигнатура/шинглы + id компаратора + порог (сервер пересчитывает Jaccard); exact — crypto-hash; этап с логикой — канонические входы (сервер гоняет `@check`). Плюс метаданные (`task_id`, `stage`, `student_id`, `nonce`, `ts`). Чекер сохраняет наружу **в момент прохождения**.
- **Инварианты:** ключ/секрет **не материализуется** в overlay/readme; **нет общего мастер-ключа на машине**.

## 7. Проверка, прогресс и интерактивность

- Проверка **незаметна**. Ручной ввод ключа — **скрытый фолбэк** (перенос прогресса / преподаватель).
- **Сеть есть** → ждём глобальный (зачёт). **Сети нет** → локальная проверка открывает следующий этап; не выполнить/нужна сеть → **свободный переход** (фолбэк).
- **Фоновая до-сверка** при запуске / переходе к следующему заданию.
- Локальный прогресс **провизорный**: сервер — истина; при расхождении помечаем, силой не откатываем.
- **Интерактивность.** Подсказки задаются в бандле (`hints`) как `(триггер → сообщение)`; триггер — команда/вывод/«застревание» (N команд или T секунд без прогресса). Эволюционируют **без пересборки образа** (§3).

## 8. Распространение ядра

- Ядро (shell, checker, hooks, canonizer) — **исходники в git**, собирается из исходников; образы = **build-артефакт**.
- **Обфускация не даёт защиты** (`marshal`/`base64`/PyInstaller/zip обратимы) → убирается. Безопасность — на серверной подписи, а не на сокрытии.
- Убрать из репозитория и истории: мастер-ключ, zip-пароль.

## 9. Границы честности (threat model)

- **Гарантируем:** результат в пределах порога от корректного (сервер перепроверяет evidence); зачёт неподделываем и привязан к личности.
- **Не гарантируем:** что студент «лично набрал шаги» (для известных решений неотличимо и приемлемо); метод-условия против мотивированного студента (оболочка — не песочница); свободный порог прощает «почти-верное».
- Приемлемо для обучалки; **убирает все тривиальные обходы**: `grep` ключа из overlay, патч чекера, общий мастер-ключ.

## 10. Тестируемость и CI

- **Ports & adapters.** Среда — за интерфейсом `Runner`/`Sandbox`; адаптеры: `TmpdirRunner`, `BwrapRunner`, `DockerRunner` (rootless, без sudo), `NspawnRunner` (прод). Один набор тестов гоняется на всех адаптерах.
- **Три тира:**
  1. **логика (pure)** — канонизация, дифф-обрезка, Jaccard/MinHash, движок хуков, `Cmd`, ключи/HMAC, evidence, парсер/кодоген: юнит-тесты, ноль контейнеров;
  2. **среда без nspawn** — rootless overlay + bwrap/docker: дифф-канонизация, захват, деривация, кодоген end-to-end;
  3. **реальный nspawn** — прод-драйвер.
- **Автономность подтверждена локально** (scoped passwordless sudo на `systemd-nspawn`/`machinectl`/`mount`/`umount`/`tar`/`rsync`): проверен полный цикл — extract → overlay compose → run-as-root → **персист в upperdir** → umount; и boot-режим `nspawn -b` → `machinectl` register/status/poweroff. Разработка ведётся с реальным драйвером без участия человека.
- Опционально: добавить `systemd-run` в sudoers для host-side exec в booted-машину в тестах.
- **CI:** те же тесты; тир 3 — на self-hosted раннере (эта машина) или GH Actions VM.

## План модернизации

Порядок (P0 → далее):

1. **Clean-rebuild** (см. решение о подходе): greenfield-репозиторий + walking skeleton (порт механик среды из `dev`, не копипаст) + **CI (ruff + тесты)** с первого коммита. Единый source-of-truth из исходников; образы = build-артефакт.
2. **Инфра-план** (порт): `systemd-nspawn` + overlay, модель образов/слоёв, реестр, арка, инструментированная оболочка. Референс — `dev` + [[Баги и фичи]] + install-скрипты. Валидация на реальной машине.
3. **Логический план** (рерайт по этому документу, TDD): приём этапа (size-adaptive Jaccard/MinHash + exact/ssdeep как частные случаи; починка семантики порога), дифф-канонизация, `@check`/conditions/hints, config-бандл + курация observe.
4. **Задание-как-код + кодоген** из режима создания; деривация конфига/сигнатур автоматом.
5. **Двухуровневые ключи + evidence + серверная подпись**; ключ = nonce; убрать мастер-ключ/обфускацию/zip-пароль; реестр — аутентификация записи.
6. **Незаметная проверка + офлайн-прогресс + фоновая до-сверка + интерактивные подсказки.**
7. **Миграция контента:** 30+ заданий + образы → под task-as-код (заодно проверка кодогена).
8. **Точечные баги старого кода** (референс при порте): цепочка `send_statistic`; `pull(args)` в `play`; `except Exception():`; `join([..., e])`; мёртвый `raise`/`print`; `Cmd.is_similar`.
