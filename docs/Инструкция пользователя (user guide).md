# Инструкция пользователя

Эта инструкция описывает повседневную работу с hashpass: установку, расположение данных, команды CLI, запуск заданий и минимальный пример собственного `Taskfile`. Полный справочник DSL находится в отдельном документе: [Авторинг заданий (task authoring).md](<Авторинг заданий (task authoring).md>).

## Установка и требования

hashpass работает с настоящей Linux-системой внутри контейнера Debian. Для этого нужны:

- Python 3.13;
- `systemd-nspawn`, обычно из пакета `systemd-container`;
- поддержка `overlayfs`;
- Docker;
- scoped passwordless sudo на команды `mount`, `umount`, `systemd-nspawn`, `rsync`, `tar`, `machinectl`.

Docker используется не как рантайм для заданий. Он нужен только один раз, чтобы экспортировать базовый rootfs из образа `debian:trixie-slim`. После этого базовый образ `debian:trixie` кэшируется и переиспользуется при сборках и запусках.

Установка CLI из корня репозитория:

```bash
make install
```

Эта команда ставит пакет в editable-режиме через `pip install --user -e .`, после чего в `PATH` появляется команда `hashpass`.

Удаление:

```bash
make uninstall
```

Если устанавливать пакет не нужно, можно запускать CLI напрямую:

```bash
python3 -m hashpass <команда>
```

Например:

```bash
python3 -m hashpass images
```

## Каталог `~/.hashpass`

По умолчанию hashpass хранит рабочие данные в `~/.hashpass`. Путь можно заменить переменной окружения `HASHPASS_HOME`:

```bash
export HASHPASS_HOME=/path/to/hashpass-home
```

В этом каталоге находятся локальное хранилище образов и заданий, базовый rootfs, кэш слоёв сборки, временные рабочие каталоги, данные локального реестра и кэш учётных данных.

Базовый rootfs создаётся при первом `build` или `run`, если его ещё нет. Неизменные шаги сборки кэшируются: если `Taskfile` и входные файлы не менялись, hashpass не выполняет их заново.

## Команды CLI

Все команды доступны через `hashpass`. Без установки используйте тот же синтаксис после `python3 -m hashpass`.

### `hashpass build <Taskfile>`

Собирает образ или задание из одного файла рецепта. Формат файла один и тот же: `Taskfile` или `Imagefile`. Если в рецепте есть хотя бы один блок `stage`, собирается задание; если блоков `stage` нет, собирается обычный образ.

```bash
hashpass build Taskfile
```

При сборке нужен логин. hashpass спрашивает его один раз и кэширует токен. Собранный ref получает namespace владельца: если в файле указано `image showcase:1`, после логина `alice` образ будет сохранён как `alice/showcase:1`. После сборки используйте ref, который CLI напечатал в строке `собрано`.

Имя и версию можно переопределить флагом `-t`:

```bash
hashpass build Taskfile -t my-lab:1
```

После сборки обычный образ отправляется в локальный реестр на `127.0.0.1`; hashpass запускает этот реестр сам, если он ещё не работает. Задания сохраняются локально, потому что скрытая логика проверки не отправляется как часть registry-blob.

### `hashpass run <ref>`

Запускает сохранённый ref. Используйте полный ref с namespace владельца — тот, что `build` напечатал в строке `собрано`.

```bash
hashpass run alice/showcase:1
```

Если ref указывает на задание, открывается интерактивная консоль студента. Если ref указывает на образ без `stage`, открывается обычная контейнер-среда с shell. Запуск локальный и не требует логина.

### `hashpass images`

Показывает локально собранные образы и задания:

```bash
hashpass images
```

Вывод содержит ref и тип: `image` или `task`.

### `hashpass serve`

Запускает локальный реестр:

```bash
hashpass serve
```

По умолчанию реестр слушает `http://127.0.0.1:8080`. Его данные лежат в `~/.hashpass/registry`. Адрес можно переопределить переменной `HASHPASS_REGISTRY`.

### `hashpass login`

Выполняет вход в реестр и кэширует токен:

```bash
hashpass login http://127.0.0.1:8080 -u alice
```

Если `-u` не указан, CLI спросит имя пользователя. Пароль вводится интерактивно.

### `hashpass push <ref>`

Отправляет ref и его цепочку родительских слоёв в реестр:

```bash
hashpass push alice/showcase:1 http://127.0.0.1:8080
```

Для push нужен кэшированный вход в указанный реестр.

### `hashpass pull <ref>`

Забирает ref и его цепочку родительских слоёв из реестра в локальное хранилище:

```bash
hashpass pull alice/showcase:1 http://127.0.0.1:8080
```

После pull ref можно запускать локально через `hashpass run`.

## Как проходить задание

Запуск задания выглядит как обычная работа в Linux-консоли:

```bash
hashpass run alice/showcase:1
```

hashpass загружает контейнер в foreground-boot, то есть терминал становится консолью системы внутри контейнера. В начале авторский текст печатается вживую, посимвольно. Затем появляется цель текущей стадии.

Студент вводит обычные команды Linux. Они выполняются внутри контейнера, а после каждой команды хост невидимо проверяет текущую стадию. Проверка может смотреть на файлы, каталоги, вывод последней команды или на результат скрытого грейдера. Проверяющая логика находится вне студенческой среды, поэтому студент не видит команды проверки, скрытые файлы и ключи.

Если стадия пройдена, hashpass переходит к следующей цели. Обязательных системных фраз вроде «принято» или «завершено» нет: любой текст приёмки задаёт автор через `on pass`, `voice bye` или финальные действия. Если решение неверное, стадия просто не проходит, и студент остаётся в той же задаче.

Подсказки тоже задаёт автор. Они могут появляться после заданного числа попыток, после простоя, по конкретной команде или по фрагменту вывода.

Автор может ограничить команды на стадии. В режиме `allow` выполняются только разрешённые команды, с учётом нейтральных команд навигации. В режиме `deny` запрещённые команды не запускаются вовсе: shell отвечает сообщением вида `Команда «X» запрещена.`.

Чтобы завершить сессию, введите:

```bash
exit
```

Ключ зачёта не печатается на экран. Он сверяется под капотом на сервере через HMAC с секретом, поэтому его нечего списывать из терминала или подделывать из вывода.

## Собрать своё первое задание

Создайте отдельный каталог и файл `Taskfile`:

```bash
mkdir -p /tmp/hashpass-hello
cd /tmp/hashpass-hello
```

Минимальный пример задания из одной стадии:

```text
image hello-report:1
run mkdir -p /home/student

stage "Запишите слово ГОТОВО в файл /home/student/report.txt"
  solve echo ГОТОВО > /home/student/report.txt
  observe /home/student/report.txt
```

Здесь `run` готовит окружение на этапе сборки. Блок `stage` задаёт цель, `solve` описывает авторское эталонное решение, а `observe` указывает, какой путь сравнивать при проверке.

Соберите задание:

```bash
hashpass build Taskfile
```

При первом запуске сборка может занять больше времени: hashpass экспортирует `debian:trixie-slim` через Docker, собирает базовый `debian:trixie` и сохраняет его в кэш.

Запустите задание:

```bash
hashpass run <ваш-логин>/hello-report:1
```

В консоли выполните:

```bash
echo ГОТОВО > /home/student/report.txt
```

После успешной проверки стадия будет пройдена. Подробности о `stage`, `variant`, `observe output`, `allow`, `deny`, `check exec`, подсказках и скрытых грейдерах смотрите в [гайде по авторингу](<Авторинг заданий (task authoring).md>).

## FAQ и подводные камни

### Нужен ли `systemd-nspawn`?

Да. Задания запускаются как настоящая Debian-система через `systemd-nspawn`, а слои собираются через `overlayfs`. Без `systemd-container`, поддержки overlayfs и настроенного scoped sudo полный цикл `build`/`run` не заработает.

### Зачем нужен Docker?

Docker нужен только для первого экспорта базового rootfs из `debian:trixie-slim`. Дальше hashpass использует кэш в `~/.hashpass` и запускает задания через `systemd-nspawn`, а не через Docker.

### Где лежат данные?

По умолчанию в `~/.hashpass`. Там находятся образы, задания, базовый rootfs, рабочие каталоги, локальный реестр и кэш входа. Для другого расположения задайте `HASHPASS_HOME`.

### Почему сборка спрашивает логин?

Сборка сохраняет образ в namespace владельца и использует локальный реестр. Логин спрашивается один раз, затем токен берётся из кэша.

### Что делать, если команда в задании не выполняется?

Проверьте, не ограничил ли автор стадию через `allow` или `deny`. Запрещённые команды блокируются до запуска, поэтому они не меняют состояние контейнера и не помогают пройти стадию.
